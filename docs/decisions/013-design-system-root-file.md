# ADR 013: Дизайн-система как docs/design-system.md

**Дата:** 2026-02-14
**Статус:** Принято

---

## Контекст

После нескольких месяцев разработки UI компоненты Simply накопили "визуальный долг":
- Разные сессии AI-ассистента использовали разные цвета: `bg-gray-100`, `bg-slate-50`, `bg-zinc-100` — для одних и тех же элементов
- Не было единых правил для hover-эффектов, отступов, шрифтов
- Не было документации по структуре UI (layout groups, навигация) — что привело к созданию дублирующих компонентов
- Переключение тем (light/dark) работало некорректно из-за хардкоженных цветов

Нужен документ-закон, который:
1. Определяет все визуальные правила
2. Документирует структуру UI (layout groups, навигация, существующие компоненты)
3. Предотвращает создание дублирующих компонентов
4. Читается AI-ассистентом перед любой работой с UI

---

## Решение

Создать файл `docs/design-system.md` — единый закон дизайн-системы.

Механизм принуждения:
1. **CLAUDE.md** (секция "UI и дизайн") содержит обязательную инструкцию: "Перед ЛЮБОЙ работой с UI — прочитай docs/design-system.md"
2. **docs/design-system.md** содержит полные правила + карту UI + проверочную grep-команду
3. **DOCUMENTATION_GUIDE.md** регистрирует файл как ⭐ критически важный + добавляет в чек-лист при изменениях

---

## Причины

1. **SSOT** — один файл, одно место. Не дублируем правила в CLAUDE.md, README и т.д.
2. **docs/ — правильное место** — согласно DOCUMENTATION_GUIDE.md, детальная документация живёт в `docs/`. Корень проекта — для точек входа (README, CLAUDE.md).
3. **CLAUDE.md как триггер** — Claude Code автоматически читает CLAUDE.md при старте. Инструкция в нём заставляет прочитать docs/design-system.md.
4. **Структура UI предотвращает дубли** — раздел 1.3 файла перечисляет ВСЕ существующие компоненты навигации. Прежде чем создавать новый — проверь существующие.

---

## Последствия

### Плюсы

- AI-ассистент всегда читает правила через цепочку: CLAUDE.md → docs/design-system.md
- Единые hover-паттерны, цвета, шрифты
- Карта UI предотвращает дубли компонентов
- Следует правилам DOCUMENTATION_GUIDE.md (docs/ для деталей)
- grep-проверка в конце файла: 0 хардкоженных цветов

### Минусы

- Два шага для AI: прочитать CLAUDE.md → затем docs/design-system.md (но CLAUDE.md итак требует чтения документации)
- Нужно обновлять при добавлении новых страниц или layout-ов

---

## Альтернативы

### Альтернатива 1: SIMPLY_DESIGN_SYSTEM.md в корне

**Что это:** Файл в корне проекта (первоначальное решение из ТЗ-DS).

**Почему отклонили:**
- Нарушает DOCUMENTATION_GUIDE.md — детальная документация должна быть в docs/
- Корень и так загружен файлами (README, CLAUDE.md, SIMPLY_STATUS.md, CHANGELOG.md и т.д.)
- Claude Code итак читает CLAUDE.md → ссылка на docs/ работает так же

### Альтернатива 2: Правила прямо в CLAUDE.md

**Что это:** Все правила дизайна в CLAUDE.md.

**Почему отклонили:**
- CLAUDE.md уже 300+ строк — навигация, не место для деталей
- Нарушает SSOT — правила смешиваются с описанием структуры проекта
- CLAUDE.md = краткие ссылки, docs/ = полные правила

## Содержимое docs/design-system.md

| Раздел | Что описывает |
|--------|---------------|
| 1. Структура интерфейса | Layout groups, карта страниц, компоненты навигации, паттерн header |
| 2. Цвета | Семантические токены, запреты, исключения |
| 3. Шрифты | Lora, Source Sans 3, JetBrains Mono |
| 4. Типографика | Стили заголовков, текста, labels |
| 5. Hover-паттерны | A: карточки с border, B: inline-элементы |
| 6-7. Тени, Радиусы | Стандарты |
| 8. Статусы задач | Цвета и иконки по статусам |
| 9. Отступы | Карточки, секции |
| 10. Dark Mode | Палитра, правила |
| 11. Правила новых компонентов | Запрет дублей, анализ layout-ов |
| 12. Проверка перед коммитом | grep-команда |
