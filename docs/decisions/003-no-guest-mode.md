# ADR 003: Удаление guest режима

**Дата:** 2026-01-26
**Статус:** Принято

---

## Контекст

Проект NegotiateAI (MIR.TRADE) изначально поддерживал guest режим для анонимных пользователей через NextAuth. Это позволяло новым пользователям попробовать чат-бот без регистрации.

**Текущая ситуация:**
- Guest mode реализован через NextAuth credentials provider
- Session cookies для guest пользователей
- История чатов guest пользователей хранится в БД
- Нет различий в функциональности между guest и authenticated users

**Новое применение:**
- Проект превращается в семейный AI-ассистент для 2 пользователей
- Приватный проект без публичного доступа
- Персонализация под конкретных пользователей (роли, system prompts)
- База знаний привязана к пользователям

---

## Решение

Полностью удалить guest режим. Приложение будет доступно только для authenticated пользователей с предопределенными аккаунтами.

**Изменения:**
- Удалить credentials provider из NextAuth
- Удалить guest session logic
- Require authentication на всех роутах
- Оставить только PostgreSQL adapter для NextAuth
- Добавить seed скрипт для создания 2 пользователей

---

## Причины

1. **Приватность проекта** - семейный проект не предназначен для публичного использования, guest доступ не нужен

2. **Безопасность** - без guest mode проще контролировать доступ, нет risk неавторизованного использования

3. **Персонализация** - guest пользователи не имеют роли, system prompts требуют authenticated users

4. **Упрощение кода** - удаление guest logic упрощает auth flow, меньше edge cases

5. **База знаний** - персональные проекты и документы требуют привязки к конкретному пользователю

6. **Rate limiting** - проще контролировать использование API (Gemini) для известных пользователей

---

## Последствия

### Плюсы

- Упрощение auth логики (на ~30% меньше кода)
- Лучшая безопасность (нет анонимного доступа)
- Полная персонализация (каждый запрос знает user context)
- Проще управление базой знаний per user
- Легче отладка (всегда известен пользователь)
- Меньше edge cases в тестировании

### Минусы

- Нельзя "попробовать" без логина (но это не нужно для семьи)
- Нужен seed скрипт для создания пользователей
- Все пользователи должны иметь аккаунты заранее
- Более жесткое требование к авторизации (может быть неудобно)

---

## Альтернативы

### Альтернатива 1: Оставить guest mode для "пробы"

**Что это:** Сохранить guest режим с ограниченным функционалом

**Почему отклонили:**
- Семейный проект, "пробовать" некому
- Добавляет сложность без пользы
- Guest пользователи не получат персонализацию
- Расход Gemini API на потенциальных гостей

**Когда может быть лучше:**
- Если проект публичный
- Для демо-версии
- Для привлечения новых пользователей

### Альтернатива 2: Guest mode с ограничениями

**Что это:** Guest могут использовать, но с лимитами (5 сообщений, нет истории)

**Почему отклонили:**
- Сложность реализации лимитов
- Не нужно для 2 пользователей
- Дополнительный код для edge case

**Когда может быть лучше:**
- Freemium модель
- Маркетинговый инструмент
- A/B тестирование

### Альтернатива 3: SSO (Google/GitHub OAuth)

**Что это:** Вход через Google или GitHub OAuth вместо guest

**Почему отклонили:**
- Overkill для 2 пользователей
- Зависимость от внешних провайдеров
- Семейный проект не требует OAuth
- Можно добавить позже если нужно

**Когда может быть лучше:**
- Если больше пользователей
- Если нужна быстрая регистрация
- Если используется корпоративный SSO

## Примечания

**Файлы для изменения:**

Auth конфигурация:
- `app/(auth)/auth.ts` - NextAuth config (удалить credentials provider)
- `app/(auth)/auth.config.ts` - Auth options
- `middleware.ts` - Require auth на всех routes

Auth UI:
- `app/(auth)/login/page.tsx` - Форма логина (только email/password)
- Удалить guest login кнопки
- Обновить UX (убрать упоминания guest)

Database:
- `lib/db/schema.ts` - Возможно упростить User schema
- Seed скрипт для создания 2 пользователей

**Seed данные:**

```sql
INSERT INTO users (id, email, role) VALUES
  ('user-1', 'vladimir@example.com', 'engineer'),
  ('user-2', 'julia@example.com', 'marketer');
```

**Middleware обновление:**

```typescript
// Require auth on all routes except /login
export default auth((req) => {
  if (!req.auth && req.nextUrl.pathname !== '/login') {
    return Response.redirect(new URL('/login', req.url))
  }
})
```

**Преимущества для реализации:**

- ~200-300 строк кода можно удалить
- 3-4 файла упростятся
- Тесты станут проще (меньше auth states)
- Меньше security surface area
