# ТЗ: Extract при сжатии (v3.78.0)

**Дата:** 2026-04-08
**Зависимость:** v3.77.0 (MiniMax + расчистка завершены)

---

## Проблема

Extract на каждое сообщение отключён (v3.77.0). Сообщения копятся в контексте, но факты не попадают в MIND. Нужен механизм: когда контекст приближается к лимиту → извлечь факты → освободить контекст.

---

## Что делаем

### 1. Изменить загрузку истории

Текущее: route.ts:349-354 — жёсткий бюджет `maxTokens: 140000`.

Новое: для chatMode=simply загружать **все сообщения где `extractedAt IS NULL`**. Без жёсткого бюджета. Для остальных chatMode — оставить как есть.

### 2. Добавить поле `extractedAt` в таблицу message

```sql
ALTER TABLE message ADD COLUMN "extractedAt" TIMESTAMP;
```

Drizzle schema: `extractedAt: timestamp("extractedAt")` в определение таблицы message.

Миграция: все существующие сообщения остаются `extractedAt = NULL`.

### 3. Подсчёт контекста и триггер Extract

В route.ts для chatMode=simply, **перед** вызовом `streamText`:

Посчитать общий контекст: `systemPromptTokens + mindTokens + historyTokens + newMessageTokens`.

Механизм подсчёта уже есть (route.ts:608-613, `calcUsagePercent()`). Использовать его с правильным лимитом.

**Лимит контекстного окна: 200,000 токенов** (минимум из MiniMax 204K и Sonnet 200K).

Два порога:

| Порог | Условие | Действие |
|-------|---------|----------|
| 80% (160K) | контекст ≥ 160K **И** пауза ≥ 10 минут | Extract в фоне (fire-and-forget) |
| 95% (190K) | контекст ≥ 190K | Extract в фоне **без проверки паузы** |

**Определение паузы:** `Date.now() - timestamp последнего сообщения в БД`. Нового механизма не нужно — просто запрос к БД.

**Fire-and-forget:** Extract не блокирует ответ. Пользователь получает ответ на своё сообщение как обычно. Факты извлекаются параллельно.

**Текущее сообщение:** отправляется модели вместе со всей историей. Extract обработает старые сообщения, и при следующем запросе контекст будет легче.

### 4. Функция batchExtractFacts

Создать в `lib/ai/memory/extract.ts` (рядом с существующей `extractAndStoreFacts`):

**Вход:** userId, chatId, массив сообщений для обработки.

**Логика:**

1. Взять сообщения с `extractedAt IS NULL`, отсортированные по дате ASC
2. Выбрать **самые старые** — они первые кандидаты на извлечение
3. Ограничить batch: максимум 50 сообщений за вызов
4. Сформировать текстовый блок из пар user+assistant
5. Вызвать Anthropic Sonnet **один раз** — «извлеки все значимые факты из этого диалога»
6. Результат → через существующий pipeline: embed → dedup → store в MIND
7. Пометить обработанные сообщения: `UPDATE message SET extractedAt = NOW() WHERE id IN (...)`
8. Если сообщений больше 50 — остальные обработаются при следующем цикле

**Модель:** Anthropic Sonnet (утверждено).

### 5. Ночной cron — страховка

В существующий cron `memory-profile` (00:00 UTC) добавить:

- Для каждого пользователя: есть ли сообщения `chatMode = "simply"`, `extractedAt IS NULL`, старше 24 часов?
- Если да → запустить batchExtractFacts

Подхватывает случаи когда пользователь ушёл на несколько дней.

---

## Что НЕ делать

- НЕ удалять сообщения из БД — они нужны для UI (скролл истории, будущий поиск)
- НЕ трогать загрузку истории для chatMode ≠ simply
- НЕ включать Extract на каждое сообщение обратно
- НЕ трогать extract.ts (существующую функцию) — добавить новую рядом
- НЕ менять модель Extract (Sonnet)

---

## Критерии приёмки

1. **Загрузка истории:** для simply загружаются только сообщения с `extractedAt IS NULL` (проверить SQL-запрос)
2. **Порог 80% + пауза:** отправить много сообщений (набрать > 160K) → подождать 10+ минут → отправить ещё одно → в логах виден вызов batchExtractFacts → в MIND появились факты → у старых сообщений `extractedAt` заполнен → при следующем запросе контекст стал легче
3. **Порог 95% без паузы:** набрать > 190K → отправить сразу → Extract запускается без ожидания паузы
4. **Fire-and-forget:** ответ пользователю приходит без задержки
5. **Ночной cron:** в логах memory-profile видна обработка старых необработанных сообщений
6. **DevPanel:** после Extract факты видны в /settings/memory
