# TZ_SimplyChatUiScaling

**Impact:** 🟧 medium → 🟥 high (симптомы уже сейчас при 326 сообщениях, не через 6-9 мес как прогнозировалось изначально)
**Найдено:** 2026-04-28 при обсуждении долгосрочной устойчивости вечного Simply chat
**Источник:** анализ кода загрузчика и UI на фоне фикса картинок (chat `3353a183`, 326 сообщений за ~5 месяцев). Подтверждённые жалобы владельца на медленное открытие чата 2026-04-28: `GET /simply 200 in 14810ms` (15 сек), `in 22339ms` (22 сек), `in 3019ms` (3 сек) при разогретом dev.

## Проблема

Simply chat = **вечный per-userId** (см. memory `project_simply_chat_persistent`). Сообщения копятся неограниченно. UI и загрузчик к этому архитектурно не готовы.

### Текущее поведение

1. **Сервер** [lib/db/queries.ts:507-599](../../lib/db/queries.ts#L507-L599) — `getMessagesByChatId` имеет cap `maxTokens: 140000`, `maxMessages: 10000`. Когда история превысит 140K токенов — старые сообщения **молча** не вернутся клиенту.
2. **UI** [components/messages.tsx:83](../../components/messages.tsx#L83) — обычный `messages.map(...)`, **virtualization отсутствует**. Все полученные сообщения рендерятся как DOM-узлы.
3. **Граница compaction невидима в UI** — пользователь видит свои старые сообщения, не понимая что модель их уже не помнит (видит только summary). Расхождение mental model.
4. **`getMessagesByChatId` вызывается 3+ раза за одно открытие /simply** — видно в dev-логах: `[Token Aware] Loaded ALL 326 messages` повторяется 3 раза на один GET. Дублирующиеся запросы из RSC + клиентских компонентов. Каждый вызов = полная выборка + парсинг JSON всех 326 сообщений.
5. **`/api/document` стреляет по каждому артефакту в чате** — в логах 10+ запросов по 1-6 секунд каждый при открытии. Eager loading всех документов сразу вместо lazy при скролле к артефакту.

### Прогноз масштабирования

При темпе ~20 сообщений/день (текущий темп владельца):

| Срок | Сообщений | Ткн истории | Что ломается |
|---|---|---|---|
| Сейчас (5 мес) | 326 | 64K | Норма |
| ~6-9 мес | ~700+ | 140K cap | Сервер начнёт обрезать старые сообщения. Первое сообщение **исчезнет из UI** без UX «Load older» |
| ~12-18 мес | ~2K видимых | — | Тормоза скролла, мобилка особенно. Память вкладки 200-500 MB |
| ~2 года | ~14K в БД, ~2K в UI | ~1M total | API-ответ ~1 MB JSON, загрузка чата 3-5 сек, мобилка вешается |

БД (PostgreSQL) и Compaction масштабируются нормально — проблема **только в клиентском слое**.

## Последствия

### 1. Молчаливое обрезание истории на сервере

При превышении 140K — старые сообщения просто не вернутся клиенту. Без UI-индикатора пользователь не поймёт что его первое сообщение существует но не загружено. Subjective experience: «приложение потеряло мою историю».

### 2. Деградация перформанса браузера

При >1000 одновременно отрендеренных сообщений начинаются лаги скролла, особенно на iOS Safari. Reflow на каждое новое сообщение становится ощутимым.

### 3. Mismatch UI ↔ модель

Пользователь видит старое сообщение, ожидает что модель его помнит, задаёт ссылку на него — модель не помнит (видела только summary). Доверие к продукту проседает.

## Предложение решения

Три согласованных шага, выполняются вместе одним ТЗ:

### A) Virtual scroll

Использовать `@tanstack/react-virtual` (стандарт индустрии, что использует ChatGPT/Claude UI). Рендерится только видимое окно ~10-20 сообщений + buffer. Решает (2).

### B) Cursor-based pagination + «Старее»

- API endpoint принимает cursor (timestamp последнего загруженного сообщения)
- При скролле к самому верху видимого окна — подгружает ещё ~50 более старых
- Кнопка «↑ Старее» если автоподгрузка не сработала (mobile-friendly)
- Решает (1) — пользователь явно видит что старее есть и может догрузить

### C) Дедупликация загрузки сообщений

`getMessagesByChatId` должен вызываться один раз на открытие /simply, не 3+. Передавать через RSC в клиентский компонент через props/context, не делать повторных fetch.

### D) Lazy loading артефактов

`/api/document?id=...` — только когда артефакт реально попадает в viewport. На входе в чат — только preview/title. Использовать тот же virtual scroll buffer что и для (A).

### E) Визуальная граница compaction

В месте где у модели заканчивается verbatim window (последние ~40K) и начинается summary — показать UI-разделитель:

```
─── Эти 200 сообщений сжаты в краткое содержание ───
     Модель помнит общий смысл, но не дословно
```

Граница рассчитывается из `chat.compactionIndex` (уже хранится в БД). Решает (3) — пользователь понимает что модель помнит, что забыла.

## Оценка

**Время:** 1.5-2 сессии (UI-heavy, нужны мануальные тесты на mobile + desktop, расширено пунктами C/D).

**Файлы:**
- `components/messages.tsx` — virtual scroll
- `components/chat.tsx` — pagination state
- `lib/db/queries.ts` — cursor-based вариант `getMessagesByChatId`
- `app/(chat)/api/messages/route.ts` или новый endpoint для пагинации
- `components/messages.tsx` или новый компонент — visual compaction divider

**Срочность:** не сейчас. Запускать когда у любого пользователя реально перевалит 500 сообщений или появятся жалобы на загрузку чата.
