**Статус:** Хвост, Medium impact

**Источник:** обнаружено Владимиром во время обсуждения Extract-on-compression триггеров
**Связано с:** [lib/ai/context-limits.ts](../../lib/ai/context-limits.ts), [app/(chat)/api/chat/route.ts:757-793](../../app/(chat)/api/chat/route.ts#L757)

## Симптом

В Simply Chat над полем ввода есть модальный виджет с прогресс-баром контекста. На скриншоте от 2026-04-16 показывает:

```
Контекст                  70 347 / 128 000
████████████░░░░░░░░░     55.0% окна модели (grok-4-1-fast-non-reasoning)

Расход за сессию
Fresh input               334 649     ₽8.53
Cache read                233 381     ₽1.31
Cache write                34 361     ₽4.29
Output                      5 553     ₽0.64
                                     ─────
Итого                                ₽14.77
```

Два самостоятельных бага в одном виджете.

---

## Баг 1 — знаменатель прогресс-бара не соответствует нашей стратегии

### Что не так

**UI говорит пользователю «55% окна модели» → ложная тревога «вот-вот упрёмся в лимит».** Реальный backend считает совсем другое:

| База сравнения | % для 70 347 токенов |
|---|---|
| UI показывает 128K (ложное окно) | **55%** |
| **SIMPLY_CONTEXT_LIMIT = 200K (наша SSOT)** | **35%** |
| До SOFT threshold (120K = 60% от 200K) | ещё 50K токенов в запасе |
| До HARD threshold (160K = 80% от 200K) | ещё 90K токенов в запасе |

### Концептуальная причина

По архитектурному правилу серии Simply_xAI ([SIMPLY_XAI_NOTES.md, ТЗ-XAI-1](../Simply_xAI/SIMPLY_XAI_NOTES.md)):

> **Защита контекста не привязана к размеру провайдерского окна.** Sliding window (140K) + Extract-on-compression независимы. Compaction API живёт для Haiku vision через capability-check.

Виджет нарушает это правило: привязывает индикатор к провайдерскому `contextWindow` конкретной модели (Grok 4.1 Fast), а не к нашему `SIMPLY_CONTEXT_LIMIT` от которого считаются пороги SOFT/HARD в [chat/route.ts:766](../../app/(chat)/api/chat/route.ts#L766).

### Плюс — число 128 000 само по себе подозрительное

Grok 4.1 Fast на xAI API имеет значительно большее окно (нужно сверить с [model-catalog.ts](../../lib/ai/model-catalog.ts) — возможно `contextWindow: 128_000` там проставлено неверно при добавлении записи, либо это legacy от старой модели). В любом случае для Simply UI эта цифра **не должна использоваться** — надо `SIMPLY_CONTEXT_LIMIT`.

### Правильное поведение

1. **Знаменатель** — `SIMPLY_CONTEXT_LIMIT = 200 000` из [context-limits.ts](../../lib/ai/context-limits.ts), не `contextWindow` модели
2. **Маркеры на баре** — SOFT 60% (120K), HARD 80% (160K), Safety 90% (180K)
3. **Label** — «Контекст Simply» или «Контекст (extract-on-compression)», не «окно модели <название>»
4. **Цветовая индикация:**
   - 0–60% зелёный («спокойно»)
   - 60–80% жёлтый («скоро extract, если ≥10 мин паузы»)
   - 80–100% оранжевый («extract сработает немедленно»)
5. **Tooltip** с объяснением что такое Extract-on-compression, в отличие от Anthropic Compaction API в expertise/create/projects

## Баг 2 — «Расход за сессию» без определения термина «сессия»

Что такое одна «сессия»? С открытия страницы? С первого сообщения в persistent чате? С последнего extract? Без определения цифры `Fresh input 334 649` не интерпретируются.

Варианты значения (все возможные):
- **A.** Кумулятив всех API calls в этом persistent Simply Chat за всё время существования чата — тогда 334K fresh input копится годами, бесконечная шкала
- **B.** Сумма с момента открытия страницы — тогда зависит от того когда пользователь перезагрузил (reset на reload странен — теряется прозрачность)
- **C.** Сумма с последнего успешного `batchExtractFacts` (т.е. с того момента когда старые сообщения были помечены `extractedAt`) — **логически самое правильное**: отвечает на вопрос «сколько я набрал с последнего сжатия»
- **D.** Сумма за календарные сутки (sliding 24h window)

### Нужно определить + проверить какая логика сейчас в коде

Не разбирали компонент → не знаем откуда числа тянутся. Первый шаг в ТЗ — **найти компонент** (grep «Расход за сессию», «окна модели», «Fresh input»), прочитать логику, понять что он считает сейчас, сверить с нашим намерением.

## Scope правок (ориентировочно)

1. **Audit model-catalog.ts** — что проставлено в `contextWindow` для `grok-4-1-fast-non-reasoning`. Если 128K — починить на реальное значение (свериться с [docs.x.ai](https://docs.x.ai/) по правилу №0). Это может оказаться отдельным мини-фиксом (catalog audit).
2. **Найти компонент** — grep «Расход за сессию» / «Контекст» / «окна модели». Прочитать логику.
3. **Перевести шкалу на `SIMPLY_CONTEXT_LIMIT`** — импорт из `context-limits.ts`, маркеры SOFT/HARD, правильный label.
4. **Определить «сессию»** — согласовать с Владимиром (вариант C самый логичный) и реализовать. Скорее всего нужна SQL-метка «последний extract» = `MAX("extractedAt")` у сообщений чата.
5. **Tooltip/легенда** — объяснить разницу Extract-on-compression vs Compaction API, чтобы пользователь понимал что видит.
6. **Визуал** — цветовые зоны, пороги.

## Definition of Done

- [ ] Прогресс-бар использует `SIMPLY_CONTEXT_LIMIT` (200K) как знаменатель, не `contextWindow` модели
- [ ] SOFT (60% = 120K) и HARD (80% = 160K) маркеры визуально видны на шкале
- [ ] Label не упоминает «окна модели» — только «Контекст Simply» (или аналогичное)
- [ ] «Расход за сессию» имеет **явное** определение того что такое «сессия» (в коде + в tooltip)
- [ ] `contextWindow` для `grok-4-1-fast-non-reasoning` в model-catalog верифицирован против docs.x.ai
- [ ] Мануальный тест: при `Total context ≈ 46K` виджет показывает ~23% (от 200K), не 36% (от 128K)
- [ ] CHANGELOG запись
- [ ] Никакой регрессии на прогресс-баре в expertise/create/projects (там Compaction API живёт, другие правила — не трогать если виджет живёт только в Simply)

## Риски / открытые вопросы

1. **Компонент возможно используется в нескольких местах** — /simply, /expertise, /create, проектные task-чаты. Нужно проверить, **единый** ли компонент. Если единый — логика должна быть capability-aware: Simply → extract thresholds, остальные → Compaction 100K trigger
2. **«Сессия» может быть осознанным выбором команды** — не моя находка. Перед фиксом уточнить у Владимира что **должно** значить это слово
3. **128K в model-catalog** — если это действительно ошибка catalog, её фикс может задеть cost calculation (`calculateCostRub`), прогресс-бар в DevPanel, другие места. Нужен **audit** всех использований `contextWindow` перед правкой
4. **Тестирование** — трудно вручную воспроизвести 60%/80% (нужно 120K/160K токенов в чате). Эмпирический тест либо через искусственный dev override `SIMPLY_CONTEXT_LIMIT=10_000`, либо через мокап данных в storybook/скрине

## Приоритет — Medium

**Почему не High:**
- Backend работает корректно — реальные пороги Extract-on-compression [chat/route.ts:774-776](../../app/(chat)/api/chat/route.ts#L774) считаются правильно, триггер срабатывает когда надо
- UX-обман создаёт **ложную тревогу**, а не пропускает критическую ситуацию — пользователь думает «скоро предел» когда на деле далеко
- Не блокирует миграцию Simply_xAI — это отдельный косметический / UX дефект

**Почему не Low:**
- Виджет был разработан специально для этой задачи («я всё к этому подводил», цитата Владимира) → его ценность в надёжном отображении → текущее состояние обесценивает работу
- Ложное «55%» может привести к решениям «надо срочно почистить чат» / «не пиши длинные сообщения» — обратный эффект от задуманного
- Дешевый фикс (1 сессия) даст высокий UX return
