## ⛔ БЛОКИРУЮЩИЕ ПРАВИЛА (ЧИТАЙ ПЕРВЫМ)

### Правило 1: Официальная документация — ДО всего остального

**Проблема:** большинство провалов при внедрении ТЗ — от работы по памяти и устаревшему знанию из обучения. Модель думает «я знаю как работает X» → пишет код по догадке → получает сломанный результат → переделываем. Knowledge cutoff = май 2025, всё что вышло позже существует только в интернете.

**Триггер:** ЛЮБАЯ работа которая затрагивает внешнюю технологию — SDK, API, библиотеку, провайдера, AI-модель, CLI-инструмент, облачный сервис. Без исключений. Если технология «знакомая» — это НЕ повод пропустить правило, наоборот: знакомые технологии эволюционируют быстрее всего, и именно по ним чаще всего ошибки «я же помню как было».

```
⛔ ЗАПРЕЩЕНО:
- Начинать ANALYSIS.md не прочитав актуальную официальную документацию всех затронутых технологий
- Предлагать техническую реализацию «по памяти» про API/SDK
- Писать код вызывающий внешнюю API/SDK без верификации актуального синтаксиса и параметров
- Соглашаться с ТЗ архитектора в части технической реализации не сверив предложенный подход с документацией
- Использовать локальный README из node_modules/ как единственный источник — он часто устаревший. Только официальный сайт/репо
- Работать с «фиксированным списком технологий» — списков не существует, правило универсально

✅ ОБЯЗАТЕЛЬНО (перед первой строчкой ANALYSIS.md / перед первой строчкой кода):
1. Перечислить ВСЕ внешние технологии которые затрагивает задача (не только явно упомянутые в ТЗ — также те что всплывают в ходе анализа кода)
2. Для каждой — найти АКТУАЛЬНУЮ официальную документацию:
   - WebSearch: `<технология> official documentation 2026`
   - WebFetch: прочитать найденные страницы
   - Проверить changelog/release notes на свежие breaking changes
3. В ANALYSIS.md создать секцию «Изученная документация»:
   - Список технологий + ссылки
   - Ключевые находки (что изменилось с моего обучения, текущая версия API, ограничения, недокументированные грабли)
   - Красные флаги для данного ТЗ (deprecations, rate limits, breaking changes с последней известной мне версии)
4. Только после этого — переходить к вопросам, рискам, рекомендациям
```

**Если документация не найдена / закрыта / на неизвестном языке** — явно написать об этом в ANALYSIS.md, попросить у пользователя ссылки или primer. НЕ выдумывать API по памяти.

**Применимость:** правило действует не только в Фазе 1 Анализа нового ТЗ. Оно применяется ко всему:
- Формальные ТЗ (Фаза 1)
- Любая мелкая задача которая трогает внешний API/SDK
- Обсуждение технических решений до согласия с архитектором
- Дебаг если есть подозрение что API/SDK ведёт себя не так как я помню
- Переход к новому этапу ROADMAP если этап затрагивает технологию не покрытую предыдущими

**Инструменты для правила:** `WebFetch` и `WebSearch` должны быть разрешены в `.claude/settings.local.json` на широкий диапазон доменов. Если при попытке прочитать документацию получаешь блокировку permissions — немедленно сообщить пользователю, не продолжать работу по памяти.

### Правило 2: После КАЖДОЙ задачи
```bash
npx tsc --noEmit
```
**Результат:** 0 ошибок → можно ставить [x]
**Если ошибки:** Исправить ДО отметки [x]

### Правило 3: После КАЖДОГО этапа
```bash
npm run build
```
**Затем ОБЯЗАТЕЛЬНО:**
1. Написать пользователю: "Этап N завершён. Прошу провести мануальный тест: [список проверок]"
2. **СТОП** — дождаться подтверждения
3. Только после "ОК" переходить к следующему этапу

### Правило 4: НЕ делать "скопом"
```
❌ Этап 1 → Этап 2 → Этап 3 → Этап 4 → build → тест
✅ Этап 1 → tsc → build → ТЕСТ → Этап 2 → tsc → build → ТЕСТ → ...
```

### Правило 5: ROADMAP.md — основной рабочий документ

**ROADMAP — это твой чеклист, а не архивный план.**

```
⛔ ЗАПРЕЩЕНО:
- Прочитать ROADMAP один раз и работать "по памяти"
- Заменять ROADMAP информацией из HANDOFF
- Считать задачу выполненной без отметки [x] в ROADMAP

✅ ОБЯЗАТЕЛЬНО:
- Перед каждой задачей: ПЕРЕЧИТАТЬ задачу в ROADMAP
- После каждой задачи: ОТМЕТИТЬ [x] в ROADMAP
- После каждого этапа: ОБНОВИТЬ статус этапа в ROADMAP (⬜ → ✅)
```

**Роли документов:**
| Документ | Роль | Когда читать |
|----------|------|-------------|
| ROADMAP.md | Рабочий чеклист — ЗАДАЧИ, ВАЛИДАЦИЯ, ФАЙЛЫ | Перед КАЖДОЙ задачей |
| HANDOFF.md | Мост между сессиями — контекст, что было | Только в начале сессии |
| CHANGELOG.md | Лог — что сделано (для истории) | В конце сессии |

**Почему это важно:**
ROADMAP тщательно составляется при планировании: задачи, файлы, критерии валидации, edge cases. Если не использовать его как чеклист — вся эта работа теряется, и через несколько сессий начинаются пропуски.

### Правило 6: Документация = Код (верификация, не копирование)

**Проблема:** Документация устаревает потому что её обновляют "по памяти" или копируют из старых docs, не проверяя реальный код. Результат — потерянные модели, неверные настройки, ложная информация.

```
⛔ ЗАПРЕЩЕНО:
- Обновлять docs/ копированием из существующей документации
- Считать docs/ актуальной без проверки кода
- Писать "providerOptions: нет" не проверив grep-ом

✅ ОБЯЗАТЕЛЬНО:
- Перед обновлением docs/ — прочитать реальный код (grep, Read)
- Сверить КАЖДУЮ модель/настройку с кодом (providers.ts, route.ts, config.ts)
- Если ТЗ затрагивает AI-модели → обновить Реестр конфигураций в ai-providers.md
```

**Ключевые документы и что в них верифицировать:**

| Документ | Что проверять | Против какого кода |
|----------|--------------|-------------------|
| `docs/ai-providers.md` → Реестр конфигураций | Модель, temperature, providerOptions, maxTokens | `lib/ai/providers.ts`, все `route.ts`, clerks, pipelines |
| `docs/ai-chats-map.md` → Быстрый обзор | Модель каждого чата | `api/service-chat/route.ts`, `chat-mode-config.ts`, `model-tiers.ts` |
| `docs/ai-chats-map.md` → Конфигурация провайдеров | Код-блок myProvider | `lib/ai/providers.ts` (скопировать реальный код) |
| `CLAUDE.md` → Структура кода | Пути файлов, описания | Реальная файловая структура (`ls`, `Glob`) |

**Быстрая проверка (команды для копирования):**
```bash
# Все модели в providers.ts
grep -n "anthropic\|google\|model" lib/ai/providers.ts

# Все модели в service-chat
grep -n "modelId\|model:" app/(chat)/api/service-chat/route.ts

# Все providerOptions в проекте
grep -rn "providerOptions\|thinkingConfig\|thinking" lib/ app/

# Все temperature в проекте
grep -rn "temperature:" lib/ app/ --include="*.ts"
```

### Правило 9: Backlog долгов — `specs/_backlog/`

**Проблема:** ТЗ часто закрывались с нерешёнными хвостами — пользователь боялся переносить такие папки в `_archive/`, потому что иначе хвосты потеряются. В результате `specs/` накапливал «замороженные» ТЗ (TZ_MindArtifacts, TZ_SaveFactV2 и др.), которые не были ни активными, ни архивными. FINDINGS.md (Правило 8) фиксирует находки внутри ТЗ, но если папка уходит в `_archive/`, FINDINGS.md уходит вместе с ней — и всё равно теряется из виду.

**Решение:** `specs/_backlog/` — отдельная видимая «доска долгов» вне ТЗ. Каждый долг — отдельный файл-заготовка (по формату SPEC). При закрытии ТЗ в Фазе 4 значимые находки из FINDINGS.md преобразуются в файлы в `_backlog/`, после чего папку ТЗ можно спокойно архивировать.

```
specs/
├── _backlog/                     ← открытые долги (видимы, не в архиве)
│   ├── README.md                ← индекс по impact
│   ├── TZ_<name>.md             ← заготовка ТЗ
│   └── ...
├── _archive/                     ← завершённые ТЗ
├── _template/                    ← шаблоны
├── TZ_<active>/                  ← активные ТЗ
└── WORKFLOW.md
```

**Жизненный цикл одного долга:**

```
1. ТЗ X идёт работа → агент находит костыль вне scope
   ↓
2. Запись в TZ_X/FINDINGS.md (правило 8)
   ↓
3. ТЗ X закрывается. Фаза 4, шаг «FINDINGS → backlog»:
   - Прочитать FINDINGS.md
   - Каждую значимую находку (medium/high impact) оформить как TZ_<name>.md
   - Положить в specs/_backlog/
   - Обновить specs/_backlog/README.md (индекс)
   ↓
4. ТЗ X переезжает в _archive/ — чисто, ничего не теряется
   ↓
5. Когда поднимаем работу над долгом → файл становится исходником ТЗ:
   mkdir specs/TZ_<name>
   mv specs/_backlog/TZ_<name>.md specs/TZ_<name>/SPEC.md
   Дальше — обычный WORKFLOW
```

**Правило перед новым большим ТЗ (мягкое):**

Перед началом любого нового ТЗ Claude **обязан**:
1. Прочитать `specs/_backlog/README.md`
2. Сообщить пользователю: «В backlog N открытых долгов: A, B, C. Хочешь сначала закрыть какой-то из них, или они не блокируют новый ТЗ?»
3. Дождаться решения
4. Если «не блокирует» — стартуем новый ТЗ
5. Если «давай сначала X» — поднимаем X из backlog в полноценный ТЗ

Это **видимость + выбор**, а не **тирания**. Долги не теряются (видны на каждом старте), но и не блокируют развитие.

**Что попадает в backlog (medium/high impact):**
- Молчаливые `try/catch` без логирования
- Мёртвый код, требующий refactor (не однострочный fix)
- Расхождения между документацией и кодом (систематические)
- Архитектурные несоответствия (несколько SSOT для одной сущности)
- Неполное покрытие (логирования / тестов / observability)

**Что НЕ попадает (фиксится сразу при обнаружении):**
- Однострочные правки вроде «убрать неиспользуемый импорт»
- Тривиальные опечатки в комментариях
- Стилистика без функционального impact

### Правило 8: Находки в работе → FINDINGS.md, не текущий scope

**Проблема:** Во время разработки ТЗ постоянно всплывают связанные находки — костыли прошлых агентов, мёртвый код, неточные комментарии, неоптимальные паттерны, расхождения docs/code. Два плохих сценария:

1. **«Заодно починим»** — сразу лезем чинить → scope ТЗ растёт → теряем фокус → ТЗ закрывается медленнее → пользователь нервничает что мы отвлекаемся
2. **«Молча проигнорируем»** — забываем → накапливается технический долг → через месяц никто не помнит откуда это взялось

**Решение:** Файл `FINDINGS.md` в папке ТЗ — единственное место для всех находок, которые НЕ блокируют текущую работу. После закрытия ТЗ файл становится исходником для маленького follow-up ТЗ.

```
⛔ ЗАПРЕЩЕНО:
- Молча игнорировать обнаруженный костыль/баг/мёртвый код
- Расширять scope текущего ТЗ «пока я тут уже» без согласия пользователя
- Складывать находки в голову — забудешь
- Использовать TodoWrite для находок (он чистится в конце сессии, находки потеряются)

✅ ОБЯЗАТЕЛЬНО:
- Любое обнаружение → ЗАПИСЬ в FINDINGS.md СРАЗУ, в момент обнаружения
- Структура записи: что найдено, где (file:line), почему это проблема, предлагаемое решение, оценка влияния (low/med/high)
- Сообщить пользователю одной строкой: «🚩 Нашёл X — записал в FINDINGS, не отвлекаюсь»
- Если находка КРИТИЧНА для текущего ТЗ (блокирует, ломает) — остановиться и обсудить с пользователем, расширять ли scope
- В Фазе 4 (Финализация): просмотреть FINDINGS.md, оформить как follow-up ТЗ (`specs/TZ_XX_Followup.md` или новый ТЗ-файл) если есть значимые находки
```

**Что записывать в FINDINGS.md:**
- Молчаливые `try/catch` без логирования
- `@deprecated` без удаления старого кода
- Магические числа/строки без ADR
- Мёртвые импорты, мёртвые экспорты, мёртвые компоненты
- Дублирующая логика в нескольких местах
- Расхождения между документацией и кодом
- Опечатки и вводящие в заблуждение имена переменных/типов
- Потенциальные улучшения производительности
- TODO/FIXME/HACK комментарии в задетых файлах

**Чего НЕ записывать (это либо сразу чинится, либо вообще не находка):**
- Стилистические придирки без чёткого «почему хуже»
- Гипотетические улучшения без конкретного триггера
- Личные предпочтения по архитектуре

**Формат FINDINGS.md:**
```markdown
# Находки ТЗ-XX

> Список нерешённых проблем, обнаруженных во время работы над ТЗ.
> После закрытия ТЗ — оформить как follow-up задачу.

## 🚩 Finding #1: Краткое название

**Где:** `path/to/file.ts:123-145`
**Что:** Описание проблемы (1-3 предложения)
**Почему проблема:** Конкретное последствие (баг, тех долг, путаница)
**Предлагаемое решение:** Как починить
**Влияние:** low / medium / high
**Обнаружено:** Этап X.Y задачи Z

---

## 🚩 Finding #2: ...
```

**Применимость:** правило универсально для всех ТЗ. Файл создаётся в момент первой находки, не заранее.

### Правило 7: Git-коммиты после КАЖДОГО этапа
```bash
git add [конкретные файлы]
git commit -m "feat(tz-XX): описание этапа"
```
**ЗАЧЕМ:**
- Гранулярный откат при проблемах (вместо "всё или ничего")
- История изменений для отладки (`git bisect`)
- Безопасность — код не теряется

**Формат коммитов:**
| Тип | Когда использовать |
|-----|-------------------|
| `feat(tz-XX):` | Новый функционал |
| `fix(tz-XX):` | Исправление бага |
| `refactor(tz-XX):` | Рефакторинг без изменения поведения |
| `chore(tz-XX):` | Удаление файлов, очистка |

**Порядок действий в каждом этапе:**
```
1. Пишу код
2. npx tsc --noEmit → 0 ошибок
3. npm run build → успешен
4. git add [файлы] && git commit
5. Запрашиваю мануальный тест
6. СТОП → жду подтверждения
```

## КРИТИЧНОЕ ПРАВИЛО

**Задача НЕ выполнена пока не прошла валидация!**

```
❌ "Код написан" — НЕ выполнено
❌ "Я просмотрел код" — НЕ валидация
✅ npx tsc --noEmit = 0 ошибок — валидация
✅ npm run build пройден — валидация
✅ Проверено в браузере — валидация
✅ Пользователь подтвердил — валидация
```


## Структура папки ТЗ

```
specs/TZ_XX_Name/
├── SPEC.md           # Само ТЗ (спецификация)
├── ANALYSIS.md       # Анализ, вопросы, риски
├── ROADMAP.md        # План внедрения (этапы)
├── CHANGELOG.md      # История изменений по этому ТЗ
├── HANDOFF.md        # Передача между сессиями
├── FINDINGS.md       # (создаётся при первой находке) Костыли/баги вне scope, для follow-up ТЗ
└── notes/            # (опционально) Brainstorm, наброски
```

## Описание файлов

### SPEC.md
**Что:** Само техническое задание (копия из браузера Claude)
**Когда создаётся:** В начале работы
**Кто редактирует:** Только пользователь

### ANALYSIS.md
**Что:** Анализ ТЗ, вопросы, выявленные риски
**Когда создаётся:** Сразу после получения SPEC.md
**Формат:**
```markdown
# Анализ ТЗ-XX

## Резюме
Краткое описание что нужно сделать.

## Вопросы для уточнения
1. ...?
2. ...?

## Рекомендации разработчика (Код-ревью)
> См. формат в Фазе 1 → Код-ревью ТЗ

## Потенциальные риски
- Риск 1
- Риск 2

## Зависимости
- Что нужно сделать до начала
- Какие компоненты затронуты

## Оценка сложности
- [ ] Простое (1-2 сессии)
- [ ] Среднее (3-5 сессий)
- [ ] Сложное (5+ сессий)
```

### ROADMAP.md
**Что:** ОСНОВНОЙ РАБОЧИЙ ДОКУМЕНТ — чеклист задач с валидацией
**Когда создаётся:** После ответов на вопросы из ANALYSIS.md
**Когда обновляется:** ПОСТОЯННО — отмечать [x] после каждой задачи, обновлять статусы этапов
**Роль:** Это НЕ архивный план. Это живой чеклист, который перечитывается перед каждой задачей.
**Формат:**
```markdown
# Roadmap ТЗ-XX

## Этапы

### Этап 1: Название
**Статус:** ⬜ Не начат / 🔄 В работе / ✅ Завершён
**Цель:** ...
**Задачи:**
- [ ] Задача 1
- [ ] Задача 2
**Файлы:** ...
**Валидация этапа:** ...
**Критерий готовности:** ...
```

### CHANGELOG.md

#### Код-ревью ТЗ (Senior Dev Review)

**Контекст:** Архитектор пишет ТЗ на основе `SIMPLY_STATUS.md` и продуктового видения. У архитектора **нет доступа к кодовой базе**. Разработчик (Claude Code) знает код глубоко — паттерны, timing, зависимости, edge cases.

**ТЗ — это не жёсткие правила.** Это ориентир. Разработчик обязан:

1. **Проверить техническую реализуемость** — будет ли предложенный подход работать с реальным кодом?
2. **Выявить конфликты с существующей архитектурой** — паттерны, форматы данных, timing
3. **Предложить альтернативу** если видит лучший путь, с обоснованием из кода
4. **Указать на избыточность** — лишние колонки, дублирующая логика, ненужные абстракции

**Формат в ANALYSIS.md:**

```markdown
## Рекомендации разработчика (Код-ревью)

> Ниже — технические рекомендации на основе анализа кодовой базы.
> Каждая рекомендация требует согласования с архитектором.

### ✅ Согласен с ТЗ
- Пункт X — ОК, совпадает с паттерном Y в коде
- Пункт Z — ОК

### ⚠️ Рекомендую изменить
| # | Было (ТЗ) | Рекомендация | Обоснование из кода |
|---|-----------|--------------|-------------------|
| 1 | ... | ... | Файл X:123 показывает что... |
| 2 | ... | ... | Timing issue: onFinish + dataStream... |

### ❓ Требует уточнения
- Пункт N — зависит от будущих планов архитектора
```

**Границы:**
| Разработчик рекомендует | Архитектор решает |
|------------------------|-------------------|
| Техническая реализация (как) | Продуктовый скоуп (что) |
| Существующие паттерны | UX и бизнес-логика |
| Performance, timing, безопасность | Приоритеты и сроки |
| Избыточные абстракции | Стратегия на будущее |

**Важно:** Архитектор может знать то, чего не знает разработчик (будущие планы, смежные ТЗ). Формат: "Рекомендую X потому что Y. Но если планируется Z — подход ТЗ может быть лучше."

**Если замечаний нет** — написать: "Спек solid, технических замечаний нет. Предложенная архитектура совпадает с существующими паттернами."

**Действия:**

**1. Проверка БД (Claude делает):**
```sql
-- Проверить что все таблицы существуют
SELECT table_name FROM information_schema.tables
WHERE table_schema = 'public' ORDER BY table_name;

-- Проверить колонки в изменённых таблицах (адаптировать под конкретное ТЗ)
SELECT column_name, data_type FROM information_schema.columns
WHERE table_name = 'ИмяТаблицы' ORDER BY ordinal_position;

-- Проверить foreign keys
SELECT tc.table_name, kcu.column_name, ccu.table_name AS foreign_table
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage ccu ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_name = 'ИмяТаблицы';
```

**2. Мануальные тесты (пользователь делает):**
- Список конкретных тестов из ROADMAP.md

**2.5. FINDINGS.md → backlog (Правила 8 + 9):**

**3. Документация (по чеклисту [DOCUMENTATION_GUIDE.md](../DOCUMENTATION_GUIDE.md)):**
