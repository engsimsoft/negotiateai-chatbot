| 1 | Пункт 4: «Удалить ВСЕ записи в `briefingHistory` при генерации» | **Мягче:** удалять все кроме `status: "generating"` (текущей), потому что `saveBriefingHistory` вызывается ДО удаления в pipeline | `generate/route.ts:82-87` — первый `saveBriefingHistory({status: "generating"})` вызывается в Step 1. Если удалить всё до этого — потеряем tracking текущей генерации. Если удалить всё после — нужно исключить только что созданную запись. Предлагаю: **удалять старые ПЕРЕД созданием новой записи "generating"** — это проще и чище. |
| 2 | Пункт 4: «Миграция — удалить все кроме свежей» | **Лучше:** Сделать очистку в runtime (в generate endpoint), а не одноразовой миграцией | Drizzle-миграции в проекте — DDL (CREATE TABLE, ALTER). Data-миграция (DELETE rows) — не типичный паттерн. Проще и надёжнее добавить `DELETE FROM briefingHistory WHERE userId = ? AND status != 'generating'` прямо в начало generate pipeline. Старые данные очистятся при первой генерации каждого пользователя. |

| 4 | Пункт 6: «Клик по сохранённой теме — скролл к ней или отдельный вид» | **Рекомендую отдельный вид (inline expand)** | Скролл к теме невозможен — сохранённая тема из прошлого выпуска, её НЕТ в текущем DOM. Предлагаю: клик → раскрывается карточка прямо в sidebar (или в main area) с контентом + источниками. Это проще и не ломает навигацию по текущему выпуску. |

### ❓ Требует уточнения

1. **[Сохранённые темы — просмотр]:** Когда пользователь кликает сохранённую тему в sidebar, что показывать? Варианты:
   - **(A)** Раскрыть карточку inline в sidebar (compact markdown preview)
   - **(B)** Заменить main area на полный рендер сохранённой темы (с кнопкой «← Назад к выпуску»)
   - **(C)** Открыть modal/drawer с содержимым

   Моя рекомендация: **(B)** — заменить main area. Это наиболее естественно: sidebar = навигация, main = контент. Кнопка «← Назад» возвращает к текущему выпуску.

2. **[TTL и маршрут /briefing/[date]]:** Если при генерации удаляются все старые брифинги — маршрут `/briefing/[date]` теряет смысл (всегда будет только одна дата). Удаляем маршрут `[date]` и упрощаем до единственного `/briefing`? Или оставляем для будущего (подписки с историей)?

3. **[Закладка — offline state]:** Когда пользователь сохраняет тему, а потом генерирует новый брифинг (старый удаляется) — сохранённые темы продолжают жить (это задумано и ОК). Но при просмотре текущего выпуска — как определять «эта секция уже сохранена»? Нужен `GET /api/briefing/topics/saved` при загрузке выпуска и match по `topicId + briefingDate`. Подтверждаю — это правильный подход?

4. **[Кнопка «Сгенерировать» и TTL]:** Нужно ли предупреждение «Текущий брифинг будет заменён»? Или генерируем молча, как сейчас?

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Race condition при удалении + создании в generate | Низкая | Потеря данных | Транзакция: DELETE + INSERT в одном SQL-запросе |
| Пользователь сохраняет тему, затем генерирует → иконка закладки не обновляется | Средняя | UX баг | Match сохранённых тем по `topicId` (не по briefingDate), обновить UI после генерации |
| Маршрут /briefing/[date] сломается без истории | Высокая (если TTL) | 404 для старых URL | Либо удалить маршрут, либо redirect на /briefing |
