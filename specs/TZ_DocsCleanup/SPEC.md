## Контекст

После уборки `CLAUDE.md` (653 → 211 строк, процессный фикс в `WORKFLOW.md` + `ROADMAP_GUIDE.md` + `DOCUMENTATION_GUIDE.md`) Владимир заметил две связанные проблемы:

1. **Папка `docs/`** — формально SSOT для технической документации, но по факту устарела или превращена в летопись. `ai-chats-map.md` показывает MiniMax как активный (вранье после xAI миграции), `architecture.md` содержит 21 версионный тег в диаграмме слоёв, `ai-minimax.md` называет M2.7 «основной LLM», `setup.md`/`troubleshooting.md` не трогали с января.
2. **`SIMPLY_STATUS.md` = 2323 строки** — 85% файла дублирует CHANGELOG (65 завершённых ТЗ), только 15% описывает реальное состояние. Версия в шапке (3.90.0) и «Статистика» (3.73.0) отстают. Файл должен быть **снапшотом** текущего состояния, а не хронологическим логом.

## Цель

Привести `docs/` и `SIMPLY_STATUS.md` в соответствие с реальностью кода и процессов, используя уже утверждённые принципы (SSOT, `DOCUMENTATION_GUIDE.md` лимиты, запрет на летопись в навигационных файлах). Работать **маленькими шагами** с HANDOFF между сессиями — защита от «обрезания углов» в длинной сессии.

3. **Этап 3:** `SIMPLY_STATUS.md` переписать с нуля как snapshot (~300 строк): таблица компонентов со статусом, активная серия, метрики, известные баги. Бэкап `.bak` **НЕ** делаем — полагаемся на git.

## Принципы

1. **Маленькие шаги + HANDOFF.** Одна сессия ≤ 1 этап (кроме мелких 4-5). Защита от усталости контекста.
2. **Не делаем `.bak` файлов.** Полагаемся на git — каждый этап один commit, легко откатить.
3. **`keep-spec-docs-simple`** (из MEMORY) — SPEC/ANALYSIS/ROADMAP ведём лаконично, не заполняем все поля шаблонов ради галочки.
4. **Не коммитим автоматически.** После каждого этапа Владимир смотрит diff и коммитит сам.
5. **Официальная документация FIRST** (Правило 1 WORKFLOW) **не применяется** — это уборка внутренних документов, внешних технологий не затрагивает. Зафиксировано в ANALYSIS.
6. **CLAUDE.md при финализации НЕ трогаем** (свежее правило из инварианта в шапке CLAUDE.md и DOCUMENTATION_GUIDE.md). Это не «принципиально новый архитектурный слой».

## Концептуальное разделение STATUS ↔ CHANGELOG (принцип, сформулированный Владимиром 2026-04-15)

**Золотой критерий для SIMPLY_STATUS.md:** отвечает на вопрос **«ЧТО РАБОТАЕТ»**, а не **«ЧТО БЫЛО СДЕЛАНО»**.

| SIMPLY_STATUS.md | CHANGELOG.md |
|---|---|
| Вопрос: *«Что работает сейчас?»* | Вопрос: *«Что и когда мы сделали?»* |
| **Настоящее время** — «Simply Chat работает на Grok 4.1 Fast» | **Прошедшее время** — «2026-04-15 в ТЗ-XAI-3 переключили Simply Chat на Grok» |
| **Фотография** — читается один раз как паспорт | **Дневник** — append-only, растёт вечно |
| Устаревает → **старая запись перетирается**, не аккумулируется | Старые записи **никогда не перетираются** |
| **Нет дат, нет версионных тегов, нет ТЗ-пометок** | Организован по версиям (`[3.91.0]`, `[3.90.0]`, …) |
| Читатель — владелец продукта, новый член команды, новая сессия Claude | Читатель — тот, кто ищет «когда мы починили X» или «что изменилось между версиями» |

**Важное уточнение (Владимир):** SIMPLY_STATUS.md **не source of truth для кода**. Когда Claude Code приступает к реализации — он всё равно читает реальный код (`lib/`, `app/`, `components/`), а не STATUS. STATUS — обзорный документ, для **чтения человеком/AI**, чтобы быстро понять «в каком состоянии сейчас продукт». Это снимает требование к STATUS быть идеально точным — достаточно быть **достаточно актуальным и правдивым в общих чертах**.

**Простая проверка «куда писать»:**
- «Simply Chat сейчас на Grok 4.1 Fast» → **STATUS** (факт настоящего)
- «В ТЗ-XAI-3 мы переключили Simply Chat на Grok» → **CHANGELOG** (событие прошлого)
- «Известная проблема: `getOrCreateSimplyChat` race condition» → **STATUS** (текущий факт)
- «Race condition обнаружен в ТЗ-XAI-2 smoke test» → **CHANGELOG** (событие)

**Следствие для Этапа 3 ROADMAP:** при переписывании SIMPLY_STATUS.md **ни одного глагола в прошедшем времени в описаниях компонентов**. Если формулировка начинается с «был добавлен / была реализована / в v3.X сделали» — это автоматически **в CHANGELOG, не в STATUS**. Если такого факта ещё нет в CHANGELOG (а по аудиту 65 ТЗ-блоков дословно дублируют CHANGELOG — там уже есть всё) — просто выбрасываем. Вариант **A** из обсуждения: если найдутся «сироты» (факт без записи в CHANGELOG / SPEC какого-либо ТЗ) — всё равно выкидываем, git-история сохранит старый SIMPLY_STATUS навсегда.

## Критерии готовности

- `docs/ai-chats-map.md` — MiniMax отсутствует в активных таблицах, Grok присутствует.
- `docs/architecture.md` — `grep -c 'v3\.' docs/architecture.md` → 0 в структурных разделах.
- `SIMPLY_STATUS.md` — ≤ 400 строк, версия совпадает с `package.json`, таблица компонентов отражает реальность.
- `specs/WORKFLOW.md` — чеклист финализации содержит явные триггеры для всех 13 файлов docs/.
- `docs/ai-minimax.md` — banner присутствует в первых 10 строках.
- Каждый этап — отдельный git commit. Владимир одобрил каждый diff вручную.

## Не-критерии

- Не обязательно дописывать актуальность всех устаревших docs/ в одном ТЗ.
- Не обязательно добавлять ADR в `docs/decisions/` (это обычная уборка, не архитектурное решение — хотя если по ходу дела появится значимое решение, оформим).
