---

## 1. Видение одной фразой

**Библиотека — это личный архив документов пользователя, с которым Simply может говорить во всех режимах работы.**

Пользователь загружает документ один раз — Simply помнит его навсегда и использует когда релевантно. Ментальная модель: «полка с подписанными папками на столе», не «инженерная база знаний».

---

## 2. Для кого и почему сейчас

**Аудитория:** российские бизнес-пользователи 40-60+, выросшие на Windows и папочной организации файлов. Их мышление о порядке: «папка в папке», «закладки по категориям», «архив на столе».

**Проблема сегодня:** документы живут только в контексте одного чата. Загрузил учебник 300 страниц в чат → проговорил → закрыл чат → повторно открыть нельзя без повторной загрузки и индексации. Не масштабируется на реальную работу.

**Решение:** персистентный архив с автоматической и ручной организацией, встроенный в ткань всех режимов Simply.

**Почему сейчас (2026-04-21):** фундамент готов. Compaction в production (v3.95.0) — большие документы не переполнят контекст. MIND усилен (v3.96-97) — автопамять из разговоров работает надёжно. Vision routing закрыт (v3.98). Серия Simply_xAI закрыта v3.92.1. Нет технических блокеров.

## 3. Принятые решения (рабочий концепт)

### 3.1 Размещение в интерфейсе

**Главная:** Библиотека — отдельный пункт первого уровня, парная карточка с «Мой контекст» в левой колонке рядом с полем ввода. Две карточки образуют логическую группу «что Simply о вас знает»:
- **Мой контекст (MIND)** — автоматическая память из разговоров
- **Библиотека** — архив документов, загруженных явно

**Название:** «Библиотека» (не «База знаний»). «База знаний» — инженерный термин. «Библиотека» — тёплое, понятное, близкое к ментальной модели 40-60+.

### 3.2 Организация контента — три уровня

**Первый уровень (ручной, основной): Коллекции**
- Папки с именами, которые пользователь создаёт сам
- Вложенность до 3 уровней (Коллекция → Подколлекция → Подподколлекция)
- Один документ может лежать в нескольких коллекциях одновременно (ссылки, не копии)
- При первом заходе — пустое состояние с приглашением создать первую коллекцию, но не блокирует работу
- Это **привычная папочная модель Windows**, ключевая для нашей аудитории

**Второй уровень (автоматический): Типы документов**
- При индексации Grok 4.1 Fast определяет тип по содержимому + имени файла
- Типы: Договор, Отчёт, Счёт, Презентация, Статья, Книга, Протокол, Переписка, Чертёж/схема, Фото, Другое
- Показываются как пилюли-фильтры: `Все 23 · Договоры 5 · Отчёты 8 · Книги 2 · Статьи 7`
- Работают поверх коллекций (фильтр внутри коллекции) или поверх всей Библиотеки

**Третий уровень (автоматический): Теги по содержанию**
- При индексации генерируются 3-5 тегов на основе СОДЕРЖАНИЯ документа (не метаданных файла)
- Примеры: «Ромашка», «поставка», «2026», «логистика»
- Показываются на карточке документа и как кликабельные фильтры
- Один документ имеет несколько тегов — соответствует реальной природе документов

**Семантический поиск:** всегда доступен сверху страницы, работает по содержанию всех документов. Это инструмент, не основа навигации.

### 3.3 Механика индексации

**Принцип:** индексация документа происходит **один раз** при загрузке. Дальше документ мгновенно доступен во всех режимах. Это ключевая ценность — пользователь не ждёт повторной обработки учебника 300 страниц.

**Статусы документа на карточке:**
- 🟡 `обрабатывается 2:30` — идёт индексация, документ не участвует в retrieval, но виден в списке
- 🟢 `готов` — проиндексирован, доступен во всех режимах
- 🔴 `ошибка` — с объяснением причины и действием (повторить / удалить)

**UX во время индексации:**
Пользователь не ждёт у прогресс-бара. Загрузил документ → получил подтверждение «идёт обработка, пришлём уведомление» → ушёл заниматься другими делами → через несколько минут всплывающее уведомление «Учебник ДВС готов к работе».

**Обработка по форматам:**

| Формат | Обработка | Результат |
|---|---|---|
| PDF текстовый | Text extraction → chunking → embeddings | Полноценный retrieval |
| PDF скан/фото документа | OCR через vision (Grok 4.1 Fast или Haiku) → embeddings | Полноценный retrieval, медленнее |
| DOCX | Text extraction → chunking → embeddings | Полноценный retrieval |
| XLSX | Структурное извлечение + текст ячеек | Retrieval + понимание табличных данных |
| TXT / MD | Chunking → embeddings | Полноценный retrieval |
| Изображение (фото, схема, чертёж) | Vision описание через Grok 4.1 Fast → embedding описания | Retrieval по описанию, клик открывает картинку |
| Презентация PPTX | Text + vision по слайдам | Полноценный retrieval |

**Принцип для UX:** пользователь не думает о форматах. Бросил любой файл — Simply разобрался сам. Если формат не поддерживается — мягкая ошибка «этот формат пока не поддерживается, попробуйте PDF или Word».

### 3.4 Retrieval в трёх chat-режимах

| Режим | Использование Библиотеки | Как выбираются источники |
|---|---|---|
| **Simply Chat (KITT)** | Ambient retrieval по всей Библиотеке автоматически | Фоновый semantic search при каждом сообщении, top 3-5 чанков в контекст |
| **Экспертиза** | По выбору пользователя: ничего / коллекция(и) / отдельные документы | Модалка выбора при старте сессии |
| **Создание** | По выбору пользователя (та же модалка) | Та же модалка выбора |
| **Клик на документ в Библиотеке** | Только этот документ | Автоматически (один выбранный, упрощённая Экспертиза с одним источником) |
| **Projects** | Не используется в MVP | — (изолированное пространство, своя логика) |

**Ключевое различие KITT vs Экспертиза:**
- **KITT** = поверхностное знание обо всём («дворецкий знает где что лежит»)
- **Экспертиза** = глубокая работа с выбранным корпусом («открыть учебник и разобрать тему»)

**Смешанный режим Экспертизы:** возможен выбор «Интернет + документы из Библиотеки» — агент собирает ответ из обоих источников. Пример: «объясни детонацию по моему учебнику и добавь что нового за последние 2 года».

**Лимит выбора в Экспертизе/Создании MVP:** 5 отдельных документов ИЛИ 1 коллекция целиком (независимо от её размера — retrieval всё равно работает top-K по выбранному корпусу).

### 3.5 Источник в ответе модели

Когда модель использовала Библиотеку для ответа — в конце сообщения появляется свёрнутая плашка (**вариант C**):

```
╭─ 📄 Из Библиотеки · 2 источника ↓ ─╮
╰──────────────────────────────────────╯
```

По клику разворачивается с деталями: имя документа, страницы/секции, ссылка «открыть документ» (открывает preview с подсветкой цитируемого фрагмента).

**Обоснование варианта C:** для аудитории 40-60+ важна визуальная чистота (минимум шума в ответе), но возможность увидеть источник по желанию критична для доверия. Свёрнутая плашка — компромисс.

### 3.6 Два входа для загрузки документа

**Основной вход:** страница Библиотеки → большая drag-and-drop зона / кнопка «+ Загрузить». Для осознанного пополнения архива.

**Дополнительный вход:** у вложения в чате появляется маленькая кнопка «Сохранить в Библиотеку». Для ситуаций «этот документ оказался важным, хочу оставить навсегда».

**Ментальная модель:** вложения в чате = временные (для этого разговора). Библиотека = постоянные (для всех будущих разговоров). Граница чёткая, пользователь решает сам.

## 4. Пользовательские сценарии

### Сценарий 1 — Первое знакомство
Иван заходит в Simply, видит на главной две парные карточки слева от поля ввода: «Мой контекст» и «Библиотека». Клик на «Библиотека» → пустая страница с объяснением простым языком: *«Загрузите сюда свои документы — договоры, отчёты, учебники, статьи. Simply запомнит их содержание и будет использовать когда вы о чём-то спрашиваете. Как личный помощник со всем вашим архивом под рукой»*. Большая зона drag-and-drop посередине.

### Сценарий 2 — Загрузка документа
Иван перетаскивает договор PDF. Появляется карточка с прогрессом: «Читаю документ… Понимаю содержание… Готово». Через 10-15 секунд карточка показывает:
- Название файла
- Автоопределённое описание одной фразой: «Договор поставки с ООО Ромашка от 15 марта 2026»
- 3-5 автотегов: `Ромашка` `поставка` `2026`
- Автотип: `Договор`
- Статус: 🟢 готов
- Текст: *«Теперь Simply учитывает этот документ когда отвечает вам»*

### Сценарий 3 — Основной use case через разговор
Иван в Simply Chat: *«какие штрафы в договоре с Ромашкой?»*
Retrieval срабатывает в фоне. Ответ:
> В договоре с Ромашкой штрафы указаны в разделе 5:
> • За просрочку поставки — 0,5% от суммы за каждый день
> • За некачественный товар — возврат 100% стоимости
>
> ╭─ 📄 Из Библиотеки · 1 источник ↓ ─╮
> ╰─────────────────────────────────────╯

Клик по плашке → открывается: `договор_ромашка_2026.pdf · стр. 7-8` + кнопка «открыть документ».

### Сценарий 4 — Глубокая работа с учебником в Экспертизе
Иван хочет разобраться с теорией детонации по своему учебнику. Открывает Экспертизу, в модалке «Источники» выбирает коллекцию «Книги по ДВС» → там лежит учебник, проиндексированный месяц назад. Нажимает «Начать экспертизу». В шапке видно: `Экспертиза · Источники: 📚 Книги по ДВС · 🌐 Интернет`. Агент работает поверх содержимого учебника без повторной обработки.

### Сценарий 5 — Прямой поиск по Библиотеке
Иван на странице Библиотеки вводит в поиск «штрафы». Результаты — не просто файлы со словом «штрафы» в названии, а документы с подсвеченными релевантными фрагментами (семантический поиск). Клик по результату → открывается документ на нужной странице.

### Сценарий 6 — Контроль памяти
На карточке документа есть действие «Что Simply знает об этом документе» → показывает извлечённые факты/фрагменты. Пользователь видит чем именно оперирует AI. Удаление документа → мгновенно выпадает из retrieval, перестаёт использоваться.

### Сценарий 7 — Опытный Windows-пользователь наводит порядок
Иван накопил 50 документов. Создаёт коллекцию «Клиент Ромашка» → перетаскивает в неё 7 связанных документов. Внутри создаёт подколлекции «Договоры 2026» и «Переписка 2026». Получает привычную структуру `Клиент Ромашка › Договоры 2026 › договор_поставка_15_03.pdf`. Хлебные крошки в шапке страницы.

### Сценарий 8 — Ленивый пользователь
Иван ничего не создаёт, просто сваливает документы в Библиотеку. Автотипы и автотеги работают сами → пользователь находит нужное через фильтры и поиск. Оба способа работают, пользователь выбирает свой.

## 5. Интерфейс — структура

**Wireframes согласованы 2026-04-21 в рабочей сессии:**
- Главная с парой карточек «Мой контекст» + «Библиотека» слева от поля ввода
- Страница Библиотеки: шапка → поиск → коллекции → фильтры по типу → популярные теги → список документов со статусами

**Визуальный стиль:** адаптируется под дизайн-систему Simply (кремовый фон `#FAF7F0`, сериф для заголовков) при реализации. Wireframes показывают логику и структуру, не финальный визуал.

**Ключевые элементы страницы Библиотеки (сверху вниз):**
1. Заголовок «Библиотека» + счётчик `23 документа · 3 коллекции` + кнопка `+ Загрузить`
2. Поиск по содержанию (полная ширина)
3. Секция «Мои коллекции» с карточками коллекций (показано: имя, счётчик документов, счётчик подколлекций) + кнопка «+ новая»
4. Секция «По типу» — пилюли-фильтры
5. Секция «Популярные теги» — фиолетовые теги
6. Секция «Недавние» — карточки документов (формат-бейдж, название, автоописание, теги, дата, статус)

**Split-view при клике на документ из Библиотеки:**
- Слева: preview документа (PDF viewer / DOCX rendered)
- Справа: мини-чат с быстрыми кнопками («Краткое содержание», «Ключевые сроки», «Мои обязательства», «Риски для меня»)
- Контекст мини-чата = только этот документ
- Не засоряет Simply Chat

## 6. Границы MVP

### 6.1 Что ВХОДИТ в MVP

- Главная с парой карточек «Мой контекст» + «Библиотека»
- Страница Библиотеки с коллекциями (до 3 уровней вложенности), автотипами, автотегами, поиском
- Загрузка через drag-and-drop и через кнопку
- Индексация 7 форматов: PDF (текст + скан), DOCX, XLSX, TXT, MD, изображения, PPTX
- Статусы документа (обрабатывается / готов / ошибка) + уведомление о готовности
- Ambient retrieval в Simply Chat
- Модалка выбора источников в Экспертизе и Создании (лимит: 5 документов ИЛИ 1 коллекция)
- Клик на документ из Библиотеки → упрощённая Экспертиза с одним источником (split-view)
- Свёрнутая плашка «Из Библиотеки» в ответе (вариант C)
- Кнопка «Сохранить в Библиотеку» у вложения в чате
- Просмотр «Что Simply знает об этом документе» на карточке

### 6.2 Что НЕ входит в MVP (отложено в v2)

- Коллекции в Projects (Projects остаются изолированным пространством в MVP)
- Умное предложение коллекций («у вас уже 5 документов про Ромашку, собрать в коллекцию?»)
- Обработка аудио/видео с транскрипцией
- OCR на русском для сложных сканов (проверить качество стандартного pipeline)
- Совместный доступ к коллекциям между пользователями
- Версионирование документов (загрузил v2 договора — что делать с v1?)
- Экспорт коллекции как архива

### 6.3 Лимиты MVP

| Параметр | Значение | Обоснование |
|---|---|---|
| Размер одного файла | до 50 МБ | Покрывает 99% реальных документов |
| Количество документов на пользователя | Soft-warning при 100, без жёсткого потолка | Подсказка «можно организовать через коллекции» |
| Вложенность коллекций | До 3 уровней | Статистически покрывает все сценарии |
| Выбор источников в Экспертизе/Создании | 5 документов ИЛИ 1 коллекция | Баланс между гибкостью и качеством retrieval |
| Количество чанков в контексте (retrieval) | 3-5 для KITT, 10-15 для Экспертизы с выбранным корпусом | Эмпирические оценки, уточнить в архитектурном документе |

## 7. Открытые вопросы для архитектурной фазы

Эти вопросы требуют изучения xAI Collections API 2026 и best practices RAG до ответа. Не блокируют продуктовый концепт, но должны быть закрыты в `SIMPLY_LIBRARY_ARCHITECTURE.md`:

1. **xAI Collections API из коробки vs кастомный pgvector + Voyage** — что правильнее? xAI Collections даёт file_search и knowledge_search нативно, но привязывает retrieval к конкретному провайдеру. pgvector + Voyage (как в MIND) — унифицируемо с MIND, но больше работы. Возможен гибрид.
2. **Unified `knowledge_search`** — единый tool для MIND + Library, или два разных? Семантика разная: MIND — личные факты, Library — содержимое документов. Модель должна понимать откуда берёт.
3. **Chunking strategy** — размер чанка, overlap, структурно-осведомлённая нарезка (заголовки, списки) или механическая? Для книг и длинных PDF — критично.
4. **Retrieval threshold** — при каком score включать Библиотеку в контекст KITT? Слишком низкий → шум в каждом ответе. Слишком высокий → модель «не находит» релевантное.
5. **Обработка сканов** — Grok 4.1 Fast vision vs Haiku vs специализированный OCR (Qwen 3.6 Plus через Dashscope как в MIND)? Качество на русских документах.
6. **Стоимость индексации на документ** — особенно сканов и больших PDF. Влияет на экономику платформы.
7. **Хранение файлов** — Vercel Blob как сейчас, или отдельное решение под большие архивы? Лимиты Vercel Hobby.
8. **Split-view** — реализация PDF preview с подсветкой цитируемого фрагмента. Какой PDF viewer библиотека, как синхронизировать скролл с цитатой.

## 8. Связь с другими компонентами Simply

| Компонент | Отношение к Библиотеке |
|---|---|
| **MIND (Мой контекст)** | Парная сущность. MIND — автоматическая память из разговоров, Library — явный архив документов. Разные ментальные модели, разные точки входа. Retrieval может быть унифицирован под капотом (`knowledge_search` ищет в обоих) или разделён. |
| **Simply Chat (KITT)** | Ambient потребитель Библиотеки. Каждое сообщение → фоновый retrieval → чанки в контекст. |
| **Экспертиза** | Активный потребитель. Пользователь явно выбирает источники при старте. Главный режим глубокой работы с документами. |
| **Создание** | Активный потребитель. Выбор источников при старте для материалов на основе конкретных документов. |
| **Projects** | В MVP не взаимодействует. В v2 — возможный переключатель «использовать общую Библиотеку» в настройках проекта. |
| **Compaction** | Фундамент. Без Compaction большие документы переполнили бы контекст мгновенно. COMPACTION-UNIFY v3.95.0 решает это. |
| **Attachment flow в чате** | Complementary. Вложения в чате — временные. Кнопка «Сохранить в Библиотеку» — мост между двумя мирами. |
| **Брифинг / Meeting** | Потенциал на v2 — автоматическое добавление в Библиотеку расшифровок встреч как тип «Протокол». |

## Приложение — Словарь терминов

| Термин | Что значит |
|---|---|
| **Библиотека** | Персистентный архив документов пользователя в Simply |
| **Коллекция** | Папка, созданная пользователем, для группировки документов |
| **Подколлекция** | Вложенная коллекция (уровень 2 или 3) |
| **Автотип** | Тип документа, определённый AI при индексации (Договор, Отчёт, Книга и т.д.) |
| **Автотег** | Ключевое слово, сгенерированное AI из содержания документа |
| **Ambient retrieval** | Фоновый поиск по Библиотеке без явной команды пользователя (используется KITT) |
| **Выбранные источники** | Документы и коллекции, явно отмеченные пользователем как рабочий корпус для сессии Экспертизы/Создания |
| **Индексация** | Процесс превращения документа в поисковые эмбеддинги (один раз при загрузке) |
| **Чанк** | Фрагмент документа, по которому работает семантический поиск |
| **Split-view** | Двухпанельный режим при клике на документ из Библиотеки: preview слева + чат справа |
| **MIND** | Автоматическая долговременная память Simply (из разговоров), парная сущность к Библиотеке |
