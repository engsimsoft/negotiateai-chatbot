## Отличия v1.1 от v1.0

- **Upload-путь пересобран (A5.13):** стандартный `POST /v1/files` + attach не работает для Office-форматов (MIME-sniffing по байтам → `octet-stream` → DOCUMENT_STATUS_FAILED). Решение — прямой `POST management-api.x.ai/v1/collections/{id}/documents` с `content_type` как полем формы. См. ADR 056.
- **autoSummary (A6.1c):** рядом с `autoDescription` (≤200 знаков, при upload до indexing) добавлен развёрнутый `autoSummary` (≤2500 знаков, после indexing через `librarySearch`+`generateObject`). Охватывает весь документ любой длины. Миграция 0063.
- **chatMode `library-document`:** изолированный мини-чат split-view. Tool set = только `librarySearch` с `lockedFileId`. MIND off. Отдельный taskId `library-document-chat`.
- **SourcePickerModal (A6.2):** выбор до 3 коллекций / 5 документов для Экспертизы и Создания. `librarySearch` принимает `scopedSourceIds` и жёстко замыкается на них (модель не может выйти за scope). Библиотечный context-блок переключается на «Выбранные источники».
- **LibrarySourcesBadge:** плашка «Из Библиотеки · N источников» в сообщениях ассистента, собирается из `chunks.fileId/documentId/pageNumber` всех вызовов `librarySearch`, дедуп по (fileId+page), клик по строке ведёт на `/library/{docId}`.
- **Race condition UI status:** summary-generator сам обновляет `status='ready'` при обнаружении xAI `PROCESSED` — защита от зависшего «обработка» в UI.
- **Polling autoSummary в split-view:** SWR-poll `/api/library/documents/{id}` каждые 5 сек пока `autoSummary === null` — устраняет требование F5 после upload.
- **Scope-cut A6.3:** кнопка «Сохранить в Библиотеку» у вложений чата отменена продуктовым решением — дублирует существующий путь `Библиотека → Загрузить`.
- **Бонус-фикс:** xAI prompt-cache в Экспертизе/Создании. MIND-блок для не-Anthropic-протокола переехал из trailing system message в trailing text-part последнего user-сообщения — стабильный префикс даёт кэшировать всю историю, а не только системный блок.

## 1. Положение в системе

Библиотека встаёт третьим хранилищем знаний рядом с двумя уже существующими. Каждое хранилище отвечает за свой слой персонализации — они **не конкурируют**, а дополняют друг друга.

| Хранилище | Что хранит | Как работает в чате | Когда попадает в контекст | Источник |
|---|---|---|---|---|
| **Профиль пользователя** (`User`) | Имя, занятость, bio, стиль общения | Статический блок system prompt | Каждое сообщение | Настройки |
| **MIND** (`memory_entry` + `user_profile_summary`) | Автофакты из разговоров, нарративный профиль | Prompt-injection (retrieval в отдельный блок контекста) | Каждое сообщение, автоматически | Разговоры пользователя |
| **Library** (**новое**, xAI Collections) | Явно загруженные документы пользователя | **Tool** `library_search`, вызываемый моделью по решению | Только когда модель сама решит что нужно | Явные загрузки пользователя |

**Ключевое различие MIND ↔ Library:**
- MIND — «что я знаю про тебя» — всегда в голове у модели
- Library — «твой архив документов» — модель открывает только когда это помогает ответу

Это прямая реализация акцента владельца: память — для личного контекста, документы — для чётких ответов в серьёзных режимах (Экспертиза, Проекты).

**Схема взаимодействия:**
```
Пользователь пишет сообщение
         │
         ▼
┌─────────────────────────────────────────┐
│ 1. system prompt (статический):         │
│    └─ Профиль (User.bio, pronouns, …)   │
│    └─ MIND Narrative (user_profile_     │
│       summary.content, Opus-генератор)  │
│                                         │
│ 2. Динамический memory block:           │
│    └─ MIND retrieve: top-5 facts        │
│       (Voyage cosine search)            │
│                                         │
│ 3. История чата (c учётом Compaction)   │
│                                         │
│ 4. Tools:                               │
│    ├─ web_search, …                     │
│    └─ library_search (НОВЫЙ) ←──────────┼─── xAI Collections API
└─────────────────────────────────────────┘
```

## 2. Главные архитектурные решения

Четыре фундаментальных решения, на которых держится вся реализация. Изменение любого — меняет весь документ.

### Решение 1 — xAI Collections как единственное хранилище RAG

**Не строим pgvector для документов.** pgvector остаётся только для MIND (там он работает, там масштаб маленький — сотни фактов на пользователя).

**Не копируем файлы в Vercel Blob повторно.** xAI хранит файлы сам ($0.10/GiB/day). Наш Blob используется только для вложений в чате (Files API), не для Library.

**Исключение:** для split-view preview (клик на документ в Библиотеке) возможно понадобится локальный кэш файла, чтобы не скачивать с xAI каждый раз. Это оптимизация v2, не MVP.

**Следствие:** вся работа с embeddings, chunking, OCR, semantic/hybrid search — **на стороне xAI**, в нашем коде этого нет. Существенная экономия работы.

### Решение 2 — Два отдельных механизма retrieval в чате

**MIND работает как сейчас — prompt-injection.** Никаких изменений MIND pipeline в рамках этого ТЗ. Факты вставляются автоматически перед каждым сообщением (как описано в [MIND_ARCHITECTURE.md §1](MIND_ARCHITECTURE.md)).

**Library работает как tool — `library_search`.** Модель сама решает, когда вызывать. При разговоре не по документам — не вызывает, экономит $0.0025 за вызов.

Формулировка в `SIMPLY_ATTACHMENT_ARCHITECTURE.md` про «один интерфейс `knowledge_search`» (наследие годичной давности, когда MIND планировался как tool) **устарела**. Обновим этот документ в Фазе финализации ТЗ.

### Решение 3 — Плоские коллекции (без вложенности в MVP)

xAI Collections — плоский список. Не эмулируем «папки в папках» на нашей стороне.

Пользователь создаёт коллекции первого уровня: «Клиент Ромашка», «Книги по ДВС», «Бухгалтерия 2026». Документ может быть в нескольких коллекциях одновременно (реализуется через two-step upload в xAI: файл загружается один раз, привязывается к нескольким collection_id).

Если в v2 появится потребность в иерархии — в кодовой базе уже есть паттерн `project_folder` (ТЗ-07C1), можно переиспользовать. На MVP не влияет.

### Решение 4 — Наша БД хранит пользовательскую организацию, xAI хранит содержимое

Разделение ответственности:

| Сущность | Наша БД | xAI |
|---|---|---|
| Имя коллекции, порядок, даты создания/изменения | ✅ | xAI тоже знает `name`, но **наша БД — source of truth для UI** |
| Список коллекций пользователя (фильтрация по userId) | ✅ | — |
| Содержимое файла, chunks, embeddings, search index | — | ✅ |
| Имя документа, его автотип, автотеги, автоописание | ✅ | xAI хранит только `name`; автотип/теги — наша работа |
| Связь «документ в нескольких коллекциях» | ✅ (M:N таблица) | xAI тоже поддерживает, но через его API это запрос — держим локально |
| Статус индексации (pending/processed/error) | ✅ (зеркалим для UI) | ✅ (source of truth через polling) |
| Physical file (байты) | — | ✅ |

**Почему локальные таблицы, если xAI умеет хранить имена и metadata?** Причины три:
1. **Скорость UI.** Загрузка страницы Библиотеки = один запрос в нашу БД, не десятки запросов в xAI Management API.
2. **Наши поля не кладутся в xAI metadata чисто.** Автотеги — массив строк, xAI fields принимают только скаляры. Храним у себя.
3. **Наша БД — это userId-scoped фильтрация.** xAI Management API не знает о нашем `session.user.id`.

## 3. Схема БД — новые таблицы

Три новые таблицы, три миграции. Именование согласовано с существующим (snake_case для таблиц, camelCase для полей как в Drizzle-схеме проекта).

### 3.1 `library_collection`

Коллекция пользователя (плоский список, без вложенности в MVP).

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID (PK) | Внутренний идентификатор |
| `userId` | UUID (FK → `user.id`) | Владелец, cascade не ставим (как в `project`) |
| `xaiCollectionId` | TEXT | `collection_<uuid>` от xAI, уникален |
| `name` | TEXT | Отображаемое имя («Клиент Ромашка») |
| `emoji` | TEXT | Опционально, UI-декор (паттерн как у `project_folder.emoji`) |
| `sortOrder` | INTEGER | Порядок отображения, пользовательский drag-and-drop |
| `documentCount` | INTEGER | Кэш (обновляется при add/remove) — для списка в UI без JOIN'ов |
| `createdAt`, `updatedAt` | TIMESTAMP | — |

Индексы: `(userId, sortOrder)` для быстрой выборки на странице Библиотеки.

### 3.2 `library_document`

Документ в Библиотеке. Файл существует в xAI, у нас — метадата для UI и фильтрации.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID (PK) | Внутренний идентификатор |
| `userId` | UUID (FK → `user.id`) | Владелец |
| `xaiFileId` | TEXT | `file_<uuid>` от xAI, уникален глобально |
| `filename` | TEXT | Оригинальное имя файла |
| `mimeType` | TEXT | Из upload |
| `size` | INTEGER | В байтах |
| `status` | ENUM (`uploading`, `processing`, `ready`, `error`) | Для UI-индикаторов (🟡/🟢/🔴) |
| `statusError` | TEXT (nullable) | Текст ошибки при `error` |
| `autoType` | TEXT (nullable) | «Договор», «Отчёт», «Книга» — от Grok 4.1 Fast на upload |
| `autoTags` | JSONB (array of strings) | ["Ромашка", "поставка", "2026"] — от Grok 4.1 Fast |
| `autoDescription` | TEXT (nullable) | «Договор поставки с ООО Ромашка от 15 марта 2026» — одна фраза |
| `originalFileUrl` | TEXT (nullable) | Vercel Blob URL на оригинал (для split-view preview; опциональный кэш) |
| `createdAt`, `updatedAt` | TIMESTAMP | — |

Индексы: `(userId, createdAt DESC)` для секции «Недавние», `(userId, autoType)` для пилюль-фильтров.

**Поле `autoType` — enum или свободный текст?** В MVP — **свободный текст**. Grok 4.1 Fast возвращает одно из значений из списка, но мы не форсируем через DB constraint. В v2 можно ввести enum для пилюль с фиксированным набором.

### 3.3 `library_collection_document`

Связь «документ в нескольких коллекциях» (M:N).

| Поле | Тип | Назначение |
|---|---|---|
| `collectionId` | UUID (FK → `library_collection.id`) | PK часть |
| `documentId` | UUID (FK → `library_document.id`) | PK часть |
| `createdAt` | TIMESTAMP | Когда документ добавлен в коллекцию |

Primary Key: `(collectionId, documentId)`. Два индекса (по обоим направлениям).

**«Документ вне всех коллекций» — как?** Документ в `library_document` без записей в `library_collection_document`. В UI показывается в секции «Без коллекции» или «Все документы». Это важно для сценария 8 из продуктового документа (ленивый пользователь сваливает всё без организации).

### 3.4 Миграции

- `0053_library-collection.sql` — `library_collection`
- `0054_library-document.sql` — `library_document` (зависит от 0053 если будет FK, но FK нет)
- `0055_library-collection-document.sql` — M:N таблица

## 4. API endpoints — новые ручки

Паттерн как у существующего `/api/user/memory` и `/api/projects/[id]/files` (по аудиту Блок 5): auth → ownership check → DB query + xAI call → JSON response.

### 4.1 Коллекции

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/library/collections` | Список коллекций пользователя. Возврат: `[{ id, name, emoji, documentCount, createdAt }]` |
| `POST` | `/api/library/collections` | Создать. Body: `{ name, emoji? }`. Делает: POST в xAI → INSERT в нашу БД |
| `PATCH` | `/api/library/collections/[id]` | Переименовать, изменить emoji. Синхронно обновляет xAI и нашу БД |
| `DELETE` | `/api/library/collections/[id]` | Удалить коллекцию. **ВАЖНО:** документы, которые были **только** в этой коллекции, переходят в состояние «без коллекции», не удаляются. Это требование продуктового документа (коллекции — ссылки, не копии). |
| `POST` | `/api/library/collections/reorder` | Изменить `sortOrder` пачкой (drag-and-drop) |

### 4.2 Документы

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/library/documents` | Список документов с фильтрацией. Query: `collectionId?`, `autoType?`, `tag?`, `search?`, `limit`, `offset` |
| `POST` | `/api/library/documents` | Загрузить новый документ. Multipart: `file`, `collectionIds[]?`. Подробнее — §5 |
| `GET` | `/api/library/documents/[id]` | Детали документа (для split-view) |
| `PATCH` | `/api/library/documents/[id]` | Изменить `filename` (переименовать), коллекции (добавить/убрать) |
| `DELETE` | `/api/library/documents/[id]` | Удалить везде. Делает: DELETE в xAI Collections → DELETE в xAI Files → DELETE в нашу БД |
| `GET` | `/api/library/documents/[id]/status` | Polling статуса индексации (для UI-индикатора 🟡→🟢) |

### 4.3 Поиск

| Метод | URL | Назначение |
|---|---|---|
| `POST` | `/api/library/search` | Прямой семантический поиск по Библиотеке (сценарий 5 продуктового документа: строка поиска на странице Библиотеки). Body: `{ query, collectionIds? }`. Внутри — вызов `POST /v1/documents/search` в xAI с `retrieval_mode: hybrid` |

## 5. Upload flow — новый документ в Библиотеку

Два входа (из продуктового документа):
- **Основной:** страница Библиотеки, drag-and-drop / кнопка `+ Загрузить`
- **Дополнительный:** кнопка «Сохранить в Библиотеку» у вложения в чате

Оба ведут на один endpoint `POST /api/library/documents`. Разница только в клиенте (из чата передаётся уже загруженный в Blob файл, со страницы — свежий upload).

### 5.1 Последовательность (server-side)

```
1. Auth check, ownership
2. Validate (size ≤ 100 MB — лимит xAI Collections; MIME в supported list)
3. INSERT library_document (status='uploading')
4. Вернуть клиенту { id, status: 'uploading' } — UI показывает карточку-скелетон
5. (background, через Next.js after() или queue)
   5.1. Upload в xAI Files API → fileId
   5.2. Attach к указанным collection_id (или к дефолтной коллекции «Без категории»)
   5.3. UPDATE library_document SET status='processing', xaiFileId=...
   5.4. Параллельно: вызвать Grok 4.1 Fast для auto-analysis:
        - извлечь первые N символов из файла (через xAI Files content API или локально до upload)
        - prompt: «Определи тип документа, 3-5 тегов, одну фразу описания. JSON»
        - UPDATE library_document SET autoType=..., autoTags=..., autoDescription=...
   5.5. Polling xAI: ждать DOCUMENT_STATUS_PROCESSED
   5.6. UPDATE library_document SET status='ready'
   5.7. (опционально MVP или v2) Push-уведомление пользователю «<filename> готов к работе»
```

**На ошибке любого шага:** `UPDATE library_document SET status='error', statusError=...`. Пользователь видит 🔴 с действием «Повторить / Удалить».

### 5.2 Автотип / автотеги / автоописание — один LLM call

Один вызов Grok 4.1 Fast (taskId `library:auto-analyze`) с structured output (schema через `generateObject` — xAI поддерживает нативно, уже проверено в ТЗ-XAI-2):

```ts
schema: {
  autoType: enum([...)]),
  autoTags: array(string).min(3).max(5),
  autoDescription: string.max(200),
}
```

Стоимость: ~$0.0001 за документ (подсобка + короткий prompt). На 1000 документов — $0.10. Не узкое место.

### 5.3 Интеграция с существующим upload flow

**Существующий `/api/files/upload`** (документы в чате) **не трогаем**. Он продолжает работать со своим Vercel Blob storage для in-chat attachments.

**«Сохранить в Библиотеку» из чата** = отдельный POST на `/api/library/documents` с указанием уже существующего Blob URL (опциональный параметр, если нет — скачивается заново из Blob). Это переиспользование, не дублирование.

## 6. Интеграция в чат — tool `library_search`

### 6.1 Регистрация tool

Новый файл `lib/ai/tools/library-search.ts` по паттерну существующих tools (по аудиту Блок 3). Структура:

```ts
export const librarySearchTool = tool({
  description: `Поиск по Библиотеке пользователя — персональному архиву документов...
                Используй когда пользователь спрашивает про свои документы,
                упоминает название документа, или когда нужны точные данные из
                загруженных файлов (договоры, отчёты, книги, статьи).`,
  inputSchema: z.object({
    query: z.string().describe('Поисковый запрос на естественном языке'),
    collectionIds: z.array(z.string()).optional()
      .describe('Ограничить поиск конкретными коллекциями'),
  }),
  execute: async ({ query, collectionIds }) => {
    // 1. Определить список коллекций (фильтр по userId + опциональный allowlist)
    // 2. Вызов xAI collections_search / file_search
    // 3. Вернуть результаты в формате { chunks: [...], citations: [...] }
  },
});
```

**Description промпта — это работа отдельная.** Точная формулировка — в проекте Prompt Engineering & Agent Behavior (по разделению проектов). Здесь — техническая оболочка и границы.

### 6.2 Подключение по chat modes

Приоритеты Library по режимам (**акцент владельца 2026-04-21: Экспертиза и Проекты — главные потребители**):

| Режим | `library_search` tool | Как выбираются источники |
|---|---|---|
| **expertise** | ✅ **PRIMARY use case** | Модалка выбора при старте (коллекции и/или документы) → передаются в `collectionIds` |
| **create** | ✅ **PRIMARY use case** | То же, модалка источников |
| **project** | ✅ **PRIMARY use case** (пересмотр MVP — см. §7) | Вся Библиотека пользователя доступна по умолчанию (без модалки) |
| **simply (KITT)** | ✅ **SECONDARY** — ambient | Tool подключён, модель сама решает вызывать или нет. Без пред-выбора коллекций |

Реализуется через расширение `getStandardTools()` в `lib/ai/tools/chat-tools.ts` (по аудиту Блок 3): добавить `librarySearchTool` в active tools для всех chat modes. KITT в «дежурном режиме» (модель редко его дёргает), Экспертиза/Создание/Проекты — активно.

### 6.3 Адаптация `getActiveToolNames()`

Логика фильтрации (по аудиту) уже учитывает chatMode. Добавить `library_search` в allowlist для всех четырёх chat modes.

### 6.4 Клик на документ из Библиотеки → split-view

Отдельный путь — не через обычный чат, а через специализированный sub-chat. UI split-view (продуктовый документ §5):
- Левая панель: preview документа (PDF viewer react-pdf или аналог — выбор v2, см. §11)
- Правая панель: мини-чат с быстрыми кнопками

Мини-чат использует тот же `library_search` tool, но с hardcoded `collectionIds: []` и additional filter `fileId = <doc.xaiFileId>` (через `filter` в xAI search API). Контекст ограничен одним документом.

**Создаём ли новую запись в `chat`?** Да — временный chat с особым `chatMode='library-document'` (новое значение). Не засоряет Simply Chat, не попадает в историю проектов.

## 7. Границы MVP

### 7.1 Что ВХОДИТ (финальный список для этого ТЗ)

Из продуктового документа v1.0 + пересмотр Projects:

- **Страница Библиотеки:** заголовок + счётчики + `+ Загрузить` + поиск + коллекции (drag-and-drop порядок) + пилюли автотипов + облако тегов + секция «Недавние»
- **Главная:** карточка «Библиотека» в паре с карточкой «Мой контекст»
- **Коллекции:** плоский список, CRUD, один документ в нескольких коллекциях
- **Автоиндексация 7 форматов** (xAI поддерживает все): PDF (текст+скан), DOCX, XLSX, TXT, MD, изображения, PPTX
- **Автотип / автотеги / автоописание** от Grok 4.1 Fast при upload
- **Статусы документа** с UI-индикаторами, polling
- **Tool `library_search`** во всех 4 chat modes по дифференциации §6.2
- **Модалка выбора источников** в Экспертизе и Создании
- **Split-view при клике** на документ (preview + мини-чат, контекст = один документ)
- **Плашка «Из Библиотеки · N источников»** в ответе модели (свёрнутая, вариант C)
- **Кнопка «Сохранить в Библиотеку»** у вложения в чате
- **Прямой поиск** на странице Библиотеки (hybrid retrieval через `POST /v1/documents/search`)

### 7.2 Что НЕ входит (v2 или позже)

- **Вложенность коллекций** (3 уровня из продуктового документа отложены — плоско в MVP)
- **Умное предложение коллекций** («у вас 5 документов про Ромашку, собрать?»)
- **Обработка аудио/видео** с транскрипцией
- **Совместный доступ к коллекциям** между пользователями
- **Версионирование документов** (загрузил v2 — что делать с v1)
- **Экспорт коллекции** как архива
- **Локальный кэш оригинала** в Vercel Blob для split-view (пока скачиваем из xAI каждый раз)
- **Push-уведомление о готовности документа** (можно v1.1 через существующий notifications flow)

### 7.3 Лимиты MVP

Откорректированы по данным из xAI docs:

| Параметр | Значение | Обоснование |
|---|---|---|
| Размер одного файла | до **100 MB** (было 50 MB в продуктовом документе v1.0) | xAI Collections позволяет до 100 MB, нет причин искусственно ограничивать |
| Количество документов на пользователя | Soft-warning при 100, без жёсткого потолка | Лимит xAI — 100K globally (по всем пользователям), на нашей стороне не упираемся |
| Вложенность коллекций | 1 уровень (плоско) | Решение §2.3 |
| Выбор источников в Экспертизе/Создании | до 5 документов ИЛИ до 3 коллекций одновременно | xAI принимает множественный `collection_ids` — смягчили продуктовый лимит «5 или 1 коллекция» |
| Top-K результатов retrieval | 10 по умолчанию (параметр `max_num_results`) | Эмпирическое best practice xAI |

## 8. Пересмотр продуктового документа — Projects в MVP

**Что было в продуктовом документе v1.0 §3.4:**
> «Projects — Не используется в MVP — (изолированное пространство, своя логика)»

**Что говорит владелец 2026-04-21:**
> «Библиотека для серьёзных работ, допустим в режиме Экспертиза или в Проектах. Где нужна чёткая информация и ответы именно из данных из Библиотеки.»

**Разбор противоречия.** Исходное решение «Projects не используются» было принято исходя из архитектурной изоляции Projects (у них своя файловая система `project_file`, свои агенты, своё рабочее пространство). Это правильно для **изоляции данных внутри проекта**.

Но **Библиотека — это user-scoped архив**, не project-scoped. Аудит подтвердил: `memory_entry` имеет `sourceProjectId`, но MIND retrieval работает для всех 4 chat modes (project включая). По аналогии, `library_document.userId` делает Библиотеку доступной для любого chat этого пользователя.

**Предлагаемое решение для MVP:** Library tool доступен в project chats **по умолчанию**. Пользователь явно видит «Библиотека» как доступный источник в UI проекта.

**Опциональный toggle «Использовать мою Библиотеку в этом проекте»** — в настройках проекта, дефолт включено. Пользователь может выключить для конкретного проекта (например, для closed-data задачи). Это v1.1, не блокирует MVP.

**Следствие:** область применимости Библиотеки — **все 4 chat modes**. Это упрощает архитектуру (одна логика подключения tool) и отвечает прямому акценту владельца.

**Нужно подтверждение владельца:** если Вы НЕ согласны с включением Projects в MVP — откатим, scope сузится до simply/expertise/create, project откладывается до v1.1.

## 11. Открытые вопросы (для Фазы ANALYSIS Claude Code)

Эти вопросы требуют точечного изучения кодовой базы или тестов. Не блокируют архитектуру, но должны быть закрыты в SPEC.

### Q1 — PDF preview библиотека

Для split-view нужен React-компонент PDF viewer с подсветкой страницы. Кандидаты: `react-pdf`, `pdf.js` напрямую, `mozilla-pdf.js-dist`. Выбор + проверка работы на Vercel Edge — задача Claude Code в ANALYSIS.

### Q2 — Стратегия polling статуса документа

Варианты:
- Клиент опрашивает `GET /api/library/documents/[id]/status` каждые 3-5 секунд
- Server-Sent Events (SSE) push на клиент
- Polling с exponential backoff

Полyaть при MVP — простейший client polling каждые 3 секунды. SSE — v2.

### Q3 — Default-коллекция «Без категории»

Когда пользователь грузит документ без явного выбора коллекции — куда он падает?

Вариант A: в `library_document` без записей в `library_collection_document`. В UI — секция «Все документы».
Вариант B: создаётся специальная коллекция «Без категории» при первой загрузке.

Предпочтение — **A** (проще, нет магических коллекций). Вариант B на ANALYSIS.

### Q4 — Stream обработки при upload

Upload идёт через `after()` Next.js (существующий паттерн в проекте) или через background queue? Проверить что `after()` справится с polling xAI (может занять минуты для больших файлов).

Скорее всего `after()` ок для MVP, для v2 — рассмотреть queue (если Vercel Hobby permits).

### Q5 — Чистка старых документов

При удалении пользователя (если такая функциональность есть / появится) — что с его коллекциями в xAI? Нужен hook на `user.delete`, который пройдёт по всем `library_collection` пользователя и удалит в xAI. Это отдельная тонкость, не MVP-блокер.
