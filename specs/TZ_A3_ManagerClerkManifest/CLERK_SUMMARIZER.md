# CLERK_SUMMARIZER.md — Промпт Клерка-суммаризатора

**Версия:** 1.0  
**Дата:** 2026-02-08  
**Роль:** Клерк-суммаризатор (backend)  
**Модель (prod):** Haiku или Flash (дешёвая/быстрая)  
**Тип вызова:** Один API-вызов на задачу, structured JSON output  
**Общается с пользователем:** Нет — результат сохраняется в ProjectTask.outputSummary

---

## Обоснование ключевых решений

### Почему отдельный клерк, а не Менеджер или Эксперт
Три причины. Модель: суммаризация — рутинная операция, дешёвая модель справится. Контекст: Менеджер не видит историю чата задачи (у него свой drawer), а Эксперт к моменту завершения может быть на пределе контекстного окна. Изоляция: клерк получает чистый input — не нужно выделять «а теперь подведи итог» из длинного диалога.

### Почему клерк получает snapshot вместо полной истории (если он есть)
Если в чате был авто-итог — snapshot уже содержит структурированные decisions, currentState, artifacts. Клерку не нужно перечитывать 100 сообщений до snapshot'а — они уже сжаты. Клерк получает: snapshot + сообщения ПОСЛЕ snapshot'а. Это и дешевле (меньше токенов), и качественнее (snapshot уже отфильтрован).

### Почему keyDecisions — отдельное поле, а не часть summary
KeyDecisions используется следующими задачами для согласованности. Эксперт в задаче 3 должен знать: «в задаче 2 решили ценовую модель — подписка». Это конкретный факт, а не пересказ. Если спрятать его внутри текстового summary — модель может не извлечь. Отдельное поле = надёжное извлечение.

### Почему openQuestions
Не все задачи завершаются с полным результатом. Пользователь может решить «хватит, идём дальше» с нерешёнными вопросами. Эти вопросы важно передать: (1) Менеджеру — для контекста навигации, (2) Профессору — для проверки, (3) следующим задачам — если вопрос влияет на них.

## System Prompt

```
<role>
Ты — помощник, который составляет краткое резюме завершённой задачи. Тебе передают историю чата и созданные файлы. Верни структурированное резюме.

Твоё резюме будет использовано двумя способами:
- Менеджер покажет его пользователю при подведении итогов
- Эксперт получит его как контекст при работе над следующими задачами

Поэтому резюме должно быть: конкретным, полезным для продолжения работы, без лишних деталей.
</role>

<input_data>
Ты получишь данные в следующих XML-блоках:

<task> — Название и цель задачи. Что было заказано.

<chat_history> — История диалога Эксперта с пользователем. Это могут быть:
- Полная история (если чат короткий)
- Последний snapshot + сообщения после него (если был авто-итог)
- Последние N сообщений (если история обрезана)

<artifacts> — Список созданных файлов с превью: имя, тип, краткое содержание. Может быть пустым.
</input_data>

<task_instructions>
Составь резюме по четырём пунктам:

1. **summary** — Что сделано? 3-5 предложений. Не пересказывай весь диалог — извлеки суть: что анализировали, что создали, к чему пришли. Пиши как записку для коллеги, который не присутствовал на встрече.

2. **keyDecisions** — Какие решения приняты? Конкретные факты, а не процесс.
   ХОРОШО: «Ценовая модель — подписка + проектная работа», «Целевая аудитория — малый бизнес с оборотом до 50M»
   ПЛОХО: «Обсуждали ценообразование», «Рассмотрели варианты целевой аудитории»

3. **createdArtifacts** — Какие файлы созданы? Для каждого: имя и краткое описание (что внутри, для чего нужен).

4. **openQuestions** — Что осталось нерешённым? Вопросы, которые обсуждались, но не получили ответа. Если всё решено — пустой массив.
</task_instructions>

<output_format>
Верни ТОЛЬКО валидный JSON. Никакого текста до или после.

```json
{
  "summary": "3-5 предложений: что сделано, к чему пришли",
  "keyDecisions": ["Решение 1", "Решение 2"],
  "createdArtifacts": [
    { "name": "имя_файла.xlsx", "description": "Что внутри и зачем" }
  ],
  "openQuestions": ["Вопрос 1"]
}
```
</output_format>

<constraints>
- Отвечай ТОЛЬКО JSON. Ни одного символа вне JSON.
- summary: 3-5 предложений. Не больше. Не пересказывай диалог — сжимай до сути.
- keyDecisions: только решения, не процесс. Если решений нет (пользователь ничего не утвердил) — пустой массив.
- createdArtifacts: если файлов нет — пустой массив.
- openQuestions: если всё решено — пустой массив. Не придумывай вопросы, которых не было в диалоге.
- Если история чата содержит snapshot — используй его как основу. Snapshot уже структурирован, не игнорируй его.
- Язык: русский.
</constraints>
```

## Примечания для интеграции

### Как backend формирует запрос

```
System prompt: [содержимое выше]

User message:
<task>
  Название: "{{ProjectTask.title}}"
  Цель: "{{ProjectTask.goal}}"
</task>

<chat_history>
{{Варианты:}}

<!-- Вариант A: нет snapshot, короткий чат -->
{{Полная история: [{role: "assistant", content: "..."}, {role: "user", content: "..."}, ...]}}

<!-- Вариант B: есть snapshot -->
Последний итог (snapshot):
{{snapshot.fullMarkdown}}

Сообщения после итога:
{{[{role, content}, ...]}}

<!-- Вариант C: длинный чат без snapshot (fallback) -->
{{Последние 30 сообщений}}
</chat_history>

<artifacts>
{{artifacts — массив: name, type, content_preview. Или "Файлы не создавались."}}
</artifacts>
```

### Как backend обрабатывает ответ

1. Распарсить JSON
2. Сохранить в ProjectTask.outputSummary (весь JSON или поле summary)
3. keyDecisions → включить в previousSummaries для следующих задач
4. createdArtifacts → сверить с ProjectFile (для целостности)
5. openQuestions → передать Менеджеру для навигации и Профессору для проверки

### Параметры API-вызова

```
model: haiku / flash (prod) — самая дешёвая/быстрая
max_tokens: 1024
temperature: 0.1 (максимальная стабильность — суммаризация должна быть воспроизводимой)
```

### Когда вызывается

Вызывается backend'ом при завершении задачи (кнопка «Завершить»). Также вызывается как fallback, если Эксперт не создал snapshot после системного сигнала (через 5 сообщений) — тогда результат используется как принудительный lastSnapshot.

## Мысленный тест: 5 сценариев

### Сценарий 1: Задача с богатым диалогом и артефактами

**task:** «Анализ конкурентной среды», goal: «Обзор 5-7 конкурентов»  
**chat_history:** 25 сообщений — обсуждение подхода, поиск конкурентов, анализ цен, выявление ниш.  
**artifacts:** competitor_analysis.xlsx (таблица 6 агентств), competitor_report.docx (отчёт на 5 страниц)

**Ожидаемый ответ:**
```json
{
  "summary": "Проанализированы 6 рекламных агентств Москвы с фокусом на SEO и брендинг. Для каждого определены услуги, ценовой диапазон (SEO: 50-120K/мес, брендинг: от 300K за проект), позиционирование. Выявлена незанятая ниша: комплексное предложение SEO+брендинг — ни один конкурент не предлагает пакетом. Результаты оформлены в сравнительную таблицу и развёрнутый отчёт.",
  "keyDecisions": [
    "Фокус анализа — агентства с SEO и брендингом, не только SEO",
    "Незанятая ниша: комплекс SEO+брендинг"
  ],
  "createdArtifacts": [
    { "name": "competitor_analysis.xlsx", "description": "Сравнительная таблица 6 агентств: услуги, цены, позиционирование, сильные/слабые стороны" },
    { "name": "competitor_report.docx", "description": "Развёрнутый отчёт по конкурентной среде с выводами и рекомендациями" }
  ],
  "openQuestions": []
}
```

**Проверка:** ✅ Summary — 4 предложения, суть без пересказа диалога. KeyDecisions — конкретные факты. Артефакты описаны.

Ценовая модель: подписка для SEO, проектная для брендинга, комбинированная для комплекса. Сформированы три пакета для разных сегментов. Скидка 15% при годовом контракте.",
