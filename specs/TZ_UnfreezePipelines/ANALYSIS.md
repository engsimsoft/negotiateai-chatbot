## Природа проблемы

### Что такое «uncommitted блокер»

В рабочем дереве проекта 12 файлов имеют изменения, которые **не закоммичены и не stashed**. Эти изменения накопились от двух замороженных ТЗ:

- **TZ_MindArtifacts** (визуализация карточек MIND, Notion-уровень)
- **TZ_SaveFactV2** (metadata для задач/календаря в memory_entry)

Оба ТЗ остановлены потому что Anthropic/Google модели не справляются с instruction following на задаче многократного заполнения структурированных metadata полей. Ожидается тест Grok через `/dev/models` (доступен после ТЗ-2 v3.84.0). Timeline: **неизвестно**.

### Почему uncommitted — это технический долг

1. **Ломает любые рефакторы pipeline-кода.** Любая попытка чистить `briefing-author.ts`, `podcast/script-generator.ts` и др. → merge conflict с uncommitted работой
2. **Ломает next ТЗ (CachePipelineMetrics).** Кэширование MiniMax pipelines требует правки тех же файлов
3. **Скрытое снижение кэш-наблюдаемости.** Каждый день uncommitted → минус один день валидных метрик `ai_usage_log` для billing
4. **Растёт со временем.** Чем дольше висит, тем сложнее восстанавливать контекст. Через месяц — невозможно
5. **Опасен при операциях типа `git stash` / `git pull` / `git checkout`.** Случайный конфликт = ручное разрешение большого блока без понимания

### Почему «дисциплинарная» работа

Это **не feature work**. Не пишется новый код, не реализуется новая логика. Только:

- Чтение `git diff` файлов
- Классификация (3 категории)
- Перемещение через `git stash` / `git commit` / `git checkout`

Дисциплинарная работа имеет **низкую неопределённость** (объём предсказуем) и **высокий риск ошибки только в одном месте** — классификация. Поэтому правило «при сомнении → stash» защищает от потери работы.

## Подход к классификации

### Три категории и их критерии

**(a) Infrastructure prep — COMMIT**

Изменения, которые:
- Имеют **самостоятельную ценность** независимо от исхода frozen ТЗ
- **Нейтральны** для продуктовой логики (не ломают существующие фичи)
- Часто это: новые типы, helpers, миграции БД, queries

**Примеры (предположительно):**
- `lib/ai/memory/types.ts` — TaskMetadata/CalendarMetadata типы. Используются в schema.ts (если уже applied), нужны и Path A (Grok справился) и Path B (ручной mode). Безопасно коммитить
- `lib/db/migrations/0051_memory-metadata.sql` — миграция БД. Уже применена локально. Откат бессмысленен. COMMIT

**(b) Orphaned WIP — ROLLBACK**

Изменения, которые:
- **Заброшены** без следа в git history
- **Не имеют связи** с активными или замороженными ТЗ
- **Не упоминаются** в недавних commits/SPECs
- Могут быть результатом случайного редактирования или давно забытого эксперимента

**Подход:** rollback через `git checkout -- <file>`. Безвозвратно.

**(c) Frozen TZ exploration — STASH**

Изменения, которые:
- **Содержательны** (не случайные опечатки)
- **Имеют связь** с frozen ТЗ
- **Не имеют самостоятельной ценности** без полной реализации соответствующей фичи

**Подход:** named stash для возможности восстановления при разморозке.

```bash
git stash push -m "WIP: TZ_MindArtifacts pipeline exploration" -- <files>
git stash list  # подтверждение
```

### Правило сомнения

**При любом сомнении в категории → STASH.**

Логика: stash восстанавливаемый, commit/rollback — потенциально разрушающий. Stash безопаснее во всех направлениях:
- Слишком много в stash → можно перенести в commit позже
- Слишком много в commit → revert + merge conflicts
- Слишком много в rollback → потеря работы

**Действие:** проверить `git log -p <file> --since="2 weeks ago"` чтобы понять контекст последних коммитов.

## Альтернативы (рассмотрены и отклонены)

### Альтернатива 1: Worktree изоляция

**Что это:** Создать отдельный worktree (`git worktree add ../simply-cache-pipelines feature/cache-pipelines`) и работать там, не трогая uncommitted на основном branch.

**Почему отклонили:**
- Не решает проблему «висящего» uncommitted — оно остаётся неделями
- Создаёт два параллельных рабочих пространства, риск расхождения базы
- При разморозке frozen ТЗ — придётся всё равно делать аудит для merge

**Когда лучше:** Если бы uncommitted был размером с целое ТЗ (тысячи строк) — изолировать в worktree было бы оправдано. Сейчас объём — десятки строк на файл.

### Альтернатива 2: Откладывать до разморозки frozen ТЗ

**Что это:** Ничего не делать, ждать теста Grok → разморозки → завершения frozen ТЗ → освобождения working tree.

**Почему отклонили:**
- Timeline неизвестен (Grok может быть через месяц)
- Billing observability сломана прямо сейчас (cost audit dashboard лжёт на 10-25%)
- Каждый день uncommitted уменьшает шанс восстановления контекста при разморозке

**Когда лучше:** Если бы был конкретный близкий timeline (1-2 недели до разморозки). Сейчас — нет.

### Альтернатива 3: Закоммитить всё «как есть» одним коммитом

**Что это:** `git add -A && git commit -m "WIP: дамп всех uncommitted"`.

**Почему отклонили:**
- Нарушает gitig hygiene — коммит без понимания содержимого
- Создаёт большой атомарный блок, который сложно revert по частям
- При разморозке frozen ТЗ — нет способа понять что из коммита ещё актуально, а что устарело

**Когда лучше:** Никогда. Это анти-паттерн.

## Вопросы, которые могут возникнуть

### Q1: Что если в diff обнаружится критичный баг-фикс, который нужно сохранить?

**A:** Это категория (a) Infra prep, COMMIT с явным сообщением `fix(unfreeze): <описание>`. Но:
- Сначала убедиться что баг действительно существует (запустить affected feature)
- Не считать «похоже на исправление» = «исправление». При сомнении → STASH с пометкой «POTENTIAL FIX, нужен review»

### Q2: Что если несколько файлов logically связаны, нужно ли их коммитить одним коммитом?

**A:** Да. Например, `memory/types.ts` + `memory-queries.ts` + `migration 0051` — это один infrastructure pack, одним коммитом. Stage всех в одну операцию `git add` перед `git commit`.

### Q3: Что если в файле смесь категорий (часть infra, часть WIP)?

**A:** Сложный случай. Варианты:
- Если разделение очевидно по hunk'ам → использовать `git stash push -p <file>` (interactive по hunk'ам). Но Bash tool не поддерживает interactive — нужно делать вручную через временные patches
- Если разделение неочевидно → STASH целиком. Лучше пожертвовать infra prep чем пытаться разрезать вслепую
- Альтернатива: использовать Edit tool как мы делали в ТЗ-CacheAudit (временно вернуть зону к HEAD-версии → commit чистого hunk → re-apply через Edit обратно)

### Q4: Что делать если `git stash` / `git checkout` не работает из-за конфликтов?

**A:** Это значит что uncommitted уже частично перекрывается с какими-то commit'ами в branch. Расследовать через `git log -p <file>`. Скорее всего, нужно будет вручную merge'ить.

### Q5: Сколько stashes — это «много»?

**A:** Не больше 3-4 named stashes на frozen ТЗ. Если получается 10+ stashes — это сигнал что классификация была неверной (слишком много wedged в (c)). Пересмотреть → возможно часть на самом деле (a) или (b).
