# Simply — Архитектура обработки вложений

**Версия:** 1.0  
**Дата:** 2026-04-15  
**Статус:** Утверждено

> Архитектурный стандарт. Все решения по обработке файлов в Simply сверяются с этим документом.  
> Изменения — только при пересмотре архитектуры, не при каждом ТЗ.

---

## Главный принцип

**Максимум работы при загрузке файла, минимум при разговоре.**

Чем больше извлечено из файла до начала чата — тем проще всей системе. Любая модель умеет работать с текстом. Не каждая модель умеет работать с файлами.

---

## Ограничения провайдеров (факты, проверено по docs.x.ai)

| Возможность | Grok 4.1 Fast / 4.20 | Claude Haiku 4.5 |
|---|---|---|
| Текст | ✅ | ✅ |
| Изображения (jpg/png) | ✅ нативно, до 20 MiB | ✅ нативно |
| PDF как file part | ❌ не поддерживается | ✅ нативно, до 100 стр |
| DOCX/XLSX как file part | ❌ не поддерживается | ❌ не поддерживается |
| Документы через API | Только через платные tools (attachment_search, collections_search) | Не применимо |

**Вывод:** Grok работает с текстом и изображениями. Для PDF и других документов нужна либо серверная конвертация в текст, либо Haiku.

## Три слоя обработки

### Слой 0 — Серверное извлечение при загрузке ($0, без AI)

Происходит на сервере при upload. Ноль токенов, ноль стоимости AI, миллисекунды.

| Тип файла | Инструмент | Результат в message.parts | Статус |
|---|---|---|---|
| TXT | as-is | text/plain | ✅ Работает |
| MD | UTF-8 decode | text/plain | ✅ Работает |
| CSV | UTF-8 decode | text/plain | ✅ Работает |
| DOCX | mammoth (extractRawText) | text/plain | ✅ Работает |
| XLSX/XLS | xlsx (sheet_to_csv) | text/plain | ✅ Работает |
| PDF (текстовый) | pdf-parse или аналог | text/plain | 🔲 Запланировано (ТЗ-ATTACH-1) |
| PDF (сканированный) | Определяется эвристикой → остаётся как PDF | application/pdf → Haiku | 🔲 Запланировано |
| JPG/PNG | as-is → Blob | image/* | ✅ Работает |

**Как отличить текстовый PDF от скана:**  
Извлечь текст библиотекой. Если количество символов на страницу ниже порога (~30 символов/страницу) — это скан или графика. Точный порог подобрать эмпирически.

**Выбор библиотеки для PDF:** Использовать то что уже есть в проекте или проверено на Vercel serverless. Не менять библиотеку без реальной причины.

**Результат Слоя 0:** После загрузки 7 из 9 типов файлов превращаются в text/plain. Остаются два типа для vision-модели: изображения (jpg/png) и сканированные PDF.

### Слой 1 — KITT: обработка в чате

#### Текстовые файлы (text/plain) → Grok

Все файлы, сконвертированные в text/plain на Слое 0.

Содержимое вставляется в сообщение как текст. Grok видит его напрямую и отвечает. Содержимое сохраняется в БД — Grok помнит файл в последующих сообщениях.

#### Изображения (jpg/png) → Haiku

**Текущее решение (принято):** Запрос с изображением маршрутизируется на Claude Haiku 4.5. Haiku видит картинку и отвечает пользователю. Ответ Haiku сохраняется в истории чата. Следующее сообщение без вложения — обратно на Grok. Grok видит ответ Haiku в истории и продолжает разговор.

**Будущее улучшение (после миграции xAI):** Двухшаговый подход — Haiku описывает изображение (специальный промпт PE-команды), описание в историю, Grok даёт умный ответ. Или: A/B тест Grok vision vs Haiku, если Grok достаточно хорош — убрать Haiku из этого маршрута.

#### PDF (текстовый) → Grok (после ТЗ-ATTACH-1)

Текст извлечён при upload (Слой 0) → стал text/plain → Grok видит как обычный текст. Никакой маршрутизации на Haiku не нужно.

#### PDF (сканированный) → Haiku

Текстовое извлечение не дало результата → файл остаётся как PDF → маршрутизация на Haiku. Haiku умеет PDF нативно (до 100 страниц).

#### Большие документы → KITT предлагает варианты

Если текст файла превышает допустимый порог для контекста чата:

KITT (через системный промпт) предлагает пользователю:
- Показать краткое содержание (первые страницы)
- Перейти в режим Экспертиза для глубокого анализа
- Сохранить в Библиотеку для постоянного доступа

Конкретные пороги (символы, страницы) — подобрать эмпирически, не хардкодить с потолка.

---

### Слой 2 — Экспертиза: глубокий анализ

Grok 4.20 с tools. Для серьёзной работы с документом.

Пользователь загрузил большой контракт, техническую документацию, финансовый отчёт. Экспертиза анализирует через tools: fetchUrl, readDocument, knowledge_search.

**Будущее:** Multi-Agent (4 агента через Responses API + MCP) анализирует документ с разных сторон.

---

### Слой 3 — Библиотека: база знаний (RAG)

Два хранилища, один интерфейс `knowledge_search`:

**MIND (Voyage AI + pgvector)** — работает сейчас:
- Автоматически извлекает факты из разговоров
- Пользователь обсуждал документ → ключевые факты попали в MIND
- Embeddings → векторный поиск по фактам

**Collections (xAI Grok API)** — запланировано (ТЗ-XAI-COL-1):
- Пользователь явно загружает документ в Библиотеку
- xAI индексирует, хранит, ищет по фрагментам
- Любая модель находит нужный кусок через `file_search` / `collections_search`
- $2.50 / 1000 поисков + storage

**Кейс:** Пользователь загрузил 200-страничный ГОСТ в Библиотеку. Через месяц в обычном чате спрашивает: "Какой допуск на подшипники по ГОСТу?" → knowledge_search → находит фрагмент → Grok отвечает точно по документу.

## Общая память между моделями

**Как Grok знает что было в файле который обработала Haiku:**

1. Пользователь прикрепил изображение → запрос ушёл на Haiku
2. Haiku ответила текстом: "На скриншоте ошибка 502, сервер nginx..."
3. Ответ Haiku **сохранён в БД** как обычное сообщение
4. Следующее сообщение (без вложения) → Grok
5. Grok загружает **всю историю** из БД → видит ответ Haiku как текст
6. Grok отвечает на основе этой информации

**Для Grok файл не нужен — ему нужен текстовый результат обработки файла.** Это и есть принцип "максимум при загрузке".

**adaptHistoryToCapabilities** — функция-адаптер. Если в истории остался file part который текущая модель не поддерживает (например, image part при модели без vision, или PDF part при Grok), заменяет на текстовый placeholder. Работает через capabilities из model-catalog (SSOT).

## Принятые решения (не пересматриваются до завершения миграции)

1. **Гибрид Grok + Haiku** для KITT. Текст → Grok. Изображения и документы → Haiku. Решение утверждено 2026-04-14.

2. **Haiku отвечает пользователю напрямую** при вложении (один вызов, не два). Двухшаговый подход — будущее улучшение.

3. **adaptHistoryToCapabilities** через SSOT capabilities каталога — единственный механизм адаптации истории. Никаких `isSimplyNonAnthropicModel`, никаких хардкодных strip-функций.

4. **PDF text extraction при upload** — приоритетное улучшение (ТЗ-ATTACH-1), но не блокирует миграцию xAI.

5. **Пороги размеров** — подбираются эмпирически, не назначаются с потолка.
