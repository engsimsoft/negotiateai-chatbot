**Версия:** 1.0  
**Дата:** 2026-04-17  
**Статус:** Утверждена (архитектурное решение)  
**Автор:** Архитектор (Claude Opus)  
**Связанные документы:** MIND_ARCHITECTURE.md, SIMPLY_ATTACHMENT_ARCHITECTURE.md, ADR 052

## Проблема

После миграции на xAI Grok выявлено критическое различие в управлении контекстом между провайдерами:

| Режим | Модель | Что происходит при переполнении |
|---|---|---|
| Simply Chat | Grok 4.1 Fast / 4.20 | MIND Extract (60%/80%) — факты сохраняются в долговременную память |
| Expertise | Grok 4.20 | **Sliding window — молчаливая обрезка старых сообщений** |
| Create | Grok 4.20 | **Sliding window — молчаливая обрезка старых сообщений** |
| Projects (Anthropic tier) | Claude Sonnet/Opus/Haiku | Anthropic Compaction API — прозрачное сжатие провайдером |
| Projects (Grok override) | Grok 4.20 | **Sliding window — молчаливая обрезка** |

**У xAI нет аналога Anthropic Compaction API.** В режимах expertise/create/projects-on-Grok пользователь теряет начало разговора без предупреждения. При загрузке больших документов (PDF, XLSX) контекст заполняется быстро — одного предупреждения недостаточно.

**Дополнительный аргумент за Grok:** контекстное окно 2M токенов. При правильном управлении контекстом это даёт огромный запас для длинных рабочих сессий в expertise и create.

---

## Решение: Simply Compaction

Собственный механизм сжатия контекста для всех Grok-чатов. Принцип: **Summary Buffer** — структурированный итог старой части + последние сообщения дословно.

### Философия

- **Пользователь не должен знать механику.** Никаких «токенов», «контекстных окон», «сжатия». Он видит: «AI помнит то, что я ему говорил».
- **Бесшовная работа.** Сжатие происходит автоматически, разговор продолжается без разрыва.
- **Предупреждение — крайняя мера**, когда сжатие исчерпано, не первая реакция.
- **Apple-подход:** одна операция решает проблему, пользователь не принимает технических решений.

## Архитектура

### Двухслойная история

Вместо отправки полной истории в LLM отправляем:

```
┌─────────────────────────────────────┐
│  System Prompt                      │
├─────────────────────────────────────┤
│  [CONTEXT SUMMARY]                  │  ← Структурированный итог
│  Сжатие старых сообщений            │     старой части разговора
├─────────────────────────────────────┤
│  MIND facts (только Simply Chat)    │
├─────────────────────────────────────┤
│  Последние N сообщений (дословно)   │  ← Свежий контекст,
│  user → assistant → user → ...      │     полная детализация
└─────────────────────────────────────┘
```

### Фазы работы

#### Фаза 0 — Обычная работа (0–50% контекста)

- Вся история отправляется как есть
- Виджет контекста: нейтральная полоска прогресса (без цифр, без процентов)
- Никаких вмешательств

#### Фаза 1 — Первое сжатие (50–70%)

**Триггер:** usage ≥ 50% от рабочего лимита (SIMPLY_CONTEXT_LIMIT, не полное окно модели)

**Действия:**
1. Grok 4.1 Fast генерирует структурированный summary старых сообщений
2. Summary инжектируется как блок `[CONTEXT SUMMARY]` в system prompt
3. Старые сообщения исключаются из отправки в LLM
4. Последние 15–20 сообщений остаются дословно
5. Summary + индекс сжатия сохраняются в БД (поле в таблице чата)

**Для пользователя:**
- В UI все сообщения остаются видимыми — визуально ничего не меняется
- Виджет показывает мягкий индикатор: иконка 📦 + «Разговор сжат»
- Разговор продолжается бесшовно

#### Фаза 2 — Повторное сжатие (снова 50–70% после Фазы 1)

**Триггер:** после первого сжатия контекст снова заполнился

**Действия:**
1. Новый summary включает: предыдущий summary + сообщения от прошлого сжатия до текущего окна
2. Обновлённый summary заменяет предыдущий в system prompt
3. Дословное окно сдвигается (снова последние 15–20 сообщений)

**Может повторяться многократно.** Каждый цикл «продлевает жизнь» разговора. С окном Grok в 2M токенов — потенциально десятки циклов.

#### Фаза 3 — Рекомендация нового чата (85%+ после 2+ сжатий)

**Триггер:** после нескольких циклов сжатия контекст всё равно критически полон (огромные вложения, экстремально длинный разговор)

**Для пользователя:**
- Настоятельная, но не паническая рекомендация: «Для лучшего качества рекомендуем начать новый чат»
- Кнопка: «Новый чат с итогом» — создаёт новый чат, инжектирует финальный summary
- Тон: помощь, не тревога. Жёлтый акцент, не красная зона

## Формат Summary

Урок индустрии: свободный текст теряет детали. Структурированный «handoff» — сохраняет.

### Промпт для генерации Summary (концепция)

> Примечание: финальные формулировки промпта — зона PE-команды. Здесь — архитектурная спецификация структуры.

```markdown
## Контекст задачи
[Что пользователь решает / над чем работает]

## Загруженные материалы
[Какие документы/файлы предоставлены, ключевые данные из каждого]

## Ключевые решения и выводы
[Что решили, какие ограничения установлены, важные факты]

## Текущий фокус
[На чём остановились, что обсуждается прямо сейчас]

## Открытые вопросы
[Что ещё не решено, что пользователь планирует обсудить]
```

### Требования к Summary

- **Максимальный размер:** 2000–4000 токенов (эмпирически подобрать)
- **Язык:** тот же что у пользователя в разговоре
- **Фокус на фактах**, не на стиле разговора
- **Материалы из вложений:** ключевые данные/выводы, не метаданные файлов
- **Нет дублирования** с system prompt и MIND facts

## Модель для сжатия

**Grok 4.1 Fast (non-reasoning)** — роль «подсобка» в архитектуре ресторана.

| Параметр | Значение |
|---|---|
| Модель | grok-4.1-fast |
| Задача | Механическая: извлечь структуру из разговора |
| Reasoning | Не нужен (non-reasoning) |
| Input cost | $0.20 / 1M tokens |
| Output cost | $0.50 / 1M tokens |

### Экономика одного сжатия

| Сценарий | Input (сообщения) | Output (summary) | Стоимость USD | Стоимость RUB |
|---|---|---|---|---|
| Короткий разговор (20K токенов) | $0.004 | ~$0.001 | ~$0.005 | ~0.50₽ |
| Средний разговор (50K токенов) | $0.010 | ~$0.002 | ~$0.012 | ~1.20₽ |
| Длинный + вложения (100K токенов) | $0.020 | ~$0.002 | ~$0.022 | ~2.20₽ |

**Вывод:** стоимость сжатия пренебрежимо мала. Даже 10 циклов сжатия за разговор — менее 25₽.

## Различие с MIND и Anthropic Compaction

| Характеристика | MIND Extract | Simply Compaction | Anthropic Compaction |
|---|---|---|---|
| **Цель** | Долговременная память | Оперативная память сессии | Прозрачное сжатие провайдера |
| **Scope** | Только Simply Chat | Все Grok-чаты | Все Anthropic-чаты |
| **Хранение** | БД (MemoryEntry, навсегда) | Поле в чате (время жизни чата) | Провайдер (непрозрачно) |
| **Что сохраняет** | Факты о пользователе | Контекст текущей задачи | Всё (решает провайдер) |
| **Модель** | Grok 4.20 (extract) + 4.1 Fast (batch) | Grok 4.1 Fast | Claude (внутренний) |
| **Триггер** | 60%/80% контекста + пауза | 50%/70% контекста | Автоматический (провайдер) |
| **В Simply Chat** | ✅ Работают вместе | ✅ (опционально, для сверхдлинных) | ❌ Не применимо |

### Взаимодействие в Simply Chat

В Simply Chat MIND и Compaction — не конкуренты, а два слоя:
- **MIND** срабатывает первым (60%/80%) — извлекает факты в долговременную память
- **Simply Compaction** — страховочная сетка, если после MIND extract контекст всё равно растёт (сверхдлинные сессии)
- Порядок: MIND extract → если контекст продолжает расти → Simply Compaction

## Виджет контекста — три типа событий

Единый компонент виджета, разная семантика в зависимости от типа события:

| Тип события | Визуал | Текст | Действие пользователю |
|---|---|---|---|
| `extract` | 🧠 Зелёный/нейтральный | «Записал в память» | Ничего не нужно |
| `compaction` | 📦 Нейтральный | «Разговор сжат» | Ничего не нужно |
| `truncation_warning` | ⚠️ Жёлтый | «Рекомендуем начать новый чат» | Кнопка «Новый чат с итогом» |
| `provider_compaction` | 📦 Минимальный | — (может не показывать) | Ничего не нужно |

### Принцип отображения

- **0–50%:** чистый интерфейс, может быть тонкая полоска без цифр
- **После compaction:** мягкий индикатор, исчезает через несколько секунд
- **85%+ после нескольких сжатий:** постоянный, но не панический сигнал с кнопкой действия
- **Никогда:** красные зоны, мигание, слово «опасность», технические термины

## Техническая реализация (высокий уровень)

### Где хранить Summary

Новое поле в таблице чата (или связанная запись):

```
compaction_summary: text | null     — текущий summary
compaction_index: integer | null    — индекс последнего сжатого сообщения
compaction_count: integer default 0 — количество сжатий в этом чате
```

### Точка интеграции

В `chat/route.ts` (или аналогичный обработчик) — перед формированием messages для LLM:

```
1. Подсчитать текущий usage (system prompt + history + MIND)
2. Если usage > threshold И compaction ещё не было для этого диапазона:
   a. Вызвать Grok 4.1 Fast для генерации summary
   b. Сохранить summary и compaction_index в БД
   c. При формировании messages: summary в system → последние N сообщений
3. Если уже есть compaction — проверить не нужно ли повторное
```

### Реализация через AI SDK

Кандидат: `prepareStep` из AI SDK v6 — позволяет модифицировать messages перед отправкой в LLM. Альтернатива: middleware-подход в `chat/route.ts` до вызова `streamText`.

### Подсчёт токенов

Использовать существующий механизм подсчёта (тот же что для виджета контекста). Не нужен точный подсчёт — достаточно оценки для определения фазы.

## Открытые вопросы

1. **Размер дословного окна (N сообщений):** 15 или 20? Или считать в токенах (последние ~30K токенов)? → Эмпирически при реализации.

2. **Максимальный размер summary:** 2000 или 4000 токенов? Баланс между полнотой и экономией контекста. → Эмпирически при реализации.

3. **Триггер — по usage% или по абсолютному числу токенов?** Usage% зависит от размера контекстного окна модели (2M у Grok). 50% от 2M = 1M токенов — это очень много. Возможно, лучше абсолютный порог (например, 100K токенов), а не процент. → Обсудить при проектировании ТЗ.

4. **Prompt caching:** xAI поддерживает `prompt_cache_key`. Summary как стабильная часть промпта — кандидат на кэширование (75% скидка на input). → Учесть при реализации.

5. **Compaction в Simply Chat поверх MIND:** нужен ли? MIND extract уже сбрасывает контекст. Но если пользователь продолжает после extract без паузы — контекст снова растёт. → Решить после анализа реальных сессий.

## Исследование (источники решения)

Решение основано на анализе индустриальных практик (апрель 2026):

- **Codex CLI (OpenAI):** handoff summary — передача контекста как «смена для другого LLM». Локальный (LLM-суммаризация) и серверный (API compact) пути.
- **Claude Code (Anthropic):** трёхуровневый механизм — обрезка tool output → cache-friendly стратегии → 9-секционный структурированный summary.
- **OpenCode:** «ступенчатое управление» — скрытие старых сообщений по timestamp + 5-секционный summary.
- **JetBrains Research (NeurIPS 2025):** observation masking сравнима с LLM-суммаризацией по качеству, но дешевле. Суммаризация не серебряная пуля.
- **Mem0:** Memory Formation > Summarization. Извлечение фактов вместо сжатия всего. Сокращение расхода токенов на 80-90%.
- **Консенсус:** Summary Buffer (summary + last N messages) — наиболее практичный компромисс для продакшен-приложений.
