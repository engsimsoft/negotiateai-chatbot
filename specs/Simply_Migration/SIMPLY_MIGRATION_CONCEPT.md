# Simply — Концепт миграции на xAI (финальный)

**Дата:** 2026-04-27
**Статус:** концепт зафиксирован, готов к разбивке на ТЗ
**Версия:** объединённая (концепт от 2026-04-26 + правки PE V2 от 2026-04-27 + архитектурные решения 2026-04-27)
**Связан с:** `SIMPLY_BRIEFING_CONCEPT.md` (Briefing pipeline — отдельный самостоятельный концепт)

---

## Главный принцип

**Надёжность важнее экономии.** Никаких заброшенных community-пакетов, single-maintainer библиотек, прокладок через старые pinned версии. Только официально поддерживаемые SDK и проверенные API. Поломка production = недоверие пользователей. Лучше платить $30-100/месяц больше за надёжность, чем экономить копейки на хрупких решениях.

---

## Протокол допуска нового провайдера или модели

**Контекст.** AI-индустрия меняется быстро — каждый месяц появляются новые модели, которые потенциально могут быть полезны Simply. Соблазн «давайте быстро подключим, попробуем» приводит к ситуациям как с MiniMax: модель работала, потом сломалась через скрытую зависимость, и весь pipeline лёг.

**Решение.** Любой новый провайдер или модель проходит **обязательный чек-лист допуска** до того как попадёт в код. Способности модели — только половина решения. Вторая половина — техническая совместимость с нашим приложением.

### Чек-лист допуска

**Раздел 1. Способности модели (что она умеет)**

| Вопрос | Зачем спрашиваем |
|---|---|
| Какую конкретно роль закрывает? (Зал / Подсобка / Кухня / Verifier / специализация) | Чтобы понимать куда вставлять, не дублирует ли существующую |
| Реальное качество на наших задачах? (тест на 5-10 типичных кейсах Simply) | Бенчмарки в интернете часто врут или измеряют не то что нам важно |
| Уровень галлюцинаций для русскоязычных бизнес-задач? | Главный приоритет Simply — ответ юристу/бухгалтеру не должен быть выдуман |
| Поддерживает ли нужные нам форматы? (русский язык, длинный контекст, function calling, vision если нужен) | Без этого технически не подключить |

**Раздел 2. Способ подключения (это и есть критическая часть)**

| Вопрос | Зачем спрашиваем |
|---|---|
| Есть ли **официальный** SDK от Vercel AI или от самого вендора? | Урок MiniMax: community-пакеты ломаются. Берём только официальное |
| Если SDK community — кто мейнтейнер, сколько активных контрибьюторов, когда последний коммит? | Single-maintainer + 5 месяцев без коммитов = красный флаг. Bus factor = 1 = отказ |
| Какие зависимости тащит SDK за собой? Не прибиты ли в нём pinned старые версии других библиотек? | Это и убило MiniMax — внутри был pinned `@ai-sdk/anthropic@3.0.6` |
| Совместим ли SDK с нашей текущей версией `ai` SDK от Vercel? Не сломает ли он другие провайдеры? | Конфликт версий ломает не только новую модель, а весь стек |
| Какой механизм аутентификации? (API ключ / OAuth / IAM) | Если требует сложной auth-инфраструктуры — растёт стоимость поддержки |

**Раздел 3. Надёжность провайдера**

| Вопрос | Зачем спрашиваем |
|---|---|
| Размер компании-провайдера и публичный статус (стартап на seed / unicorn / большая корпорация)? | Стартап на seed может закрыться через 6 месяцев. Не строим pipeline на песке |
| Есть ли публичный status page и история uptime? | Без этого не сможем диагностировать проблемы и измерить SLA |
| Где хостится API? (US / EU / RU / CN) — есть ли политические/санкционные риски? | Российская аудитория, но возможны ограничения с обеих сторон |
| Какая модель оплаты? Pay-as-you-go или только подписка? | Simply — pay-as-you-go провайдер. Месячная подписка с предоплатой = vendor lock-in |
| Есть ли SLA и компенсации при простоях? | Для production-чата критично |

**Раздел 4. Стоимость владения**

| Вопрос | Зачем спрашиваем |
|---|---|
| Цена $/1M input + output токенов | Базовая экономика |
| Прогноз месячных расходов на наших объёмах | Реальные деньги, не теоретические |
| Минимальный платёж / fixed costs | Скрытые расходы |
| Сколько **времени разработчика** уйдёт на интеграцию и поддержку? | Часто это дороже самой модели |

**Раздел 5. Стратегия отката**

| Вопрос | Зачем спрашиваем |
|---|---|
| Если эта модель завтра ляжет — на что переключаемся? | План Б должен быть до подключения, не после падения |
| Подключение через model router (Блок 9) — одна строка в конфиге? | Если провайдер не вписывается в нашу абстракцию — это сигнал что архитектура ломается под него |
| Сколько кода удалять при откате? | Если откат — это рефакторинг 50 файлов, значит провайдер слишком глубоко проник |

### Правила решения

**Красные флаги (отказ без обсуждения):**
- Только community-пакет с одним мейнтейнером
- Pinned старые версии других зависимостей внутри SDK
- Нет публичного status page
- Только месячная подписка с предоплатой без pay-as-you-go
- Нет официальной документации SDK на английском или русском

**Жёлтые флаги (требуют отдельного обоснования):**
- Стартап моложе 1 года
- Только один регион хостинга
- SDK младше 6 месяцев на рынке
- Нет публичных бенчмарков uptime

**Зелёный свет:**
- Все ответы на чек-лист собраны
- Красных флагов нет, жёлтые обоснованы
- Реальный тест на наших задачах пройден
- План отката готов

### Кто проверяет

Архитектор Simply (Claude Opus в этом проекте) **обязан пройти чек-лист и написать заключение** до того как задача попадёт в Claude Code. Заключение прилагается к ТЗ.

**Урок MiniMax:** мы не прошли этот чек-лист в момент подключения. Подключили потому что «модель работает». Через 6 месяцев получили silent hang, потерянное время на отладку, миграцию на Kimi. Чек-лист — это страховка от повторения.

---

## Идея в одном абзаце

Уйти от зоопарка провайдеров к принципу «лучшая модель на каждой роли». xAI берёт на себя всю основную работу (чат, поиск, PDF, OCR, артефакты-кандидат). Anthropic Opus остаётся только аудитором сложных задач (Профессор/Проекты — отдельный редизайн). Perplexity Sonar — отдельная пользовательская функция «Исследовать» + tool Multi-Agent + tool Экспертизы. Kimi K2.6 — новая «кухонная» модель вместо MiniMax (для длинных фоновых документов) + External Verifier для Экспертизы. MiniMax уходит из проекта полностью.

Архитектура Simply provider-agnostic через model router — переключение модели на роли это одна строка в конфиге.

## Что решили делать

### Блок 1. Интернет-инструменты — четыре специализированных инструмента

| Задача | Инструмент | Где используется |
|---|---|---|
| Быстрый поиск + чтение страниц | xAI `web_search` | Встроен в обычные ответы во всех режимах |
| Глубокое исследование | Perplexity Sonar (`sonar-reasoning-pro`) | (1) Кнопка «Исследовать» в Simply Chat, (2) tool Multi-Agent, (3) tool в режиме Экспертиза |
| Поиск по X | xAI `x_search` | Один из tools Multi-Agent |
| Документы пользователя | xAI Collections (`librarySearch`) | Один из tools во всех режимах |

Brave Search и наш `fetchUrl` уходят полностью — xAI `web_search` сам открывает найденные страницы и проверяет их. Perplexity остаётся — это №1 в мире для глубокого исследования, у xAI нет API-аналога.

Миграция применяется **сразу ко всем режимам** (Simply Chat, Экспертиза, Создать). Один инструмент везде. Иначе получаем новый зоопарк под видом миграции.

### Блок 2. UI — три кнопки в Simply Chat

Кнопок выбора инструмента нет. Есть **три кнопки управления режимом мышления — только в Simply Chat**:

| Кнопка | Что делает | Модель |
|---|---|---|
| (без кнопки) | Обычный ответ | Grok 4.1 Fast (быстрая) |
| **Думать** | Tier upgrade на разовый ответ | Grok 4.20 reasoning |
| **Исследовать** | Запускает Perplexity для этого сообщения | Sonar Reasoning Pro |
| **Команда экспертов** | Включает Multi-Agent режим | Grok 4.20 Multi-Agent |

После ответа в чате остаётся плашка «Глубокое исследование · 23 источника» / «Поиск в интернете · 5 источников» / «Из Библиотеки · N источников».

**В Экспертизе кнопок нет** — UI чистый, без кнопок управления режимом. Причины:
- «Думать» не нужна — Grok 4.20 reasoning в Экспертизе работает всегда
- «Исследовать» не нужна — Perplexity доступна модели как tool, она сама решает когда вызывать
- «Команда экспертов» не нужна — Экспертиза работает соло; если задача шире одного эксперта, модель в тексте рекомендует переключиться в Simply Chat и нажать «Команда экспертов»

UI-консистентность с продуктовым обещанием: пользователь платит за то что модель **сама ведёт работу до результата**. Кнопки в Экспертизе = признание что модель не справляется автономно.

Apple-подход: каждая кнопка = понятная решённая задача. Никаких «выбор инструмента» — это технический выбор, не пользовательский.

### Блок 3. PDF — полностью на xAI Files API

Текстовые, сканы, смешанные — все идут одним путём через xAI Files API + `attachment_search`. xAI делает OCR и layout-aware parsing на своей стороне.

Что удаляется:
- Библиотека `pdf-parse`
- Эвристика «30 символов на страницу»
- Привязка PDF к Haiku через `chat-vision`

Что закрывается этим решением: проблема «пользователь общается с Grok → подкидывает PDF → его читает Haiku → Grok дальше видит только пересказ». PDF теперь остаётся в контексте Grok как `file_id`, никаких пересказов.

**Стратегия резервирования:** PDF параллельно лежит в Vercel Blob. При ошибке xAI Files API → re-upload из Blob. Не зависим только от того что xAI хранит файл.

**Чек-лист удаления переходного кода (Шаг 4):**
- `convertTextFilePartsInMessage` и `convertTextFilesInAllMessages` в [app/(chat)/api/chat/route.ts:233-284](../../app/(chat)/api/chat/route.ts#L233) — после xAI Files API файлы идут по `file_id`, конверсия text/plain в inline text больше не нужна.
- Блок `stripOldAttachmentsFromHistory` обработки `📄 **Файл:` маркера в [route.ts:343-352](../../app/(chat)/api/chat/route.ts#L343) — станет no-op.
- UI-детектор inline-маркера в [components/message.tsx](../../components/message.tsx) (`inlineFileMatch`, регекс `^📄 \*\*Файл: ...\*\*\n\`\`\``) — был добавлен v3.100.5 как UI-фикс «портянка после reload». После Шага 4 в БД будут file parts → карточка отрисуется через `attachmentsFromMessage`, детектор станет мёртвым кодом.

### Блок 4. Vision/OCR — упрощение до одного пути

- TaskId `vision:ocr` (мёртвый код, 0 вызовов) — удаляется вместе с файлом `lib/ai/vision-ocr.ts`
- TaskId `chat-vision` остаётся как страховка для dev-сценариев в `/dev/models`. Default-модель меняется с Claude Haiku на Grok 4.1 Fast non-reasoning

Anthropic полностью уходит из обработки картинок и PDF.

### Блок 5. Multi-Agent — полноценный агент с планированием

Когда пользователь нажимает «Команда экспертов» — Multi-Agent **не отвечает сразу**. Работает по фазам:

**Phase 1 — Уточнение (опционально).** Если контекста мало → агент задаёт пользователю наводящие вопросы.

**Phase 2 — План.** Создаётся todo-list с выбором инструментов под каждый шаг.

**Phase 3 — Сбор информации.** Агенты по плану ходят в источники через function calling:
- Встроенные xAI tools: `web_search`, `x_search`, `code_execution`
- Наши client-side tools: `perplexity_research`, `librarySearch`

**Phase 4 — Обсуждение.** 4 sub-агента разбирают собранное между собой через `use_encrypted_content` (полная история контекста, не саммари).

**Phase 5 — Финальный ответ.**

**Технически:** Perplexity подключается **как наш собственный tool через function calling в Responses API**, не через MCP-сервер. Никаких публичных endpoints. Это обычный client-side tool как `librarySearch`. Multi-Agent сам решает когда вызывать Perplexity, может вызвать несколько раз с разными параметрами.

Compaction (v3.95) работает поверх этого без изменений — провайдер-агностично.

**Что отбросили:**
- MCP-сервер для Perplexity — публичный endpoint = риски auth/throttling/observability
- Pre-flight Perplexity (всегда вызывать перед Multi-Agent) — заменено на agentic подход где модель сама решает
- Саммари при handoff — Multi-Agent работает с полной историей через `use_encrypted_content`
- LangGraph/OpenAI Agents SDK паттерны — не применимы, 4 sub-агента это внутреннее устройство одной модели

### Блок 6. Иерархия моделей — пять ролей

| Слой | Модели | Где |
|---|---|---|
| **Зал** (видит пользователь) | Grok 4.20 reasoning | Экспертиза, Создать, ответы в реальном времени |
| **Подсобка** (фон, дёшево) | Grok 4.1 Fast | Memory, Compaction, Filter, утилиты |
| **Кухня** (длинные документы) | Kimi K2.6 | Briefing author/section/podcast (вместо MiniMax), кандидат для артефактов |
| **External Verifier** | Kimi K2.6 | Независимая проверка критических утверждений в Экспертизе |
| **Аудитор** | Claude Opus | Профессор / Проекты (отдельный редизайн позже) |
| Embeddings | Voyage | MIND |
| Search | Perplexity | Кнопка «Исследовать» + tool Multi-Agent + tool Экспертизы |

**Принцип:** xAI делает основную работу, специализированные модели на специализированные задачи. Anthropic уходит из всего кроме аудита. **MiniMax уходит из проекта полностью.**

Для российского бизнеса (юристы, бухгалтеры, инженеры) **отсутствие галлюцинаций важнее глубины** — главный приоритет Simply. xAI заявлен как low hallucination + strict prompt adherence.

**External Verifier — обоснование.** Kimi K2.6 — независимая школа обучения от Grok (китайская vs американская) — даёт реальный второй взгляд, не повторяющий слабости Grok. Закрывает открытый вопрос O1 концепта (механика подключения Opus-аудитора) применительно к Экспертизе. Opus остаётся для Профессор/Проекты как было; Экспертиза получает Kimi K2.6.

**Концентрация ставки на Kimi K2.6:** одна модель в трёх ролях (Кухня + Verifier + кандидат для артефактов). Принимаем риск — провайдер-агностичность через model router (Блок 9) покрывает откат.

### Блок 6.5. Режим Экспертиза — спецификация

**Назначение:** премиум-режим для серьёзных деловых запросов где пользователь ждёт ответ профессионального уровня и готов подождать.

**Базовая модель:** `grok-4.20-reasoning` (single agent, всегда включён, не через кнопку).

**Параметры:** температура 0.3 (наследуется от текущей конфигурации).

**Язык системного промпта:** русский (PE-решение, согласуется с рекомендацией xAI: системный промпт на языке аудитории даёт лучшее instruction following).

**Палитра tools модели:**
- `web_search` (xAI built-in)
- `librarySearch` (xAI Collections)
- `code_execution` (xAI built-in)
- `perplexity_research` (наш client-side tool через function calling)
- `createDocument`

**Что модель НЕ делает в Экспертизе:**
- Не вызывает `x_search` (вне области режима)
- Не работает в режиме многоагентного обсуждения (это Multi-Agent, отдельный режим)

**UI:** чистый чат, без кнопок управления режимом.

**External Verifier:** Kimi K2.6 на критических утверждениях. **Механизм определяется A/B тестом** (см. Шаг 8 плана работ): синхронная цепочка vs постобработка с плашкой. Делаем оба варианта, сравниваем на реальных кейсах, выбираем лучший.

**Граница с режимом Проекты:**
- Экспертиза работает в стандартной архитектуре Simply: `SIMPLY_CONTEXT_LIMIT` 200K токенов, MIND extract при подходе к `CONTEXT_BUDGET` 140K, Compaction срабатывает при необходимости. Все механизмы сжатия провайдер-агностичны и работают одинаково во всех режимах
- **Никаких отдельных технических лимитов под Экспертизу нет**
- Граница с Проектами — **продуктовая, не техническая**: Экспертиза = одноразовая консультация (пришёл, спросил, получил ответ), Проекты = накопительная работа (документы, итерации, возврат к одной теме). Модель Экспертизы рекомендует переключиться на Проекты по характеру задачи, не по числу токенов

**Workflow и поведение модели** — территория PE, фиксируется в системном промпте Экспертизы (отдельная сессия PE).

**Опциональное расширение в будущем (не v1):**
По рекомендации xAI возможна hybrid-архитектура где Экспертиза вызывает `grok-4.20-multi-agent` для отдельной фазы deep gathering на сложных задачах, а финальный синтез и артефакт делает reasoning-модель. **В v1 не реализуется** — сначала надёжная reasoning-версия. Зафиксировано в backlog как `TZ_ExpertiseHybridMultiAgent`.

**Зависимости:**
- Блок 1: Perplexity как tool модели — обязательно
- Блок 3: xAI Files API — критично (модель видит документы напрямую)
- Блок 6: Kimi K2.6 как verifier — обязательно
- Миграция артефакт-промптов в Skills — блокер качества Экспертизы тоже, не только A/B теста артефактов

### Блок 7. Артефакты — A/B тест 3 моделей

Сейчас все 5 типов на Sonnet 4.6. Тестируем:

| Модель | Кандидат как |
|---|---|
| Sonnet 4.6 | Эталон (текущая) |
| Kimi K2.6 | Document-to-Skill специализация, новая «кухня» |
| Grok 4.20 reasoning | Единая экосистема xAI |
| MiniMax | **исключена** (модель уходит из проекта) |

**Решение per-type** — на разных типах артефактов могут победить разные модели.

Принцип выбора: если качество китайской модели сопоставимо с Sonnet → берём дешёвую (экономия 70-90%). Если хуже — оставляем Sonnet для этого типа.

**Окончательный выбор только после реальных тестов, не по рейтингам.**

**Блокер A/B теста:** все промпты артефактов inline в `artifacts/<kind>/server.ts`, заточены под Sonnet. Без переноса в `lib/prompts/skills/<kind>/SKILL.md` тест будет несправедливым. Поэтому миграция промптов в Skills — обязательная зависимость теста.

### Блок 8. Архитектурные правила выбора инструмента

Архитектор Simply фиксирует **правила и условия**. **Формулировки промптов** — задача проекта Prompt Engineering & Agent Behavior.

**Триггеры выбора инструмента (универсальная палитра):**

| Триггер запроса | Инструмент |
|---|---|
| Конкретный факт, цифра, курс, погода, новость | `web_search` |
| Запрос с прямым URL «прочитай эту статью» | `web_search` (xAI открывает автоматически) |
| Свежие посты, обсуждения, мнения | `x_search` |
| Сравнение нескольких вариантов / технологий / рынков | `perplexity_research` |
| Многошаговый аналитический отчёт | `perplexity_research` |
| Документы пользователя | `librarySearch` |
| По умолчанию | `web_search` |

**Доступность инструментов по режимам:**

| Инструмент | Simply Chat | Экспертиза | Multi-Agent | Создать |
|---|---|---|---|---|
| `web_search` (xAI) | да | да | да | да |

| `code_execution` (xAI) | нет | да | да | по необходимости |

### Блок 9. Forward compatibility — model router и unified interface

xAI подтвердил:
- 17 апреля 2026 вышла Grok 4.3 beta (видео, слайды, PDF, speech)
- Grok 5 ожидается середина 2026
- Endpoints 4.20 продолжат поддерживаться

**Рекомендация xAI:** «Сразу стройте абстракцию (model router + unified interface) — тогда миграция на 4.3 / 5 займёт дни, а не недели.»

**Что это значит для архитектуры миграции:**
- Любая привязка к конкретному model name (`grok-4.20-reasoning`, `grok-4.20-multi-agent`, `kimi-k2.6` и т.д.) идёт через единый абстрактный слой
- TaskId в коде (например `expertise`) ссылается на role + tier, а не на конкретную модель
- Замена модели для конкретного taskId — одна строка в конфиге, не в коде
- Это не отменяет провайдер-агностичность Vercel AI SDK, но добавляет внутренний слой роутинга

**Текущее состояние:** частично уже реализовано через `lib/ai/task-assignments.ts` + `lib/ai/model-catalog.ts` (ADR-053). Финальная доработка после Фазы Г.

**Связь с провайдер-агностичностью:** концепт декларирует «архитектура Simply provider-agnostic — переключение модели на роли это одна строка в коде». Этот блок — конкретизация: внутренний router-слой между taskId и провайдером, чтобы при выходе нового Grok достаточно было обновить роутинг для роли «Зал», и все режимы автоматически перешли на новую модель.

## Открытые продуктовые вопросы

### O1 — Механика подключения External Verifier (Kimi) в Экспертизе

**Решено сделать A/B тест:** реализуем оба варианта, сравниваем на реальных кейсах:

- **Вариант A (синхронная цепочка):** Grok отвечает → Kimi проверяет → reconciliation → пользователь видит финальный проверенный ответ. Время до ответа +5-10 сек, всегда 2x стоимость, один проверенный ответ
- **Вариант B (постобработка):** Grok отвечает сразу → Kimi проверяет в фоне → плашка «verifier ✓» / «verifier disagreed» появляется позже. Без задержки ответа, всегда 2x стоимость, transparency через плашку

Решается на этапе Шага 8 плана работ.

### O2 — Применимо ли это к режиму Проекты

Режим Проекты будет полностью переделан под xAI после Multi-Agent. Принципы те же — но это отдельный концепт и отдельное ТЗ. **В текущем документе не обсуждается.**

### O3 — Жизненный цикл PDF в Files API

- TTL (автоудаление через N дней или при удалении сообщения)
- Хранение `file_id` в БД (привязка к message attachment)
- Re-upload из Vercel Blob если файл уже удалён в xAI

Решается в ТЗ при реализации Блока 3 (Шаг 4).

### O4 — Интерактивные HTML/React артефакты — отдельный будущий концепт

Это **новый класс архитектуры**, не миграция. Текущая система Simply этого не поддерживает — нет canvas-runtime, нет sandbox, нет нового `artifactKind`.

Сильные кандидаты по специализации (для будущего теста): Kimi K2.6 (заявляет «Awwwards-level front-end»), GLM-5.1, Sonnet 4.6.

**Зачем это будет нужно:** аудитория 40-60+ выигрывает от визуализации больше всего — объяснение сложных концепций, сравнения, дашборды, образовательный контент. Конкурентное преимущество — российские AI-продукты этого пока не делают.

**Решение по этому пункту:** оформляется отдельным концептом и отдельным ТЗ **после** закрытия миграции xAI.

### O5 — Reconciliation при расхождении Grok ↔ Kimi-verifier

Решение: показать пользователю обе позиции с пометкой «эксперт Kimi не согласен с пунктом X — вот его обоснование». Transparency, не маскировка. Не тай-брейкер третьей моделью — это удорожание без пропорционального выигрыша.

Точная UI-реализация плашки расхождения — на этапе Шага 8.
