# Simply Briefing — Концепт миграции и расширения источников

**Дата:** 2026-04-27
**Статус:** концепт согласован, приоритет наравне с миграцией xAI
**Связан с:** `SIMPLY_MIGRATION_CONCEPT.md` (общая миграция платформы на xAI)

**Что обновлено относительно версии 2026-04-26:**
- Discovery всех типов источников переведено на xAI (web/telegram/youtube/x), без платных API на этапе onboarding — проверено реальным тестом на узкой русскоязычной теме («налоговый учёт малого бизнеса») и глобальной англоязычной («AI research»)
- Telegram discovery: xAI `web_search` через каталоги (tgstat.com, telemetr.io, telegramgroups.co) вместо платного TGStat API
- Добавлен X (Twitter) как четвёртый канал discovery через нативный xAI `x_search`
- **YouTube daily fetch переведён с Supadata на YouTube RSS feed + xAI web_search** — Supadata не нужен для briefing после реальной проверки покрытия Grok'ом
- Зафиксирован принцип «лучшие источники независимо от языка»
- Зафиксирована иерархия моделей onboarding по принципу «Зал/Подсобка»
- TGStat API и Supadata остаются опциональными fallback для production-нагрузки, не блокеры MVP

---

## Идея в одном абзаце

Briefing — это AI-агент, который вместо пользователя собирает свежие новости из его персональных источников (веб-СМИ, Telegram-каналы, YouTube-каналы экспертов, аккаунты экспертов на X) и каждое утро присылает связный брифинг в Telegram-канал пользователя. Сейчас Briefing работает на Perplexity discovery + ручной парсинг Telegram + RSS веб-сайтов + MiniMax для написания статьи. После миграции — единая xAI-экосистема (Grok 4.20 reasoning ведёт диалог, Grok 4.1 Fast выполняет агентный поиск через встроенные `web_search` и `x_search`) закрывает discovery всех типов источников; daily fetch остаётся на бесплатных официальных каналах (RSS веб-сайтов, RSS YouTube, t.me/s/, xAI x_search для X); а MiniMax заменяется на Kimi K2.6 для написания статьи. Платных каталогов и third-party scraping-сервисов в критичном пути MVP — нет.

## Что решили делать

### Принцип: разные источники = разные инструменты (но единый провайдер)

| Тип источника | Onboarding (подбор) | Daily fetch (чтение) |
|---|---|---|
| **Веб-СМИ, блоги** | xAI `web_search` без фильтров | RSS / fetchPage cascade (как сейчас) |
| **Telegram-каналы** | xAI `web_search` + `allowed_domains: ["tgstat.com", "telemetr.io", "telegramgroups.co"]` | t.me/s/ scraping (как сейчас) |
| **YouTube-каналы** | xAI `web_search` + `allowed_domains: ["youtube.com"]` | YouTube RSS feed `videos.xml?channel_id=...` + xAI `web_search` для глубины описания при необходимости |
| **X (эксперты, аккаунты)** | xAI `x_search` (нативный, semantic + user search) | xAI `x_search` + `allowed_x_handles` (узкий список сохранённых юзеров) |

Все 4 discovery вызываются параллельно (parallel tool calls). Conversation orchestrator на каждой теме сам решает какие из 4-х каналов нужны: для глобальной экспертизы (AI, tech, инвестиции) — все 4; для российского узкоспециального (налоговый учёт, ритейл РФ) — преимущественно web + Telegram; для тем с сильной видео-составляющей (образование, технические разборы) — добавляется YouTube.

**Все 4 канала daily fetch — бесплатные, без third-party API:**
- Веб через RSS (как сейчас) — официально, бесплатно
- Telegram через t.me/s/ (как сейчас) — серая зона, но работает
- YouTube через RSS feed канала — официально, бесплатно, без API key
- X через xAI `x_search` — нативно в xAI, который мы уже используем

### Замена модели для написания статьи: MiniMax → Kimi K2.6

Все три точки briefing pipeline переводятся на Kimi K2.6:
- `briefing:author` — длинная статья брифинга
- `briefing:section` — отдельные секции для refresh
- `briefing:podcast-script` — сценарий подкаста

`vercel-minimax-ai-provider` удаляется из dependencies, namespace `minimax` и `minimaxLong` убираются из `lib/ai/registry.ts`. **MiniMax уходит из проекта полностью.**

Подключение Kimi через официальный `@ai-sdk/openai-compatible` — стабильный пакет Vercel, без community-зависимостей. Прямой ключ Moonshot уже есть.

### Иерархия моделей в onboarding

| Уровень | Модель | Роль |
|---|---|---|
| **Зал** (видит пользователь) | **Grok 4.20 reasoning** | Conversation orchestrator: ведёт диалог, понимает контекст пользователя, формирует темы и `briefingStyle`, решает какие из 4-х tools вызвать на конкретной теме. Заменяет Sonnet 4.6. |
| **Подсобка** (фон, дёшево) | **Grok 4.1 Fast** | Discovery workers внутри 4 tools (`webDiscovery`/`telegramDiscovery`/`youtubeDiscovery`/`xDiscovery`). Натренирован для agentic search — это его основная компетенция. Вызывает встроенные xAI tools (`web_search`/`x_search`). |
| **Кухня** (длинные документы) | **Kimi K2.6** | `briefing:author` / `briefing:section` / `briefing:podcast-script` |

**Принцип «Зал/Подсобка» соблюдён:** умный думает (Grok 4.20 reasoning ведёт диалог и принимает решения), дёшевый делает (Grok 4.1 Fast быстро выполняет поисковые запросы). Единая xAI-экосистема — один провайдер на весь pipeline кроме автора.

### Что меняется vs текущая реализация

**Onboarding — критичный апгрейд качества:**
- Сейчас: Perplexity sonar-pro **одним промптом** ищет и сайты, и Telegram-каналы → результат: битые ссылки, выдуманные каналы, низкая точность. Корень проблемы: Perplexity отдаёт ссылки **из своего индекса**, не открывая страницы при выдаче. Telegram-каналы возвращаются из веб-индекса (старые подборки, LLM-генерированные списки) — половина мёртвые или выдуманные.
- После: четыре параллельных специализированных discovery через xAI, который **реально открывает страницы** при поиске. Битые ссылки фильтруются на стороне провайдера. Telegram-каналы вытаскиваются из реальных каталогов (TGStat/Telemetrio/TelegramGroups), которые xAI читает в момент запроса. Покрытие шире (3 каталога одновременно), точность выше.
- **Подтверждено реальным тестом** на узкой теме «налоговый учёт малого бизнеса»: 8 проверенных каналов с точными @username, подписчиками (37k, 28k, 4k, 1k, 470, 440, 341, 163), датами последних публикаций и темами постов («поправки по НДС-вычетам при смене объекта УСН»), включая длинный хвост нишевых каналов.
- **Подтверждено на глобальной теме AI research:** 6+ каналов с английским контентом, корректные @username, ссылки на arXiv, GitHub-репозитории.

**Daily fetch — расширение покрытия без third-party API:**
- Сейчас: только RSS, web (через fetchPage), Telegram (через t.me/s/)
- После: + YouTube-каналы через **официальный RSS feed канала** + X-аккаунты через нативный xAI `x_search` с `allowed_x_handles`

**YouTube — без Supadata, без YouTube Data API key:**
- Сейчас: не покрыт вообще
- После: YouTube публикует **бесплатный RSS feed** для каждого канала (`https://www.youtube.com/feeds/videos.xml?channel_id=CHANNEL_ID`). Этот feed отдаёт 15 последних видео с `title`, `description`, `published_at`, `link` — для briefing этого хватает. Если нужно больше глубины (chapters, summary, top comments) — открываем страницу видео через xAI `web_search`, Grok возвращает description с chapters в 85-95% случаев.
- **Полный дословный transcript для briefing не требуется** — для отбора и пересказа экспертного видео достаточно title + description + chapters. Дословный transcript — это отдельная фича Стенограммы, не briefing.

**Написание статьи — замена модели:**
- Сейчас: MiniMax-M2.7 через хрупкий community-пакет (silent hang с 23 апреля)
- После: Kimi K2.6 через официальный `@ai-sdk/openai-compatible`

**Orchestrator onboarding — миграция модели:**
- Сейчас: Sonnet 4.6 ведёт диалог через 4 client-side tools (deepResearch/fetchUrl/readTelegramChannel/updateBriefingPreview)
- После: Grok 4.20 reasoning ведёт диалог через 4 новых discovery tools + сохранённые updateBriefingPreview/fetchUrl/readTelegramChannel. Mixing server-side (xAI native) и client-side (наши) tools в одном запросе официально работает в xAI Responses API.

### Что НЕ меняется

- Telegram fetching через t.me/s/ scraping остаётся (бесплатно, работает, других legal путей чтения публичных каналов без админ-прав нет)
- RSS-обработка для веб-СМИ остаётся (бесплатно, без AI)
- pdf-parse и server-side утилиты — без изменений
- Финальная компоновка брифинга AI-моделью (Author) остаётся отдельным этапом
- `fetchUrl` — остаётся для обнаружения RSS на найденных веб-страницах (xAI `web_search` не возвращает RSS-фиды, а daily fetch без RSS работает хуже)
- `readTelegramChannel` — остаётся для валидации @username, который пользователь ввёл руками
- `updateBriefingPreview` — UI tool без изменений

## Принцип: язык источников

**Discovery ищет лучшие в мире источники по теме — независимо от языка. Автор переводит на русский в момент написания брифинга.**

Это два разных этапа pipeline, и они должны быть разведены:

| Тема | Где лучшие первоисточники | Discovery поведение |
|---|---|---|
| AI research | Anthropic blog, OpenAI, ArXiv, Two Minute Papers (YouTube), Yannic Kilcher (X) — англоязычные | Возвращает англоязычные источники |
| Российский налоговый учёт | Только русскоязычные (юристы, ФНС-разъяснения, бухгалтерские эксперты) | Возвращает русскоязычные естественным образом |
| Глобальные технологии | Микс — TechCrunch (en), Habr (ru), Telegram-каналы экспертов (оба языка) | Возвращает микс |
| Российский ритейл | Преимущественно русскоязычные + некоторые англоязычные глобальные обзоры | Возвращает соответствующий микс |

**Критерий отбора — качество источника**, не его язык: авторитет, частота публикаций, экспертность, citation index. Язык определяется темой, а не пользовательским предпочтением.

**Автор брифинга (Kimi K2.6)** в системном промпте получает явное правило: работает с источниками на любом языке, пишет брифинг на русском, переводит термины адаптивно с сохранением точности. Это требование PE-команды для финальной формулировки промпта.

**Что это убирает из текущей реализации:**
- Поле `sourceLanguage` остаётся в данных (для UI и контекста автору), **но не используется как фильтр на этапе discovery**
- Промпт onboarding больше не говорит «по умолчанию русскоязычные» — говорит «лучшие в мире по теме»

## Зачем это аудитории Simply

Целевая аудитория — российский бизнес 40-60+. Анализ их потребностей:

| Источник новостей | Доля в их новостной диете | Сейчас покрыто? | После реализации |
|---|---|---|---|
| Telegram-каналы | ~50-60% | да, но низкое качество подбора | да, точное качество подбора через каталоги |
| Российские деловые СМИ | ~25-30% | да | да |
| YouTube эксперты (через VPN) | ~10-15% | **нет** | **да** через RSS feed канала |
| X (Twitter) — эксперты | ~5-10% (особенно для тем глобальной экспертизы) | **нет** | **да** через нативный xAI `x_search` |
| Instagram, TikTok, Facebook | ~0% | не нужно (заблокированы в РФ) | не нужно |

После реализации: **95%+ покрытие** новостной диеты бизнес-аудитории через автоматический брифинг. Для тем с глобальным контекстом (AI, tech, инвестиции) X-аккаунты экспертов добавляют ценный сигнал, который российский Telegram не покрывает.

## Почему именно эти инструменты — обоснование

### xAI `web_search` для веба и каталогов

Из официальной документации `docs.x.ai/docs/guides/tools/search-tools`:
- Real-time поиск + браузинг веб-страниц (xAI открывает найденные страницы и проверяет их)
- `allowed_domains` / `excluded_domains` — точечный контроль до 5 доменов
- Citations возвращаются нативно
- Только через Responses API
- Grok 4.1 Fast специально натренирован для agentic search

Преимущество перед Perplexity для onboarding: xAI **сам открывает страницы** в процессе поиска → битые ссылки фильтруются автоматически. Perplexity возвращает ссылки на основе индекса, не проверяя живы ли они сейчас.

### xAI `web_search` через каталоги для Telegram (вместо платного TGStat API)

Изначально концепт предусматривал TGStat Search API как основной источник Telegram-каналов на этапе onboarding. После проверки реальностью — отказались.

**Почему отказались от TGStat API:**
- Только месячная подписка с предоплатой, нет pay-as-you-go
- Тариф S (2 100 ₽) поддерживает только 30 каналов и 6 000 запросов в месяц — впритык
- Тариф L (для 1000 пользователей) — цена не публикуется, нужен запрос в sales
- Нет публичной status-page, нет SLA в оферте, нет публичных бенчмарков latency
- Нет официального Node.js/TypeScript SDK — только community-обвязка для Python/PHP/Go
- Vendor lock-in на одного российского ИП (Кижикин Ю.А.)

**Почему xAI `web_search` через каталоги работает лучше:**
- TGStat, Telemetrio и TelegramGroups публикуют свои каталоги как веб-страницы — TopChannels, рейтинги по категориям, метрики каналов (subscribers, ER, citation index)
- xAI `web_search` с `allowed_domains: ["tgstat.com", "telemetr.io", "telegramgroups.co"]` (3 каталога одним вызовом) **открывает эти страницы при поиске** и вытаскивает каналы по теме с метриками
- **Покрытие шире** одного API — пересечение трёх каталогов даёт более полную картину
- **Каналы заведомо живые** — xAI проверяет страницы в момент запроса
- **Бесплатно** — входит в xAI, который мы используем для основной работы
- **Нет vendor lock-in** — добавил/убрал домен в `allowed_domains`, и всё
- **Нет SLA-рисков** на одного провайдера — упал TGStat, остаются Telemetrio и TelegramGroups в том же `allowed_domains`

**Подтверждено реальным тестом** на узкой теме («налоговый учёт малого бизнеса») и глобальной («AI research»). Качество выдачи — точные @username, подписчики, даты последних публикаций, темы постов. Ссылки рабочие, выборочно проверены вручную.

### YouTube RSS feed + xAI `web_search` для YouTube (вместо Supadata)

Изначально концепт предусматривал Supadata API для YouTube transcripts на этапе daily fetch. После анализа реальной потребности briefing и проверки возможностей xAI — отказались.

**Что нужно для briefing на YouTube-канале:**
1. Знать, что вышло новое видео
2. Понять о чём оно (для включения в брифинг)
3. ~~Полный дословный transcript~~ — для briefing не требуется

**Почему отказались от Supadata:**
- Single-maintainer проект (Rafal Zawadzki, Берлин), bus factor = 1 — тот же тип риска, что только что заставил нас отказаться от MiniMax
- Best-effort SLA без формальных гарантий, uptime 99.7% (простои до 2 часов несколько раз в квартал)
- YouTube ToS gray zone — Supadata формально нарушает условия использования YouTube
- Подписочная модель $17-897/мес поверх задачи, которую можно решить бесплатно

**Почему YouTube RSS feed + xAI `web_search` достаточно:**

YouTube публикует **официальный бесплатный RSS feed** для каждого канала:
```
https://www.youtube.com/feeds/videos.xml?channel_id=CHANNEL_ID
```

Возвращает 15 последних видео с `title`, `description`, `published_at`, `link`, `thumbnail`. Без API key, без серой зоны, без подписки. Тот же подход, что для веб-СМИ через RSS.

Для большинства экспертных каналов (Two Minute Papers, AI Explained, Yannic Kilcher) `description` содержит TLDR с key takeaways — этого достаточно для briefing.

Если нужна большая глубина (chapters видео, summary всего ролика, top comments) — xAI `web_search` открывает страницу видео и возвращает description + chapters с таймкодами в **85-95% случаев** (проверено реальным запросом к Grok). Топ-комментарии в 40-70% случаев. **Полный дословный transcript для briefing не нужен** — для пересказа экспертного видео хватает description + chapters.

**Подтверждено реальной проверкой через Grok.** Сам xAI чётко обозначил границы: title/channel/description/summary с chapters — надёжно (85-95%); полный дословный transcript — ненадёжно (20-60%), но для briefing и не требуется.

**Когда Supadata всё-таки имеет смысл (вне scope этого концепта):**
Для отдельной фичи **Стенограмма** (пользователь даёт ссылку на YouTube/TikTok/Instagram, ожидает дословный transcript) — там Supadata Pro/Mega ($17-47/мес) оправдан как multi-platform решение в одном API. Но это другой use case, не briefing.

### xAI `x_search` для X-экспертов

Из официальной документации `docs.x.ai/developers/tools/x-search`:
- Keyword search, **semantic search**, **user search**, thread fetch
- `allowed_x_handles` / `excluded_x_handles` — фильтр по аккаунтам
- `enable_video_understanding` — анализ видео в X-постах через `view_x_video`
- Real-time доступ к X-контенту, не индекс

xAI владеет X — нативная интеграция. **`user search` находит людей по теме, не только посты** — это критически важно для onboarding (находим топовых исследователей по AI, ведущих бизнес-аналитиков).

Один провайдер закрывает и discovery (поиск экспертов), и daily fetch (отслеживание `allowed_x_handles` сохранённых аккаунтов). Никаких сторонних Twitter-API.

### Kimi K2.6 для написания статьи

**Почему MiniMax больше не подходит:**

Это не одна поломка — это структурная проблема. Официального `@ai-sdk/minimax` от MiniMax нет, только community-пакет `vercel-minimax-ai-provider`. Этот пакет:
- 5 месяцев без обновлений
- 0 PR
- 7 stars
- Один автор
- Внутри жёстко прибита версия `@ai-sdk/anthropic@3.0.6` (latest 3.0.71)

Это значит: даже если сейчас починим — через 3-6 месяцев история повторится при следующем обновлении `ai` SDK или Anthropic-провайдера. **Ради $30-50/месяц экономии получаем системную хрупкость.** Плохая сделка.

**Почему Kimi K2.6 надёжнее:**

| Параметр | MiniMax-M2.7 | Kimi K2.6 |
|---|---|---|
| Официальная поддержка SDK | только community-пакет | `@ai-sdk/openai-compatible` (официальный Vercel) |
| Состояние пакета | заброшен 5 мес | активно поддерживается |
| Качество (Intelligence Index) | 50 | 54 |
| Document-to-Skill специализация | нет | да (заявлена Moonshot как core feature) |
| Цена $/1M (blended) | $0.53 | $1.71 |

Kimi в 3 раза дороже MiniMax, но это **копейки в абсолютных цифрах** для бизнес-приложения. На 1000 брифингов в месяц разница ~$30-60. За эту цену получаем стабильность production.

**Бонус:** Kimi K2.6 уже включена в A/B тест артефактов (см. `SIMPLY_MIGRATION_CONCEPT.md` Блок 7). Если она хорошо себя покажет на briefing — это сильный сигнал и для артефактов. Унификация «кухонной» модели через всё приложение.

## Стратегия надёжности

### Что зависит от чего

| Компонент | От чего зависит | Уровень риска |
|---|---|---|
| Onboarding (orchestration + discovery) | xAI Responses API + `@ai-sdk/xai` | Низкий (крупный провайдер, официальный SDK, единая экосистема) |
| Discovery Telegram | xAI + публичные каталоги (3 параллельно) | Низкий (резерв через `allowed_domains` — упал один каталог, остаются другие) |
| Daily fetch Web | RSS feeds (стандарт, miscellaneous publishers) | Низкий |
| Daily fetch Telegram | t.me/s/ scraping | **Средний** — серая зона, Telegram может закрыть превью-страницы |
| Daily fetch YouTube | YouTube RSS feed (официальный) + xAI fallback | Низкий (официальный feed, не зависит от third-party) |
| Daily fetch X | xAI `x_search` | Низкий (нативный, тот же провайдер) |
| Briefing author/section/podcast | Moonshot API + `@ai-sdk/openai-compatible` | Низкий (официальный SDK) |
| Embeddings | Voyage HTTP API | Низкий |

**Ноль single-maintainer зависимостей** в критичном пути MVP. Это качественно отличает архитектуру от текущей (MiniMax через `vercel-minimax-ai-provider` дал silent hang именно из-за single-maintainer риска).

### План B при отказе xAI на onboarding

Onboarding — разовый процесс (юзер настраивает брифинг). Сложный fallback не нужен — достаточно вежливой ошибки «сервис временно недоступен, попробуйте через минуту» с автоматическим retry через exponential backoff.

Глобальный xAI-failover для всего приложения — отдельная задача, см. `SIMPLY_MIGRATION_CONCEPT.md` секцию «Стратегия надёжности».

### План B для daily fetch (если что-то перестанет работать)

**Telegram (если t.me/s/ станет ненадёжным):** разовый pivot на платный API:
- **TGStat Search/Stat API** — `channels/posts` метод
- **Telemetr.io API** — реальная альтернатива с OpenAPI v3 / Swagger

**YouTube (если RSS feed закроют):** xAI `web_search` остаётся как primary fallback — чтение страницы канала. Если и это перестанет работать — **Supadata Pro $17/мес** или **Apify** (codepoetry actor, $0.001/req) как тонкий wrapper. Архитектурно — `IYouTubeFetchProvider` с RSS как primary, AI fallback как secondary; интерфейс закладывается в код, реализация — только RSS на старте.

**X (если xAI x_search станет недоступен):** перезапуск задачи через retry. X-API альтернатив без xAI ecosystem — нет (third-party Twitter API больше не дают такого качества semantic search).

### Что мы запрещаем себе делать

- Использовать заброшенные community-пакеты (как `vercel-minimax-ai-provider` стало уроком)
- Зависеть от single-maintainer библиотек на критичном пути
- Жёстко прибивать старые версии зависимостей (`pinned` точные версии)
- Создавать публичные endpoints для входящих вызовов от внешних сервисов
- Принимать решения об экономии не оценив риск отказа
- Привязываться к одному платному API там, где xAI или официальный RSS закрывает задачу бесплатно

## Verification gate как практика

Каждое ТЗ онбординга начинается с **теста узкой темы** до того, как пишется код:

1. Берём узкую русскоязычную бизнес-тему («налоговый учёт малого бизнеса», «российский ритейл», «1С-программирование»)
2. Отправляем тестовый запрос xAI с конфигурацией discovery, заложенной в ТЗ
3. Сверяем результат: точность @username (выборочная проверка через t.me/), точность подписчиков, релевантность теме, наличие длинного хвоста
4. Если результат проходит порог качества — пишем код. Если не проходит — корректируем конфигурацию или возвращаемся к концепту.

Аналогично для глобальной англоязычной темы. Это инженерная практика, а не отдельный шаг ТЗ — встраивается в Phase 1 каждого ТЗ как validation gate.

Аналогичный verification gate для daily fetch:
- YouTube RSS feed: тест на 5-7 топовых экспертных каналов разных тем — проверка что description достаточно для briefing на 80%+ каналов
- X через xAI x_search: тест отслеживания `allowed_x_handles` для известного эксперта — проверка свежести и фильтрации

## Связь с общей миграцией xAI

Briefing — **самостоятельный pipeline**, не использует AI tools (`webSearch`, `fetchUrl`, `readTelegramChannel`) общего чата. Все вызовы идут к специализированным функциям briefing pipeline.

Это означает:
- Миграция AI tools на xAI `web_search` (Блок 1 общего концепта) Briefing напрямую **НЕ затрагивает**
- Briefing мигрирует **отдельным треком ТЗ** — замена `callPerplexity` на 4 discovery через xAI + добавление YouTube RSS + добавление xAI x_search для X + замена MiniMax на Kimi K2.6 + миграция orchestrator с Sonnet на Grok 4.20 reasoning
- Может выполняться **параллельно** с миграцией основных интернет-инструментов или **после**

## Что блокирует / что нужно проверить перед ТЗ

### Блокер B1 — MiniMax silent hang (закрывается через миграцию на Kimi)

**Причина проблемы зафиксирована, не гипотеза:**

Пакет `vercel-minimax-ai-provider@0.0.2` имеет pinned зависимость `@ai-sdk/anthropic@3.0.6`. Текущая версия на npm — 3.0.71. Между ними был критический фикс PR vercel/ai #6388 «prevent truncated Claude streams» (29.12.2025). Апгрейд `ai` SDK с 6.0.116 на 6.0.168 (commit 97af934, 23.04.2026) вскрыл этот старый баг — парсер MiniMax-стримов не может корректно завершить чтение после thinking-блоков.

**Решение принято: миграция на Kimi K2.6.** Не чиним хрупкое подключение к MiniMax. Убираем модель из проекта.

### ~~Открытый вопрос O1 — TGStat API: цена и доступность~~

**Закрыт.** TGStat API не используется на этапе onboarding — discovery Telegram-каналов делается через xAI `web_search` по веб-каталогам (tgstat.com, telemetr.io, telegramgroups.co). Платный API TGStat остаётся опциональным fallback для daily fetch постов на этапе production, не блокер MVP.

### ~~Открытый вопрос O2 — Supadata API: проверка надёжности~~

**Закрыт через отказ от Supadata в briefing.** YouTube daily fetch покрывается официальным RSS feed канала + xAI `web_search` для глубины описания. Полный дословный transcript для briefing не требуется. Supadata остаётся опциональным провайдером для отдельной фичи **Стенограмма** (вне scope этого концепта).

### Открытый вопрос O3 — Discovery формат для onboarding

Четыре параллельных discovery (web / telegram через каталоги / youtube / x) возвращают результаты в разных форматах. Нужна единая нормализация в `briefing_sources` таблицу с типом источника (`type: "web" | "telegram" | "youtube" | "x"`). Решается в ТЗ.

### Открытый вопрос O4 — Дедупликация на уровне профиля

Один источник может прийти из разных путей (`webDiscovery` нашёл сайт компании → `telegramDiscovery` нашёл её Telegram → `xDiscovery` нашёл её X-аккаунт). Это разные источники одной сущности — оставляем все или дедуплицируем по первоисточнику?

Базовая дедупликация по `sourceUrl` обязательна (один и тот же URL не может прийти дважды). Сложнее: нужно ли отслеживать «один автор в нескольких каналах»? Решается в ТЗ.

### Открытый вопрос O5 — channel_id для YouTube RSS feed

YouTube RSS feed работает с `channel_id` (формат `UCxxxxxx...`), не с `@handle`. На этапе discovery xAI возвращает каналы как ссылки `youtube.com/@handle` — нужно конвертировать `@handle` в `channel_id` перед сохранением в `briefing_sources`. Это разовая операция (открыть страницу канала, извлечь `channelId` из метаданных). Делается в ТЗ через простой парсер страницы канала.

## Что закрывается этим планом

После реализации:
- Битые ссылки на этапе подбора источников — почти исчезают (xAI открывает страницы при поиске)
- Низкое качество подбора Telegram-каналов — три каталога одновременно дают точную картину с метриками
- Слепое пятно по YouTube — закрывается через **официальный RSS feed канала + xAI web_search**, без third-party API
- **Слепое пятно по X** — закрывается через нативный xAI `x_search`
- Зависимость от Perplexity для onboarding — уходит, остаётся только для глубокого исследования (кнопка «Исследовать») и Multi-Agent
- **MiniMax silent hang — устраняется навсегда** (модель уходит из проекта)
- Системная хрупкость через заброшенный community-пакет — устраняется
- **Vendor lock-in на платный каталог Telegram** — устраняется через xAI `web_search` с `allowed_domains` на 3 каталога
- **Single-maintainer риск Supadata в критичном пути** — устраняется через YouTube RSS + xAI fallback
- **YouTube ToS gray zone в критичном пути** — устраняется (RSS feed официальный, xAI читает публичные страницы)
- **Русскоязычный фильтр на discovery** — снимается, ищем лучшие в мире по теме

**Итог:** в критичном пути MVP **ноль single-maintainer пакетов, ноль платных third-party API, ноль серых зон** (кроме существующего t.me/s/ — оставлен как есть, замена возможна в production).
