## ✅ Finding #1: Устаревший `contextWindow` для Grok 4.1 Fast обеих записей в model-catalog.ts — ЗАКРЫТО Phase 3.1 (2026-04-28)

**Где:** [lib/ai/model-catalog.ts:388](../../../lib/ai/model-catalog.ts#L388) (reasoning), [lib/ai/model-catalog.ts:398](../../../lib/ai/model-catalog.ts#L398) (non-reasoning)

**Что:** Обе записи `grok-4-1-fast-reasoning` и `grok-4-1-fast-non-reasoning` имеют `contextWindow: 128_000`. По актуальной документации xAI (docs.x.ai, проверено WebSearch 2026-04-28) и независимым источникам (datastudios.org, mem0.ai, designforonline.com) — реальное окно **2 000 000 токенов**. Расхождение 16x.

**Почему проблема:**
- Estimator (если есть в проекте) и compaction логика могут принимать решения о подрезке истории на основе ложного 128K лимита → преждевременная компактация / отказ от длинного контекста, который модель реально тянет.
- DevPanel и UI показывают неверный лимит → пользователь и владелец принимают неверные решения о вмещении документов.
- `docs/ai-providers.md` и `docs/ai-chats-map.md` могут унаследовать неверное число.

**Предлагаемое решение:** Обновить `contextWindow: 128_000 → 2_000_000` в обеих записях. `maxOutput: 16_000` — оставить (актуальное значение xAI не подтверждено в ходе аудита, отдельный микро-фолоу-ап при необходимости).

**Влияние:** **medium** (затрагивает SSOT каталога, потенциально влияет на estimator + compaction решения, но не ломает текущий код — просто упускает возможность).

**Обнаружено:** Phase 1.2 Audit, ТЗ-Simply_Migration_Step3.

**Решение по этому ТЗ:** **Чиним в рамках Phase 3.1** — обновление `chat-vision` default требует подтверждения корректности catalog-записи; раз уж лезем — поправим contextWindow. Это не расширение scope, а sanity-fix на пути.
