# ТЗ-DEV3: Developer Panel для Onboarding

**Версия ТЗ:** 1.0
**Дата:** 2026-03-01
**Версия проекта:** 3.58.0 → 3.59.0
**Зависимости:** ТЗ-DEV1 (v3.57.0), ТЗ-DEV2 (v3.58.0)

---

## Контекст проблемы

В режиме онбординга брифинга модель систематически галлюцинирует — утверждает что вызывала инструменты (deepResearch, fetchUrl, readTelegramChannel), хотя на самом деле не делала этого. Guardian в bypass-режиме только логирует, но не блокирует. Для будущего FIX4 (борьба с галлюцинациями) критически важно **видеть** что происходит внутри: какие инструменты вызваны, с какими параметрами, что вернулось, а что — выдумано.

DEV1 (v3.57.0) уже даёт базу: модель, токены, стоимость, время под каждым ответом. Но:
1. DEV1 работает только в основном чате (`Chat` компонент) — не в онбординге (`BriefingChatPanel`)
2. Нет детализации tool calls — нельзя увидеть что именно вернул fetchUrl или readTelegramChannel
3. Нет предупреждений о проблемах с источниками (blocked, невалидный канал, мало постов)

---

## Цель

Панель разработчика в режиме онбординга брифинга (`/briefing/setup`), позволяющая видеть:
- **Все tool calls** с параметрами и результатами
- **Верификацию источников** — RSS найден? Контент читается? Канал валиден?
- **Содержимое updateBriefingPreview** — snapshot данных на момент записи
- **Предупреждения** — мёртвые источники, blocked контент, мало постов

---

## Требования (от архитектора)

### 1. Tool Calls трассировка

Для каждого вызова deepResearch, fetchUrl, readTelegramChannel, updateBriefingPreview показать:
- Что вызвано (tool name)
- С какими параметрами (args)
- Что вернулось (structured result)
- Сколько заняло (duration)

**Главное** — видеть использовал ли агент инструменты или ответил «из головы».

### 2. Source Verification результаты

**fetchUrl:**
- RSS найден или нет? (`rssUrl` field)
- Контент читается или blocked? (content length, source method)

**readTelegramChannel:**
- Канал валидный? (`isValid`)
- Сколько постов найдено

### 3. updateBriefingPreview содержимое

Что агент записал в превью:
- Сколько тем (topic count + names)
- Сколько источников (source count)
- Какие URL добавлены

Видеть snapshot данных на момент записи.

### 4. Cost Breakdown (по аналогии с DEV2)

Полная разбивка стоимости по шагам/инструментам — как в Pipeline Trace DEV2:
- **Per-step cost** — стоимость каждого AI-шага (input/output tokens × rate)
- **Per-tool cost** — сколько стоил каждый deepResearch, fetchUrl и т.д. (учитывая что deepResearch использует Perplexity API с отдельной стоимостью)
- **Total cost** с процентным breakdown
- **Bar chart** визуализация (какой шаг съел больше всего бюджета)

**Зачем:** Понимать на что расходуется бюджет → решать какую модель заменить (если дорого) или усилить (если дёшево). Критично для оптимизации.

### 5. Warnings (по аналогии с DEV2)

- RSS обнаружен но не проверен fetch-ом
- Источник partial/degraded (контент не полностью прочитан)
- Канал с малым числом постов (< 3)
- fetchUrl не смог прочитать RSS-фид
- readTelegramChannel вернул `isValid: false`
- Инструмент упомянут в тексте но НЕ вызван (Guardian detection)

## Формат

**Тот же Drawer что в DEV1**, но с дополнительной секцией **"Tools"** между Timeline и Guardian. Каждый tool call как раскрываемый блок.

**Footer** — компактная строка под каждым ответом ассистента (как в DEV1):
```
Sonnet 4.6 · 1.5K tok · ₽0.12 · 3 tools · 2.3s
```

Добавлен счётчик `tools` — общее число tool calls в этом ответе.

---

## Технические ограничения

- ONLY активно при `SIMPLY_DEV_MODE=true` (как DEV1/DEV2)
- Zero overhead в production
- Сервер (service-chat route) уже эмитит debug events — нужна только клиентская интеграция
- Переиспользовать `DevPanelFooter` и `DevPanelDrawer` из DEV1 (не дублировать)
- `TraceCollector` из DEV2 НЕ переиспользовать — он для пайплайнов, не для чатов
