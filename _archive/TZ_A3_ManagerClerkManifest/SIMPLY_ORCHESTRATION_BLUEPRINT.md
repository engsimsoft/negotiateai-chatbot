## 1. Контекст и цели

### Что решаем

Пользователь создаёт проект через Секретаря и попадает в пустой чат. Это не отличается от ChatGPT. Три проблемы:

- **Не знает с чего начать.** Пришёл с идеей — не знает как декомпозировать на шаги.
- **Контекстное окно заканчивается.** Длинный чат → деградация качества. Пользователь думает «AI плохо работает».
- **Нет контроля качества.** Первый черновик = финальный. Нет второго мнения.

### Вдохновение

Паттерн Orchestrator из Kilo Code: центральный агент разбивает задачу на подзадачи, делегирует специализированным режимам, каждая подзадача работает в изолированном контексте. Информация течёт вниз через инструкции, вверх через резюме.

### Адаптация для Simply

В Kilo пользователь — программист. В Simply — бизнесмен 40-60+. Поэтому:

- Пользователь = заказчик. Говорит «что» хочет, утверждает план, принимает результаты.
- Переключение между ролями — автоматическое. Пользователь видит прогресс, но не управляет маршрутизацией.
- Система учит правильному ведению проекта — последовательность, документация, контроль.

## 2. Роли системы

Четыре роли. Пользователь взаимодействует только с двумя (Менеджер и Эксперт).

### 2.1 Секретарь

| Параметр | Значение |
|---|---|
| **Где** | Страница создания проекта (уже работает) |
| **Модель (dev)** | Gemini |
| **Модель (prod)** | Gemini или Sonnet |
| **Общается с пользователем** | Да |

Быстрое интервью → паспорт проекта (название, описание, контекст). 2-3 минуты. Реализован в v3.11.

### 2.2 Менеджер проекта (Orchestrator)

| Параметр | Значение |
|---|---|
| **Где** | Страница проекта — панель управления |
| **Модель (dev)** | Gemini |
| **Модель (prod)** | Sonnet |
| **Общается с пользователем** | Да — при первом контакте, между задачами, при добавлении файлов |

**Что делает:**
- Встречает при первом входе в проект
- Разбирает загруженные документы (постоянная функция, не разовая)
- Создаёт и обновляет структуру папок
- Инициирует планирование (передаёт данные Профессору)
- Переводит план Профессора на язык пользователя (через Эксперта)
- Создаёт задачи в Пульсе на основе утверждённого плана
- Между задачами: подводит итог, предлагает следующий шаг
- Формирует резюме завершённых задач для передачи в следующие

**Чего НЕ делает:**
- Не выполняет задачи (это Эксперт)
- Не проверяет качество (это Профессор)
- Не ведёт экспертный диалог

### 2.3 Профессор (Стратег + Контроль качества)

| Параметр | Значение |
|---|---|
| **Где** | Бэкенд. Пользователь видит только результаты |
| **Модель (dev)** | Gemini |
| **Модель (prod)** | Opus |
| **Общается с пользователем** | Нет — только через Менеджера/Эксперта |

**Два момента участия:**

**На входе — планирование.** Получает: паспорт + manifest документов + tools_manifest + ответы на уточняющие вопросы. Работает по жёсткому фреймворку (раздел 6). Возвращает структурированный план.

**На выходе — проверка (опционально).** Получает результат задачи. Три вердикта:
- ✅ Одобрено — задача закрыта
- ⚠️ Замечания — показать пользователю, предложить доработать
- ❌ Критичные проблемы — на доработку

Режим Профессора — опциональный, по умолчанию включён. Менеджер объясняет на языке ценности: «проверка лучшей моделью = качество выше, но стоит дороже».

### 2.4 Эксперт (Аналитик + Собеседник)

| Параметр | Значение |
|---|---|
| **Где** | Чат задачи (каждая задача = отдельный чат) |
| **Модель (dev)** | Gemini |
| **Модель (prod)** | Sonnet |
| **Общается с пользователем** | Да — основной собеседник при работе над задачей |

**Что делает:**
- Ведёт диалог с пользователем внутри задачи
- Анализирует, предлагает варианты, обсуждает
- Использует инструменты (поиск, генерация документов, анализ)
- При планировании: переводит план Профессора на понятный язык
- Показывает прогресс tool use в Пульсе (🔍 Поиск..., 📊 Создание...)

### 2.5 Исполнитель (зарезервирован на будущее)

Не реализуется на первом этапе. Это backend-оптимизация: когда Эксперт вызывает tool (поиск, генерация), сам вызов может обрабатываться дешёвой моделью (Flash/Haiku). Пользователь этого не видит. По сути — Smart Routing на уровне tool execution.

## 3. Полный flow проекта

### Обзорная схема

```
ФАЗА 0          ФАЗА 1              ФАЗА 2           ФАЗА 3          ФАЗА 4
Секретарь   →   Подготовка      →   Планирование  →  Утверждение  →  Выполнение
(паспорт)       рабочего места      (Профессор)       плана           задач
                (Менеджер)                            (Эксперт)       (Эксперт)
                                                                      ↕
                                                                     Проверка
                                                                     (Профессор)
```

### Фаза 0 — Секретарь (реализован)

Быстрое интервью. Результат: паспорт проекта (название, описание, контекст).
Пользователь нажимает «Создать проект» → переход на страницу проекта.

### Фаза 1 — Подготовка рабочего места

**Триггер:** Первый вход в проект ИЛИ загрузка новых файлов в любой момент.

**1a. Первый контакт (Менеджер)**

Менеджер встречает пользователя:
- Показывает что прочитал паспорт
- Объясняет режим Профессора (ценность + стоимость): «Каждую задачу может проверить лучшая модель. Качество выше, стоит дороже. Включить?»
- Предлагает загрузить документы если их нет

**1b. Разбор документов (Менеджер — постоянная функция)**

> Это не разовая фаза, а сервис. Работает при каждой загрузке файлов, в любой момент жизни проекта.

Три режима запуска:
- **Автотриггер**: файл(ы) загружены → «Разобрать?» (одна кнопка)
- **Ручной**: пользователь просит Менеджера / нажимает кнопку
- **При первом входе**: если файлы уже есть

Процесс разбора:
1. Менеджер анализирует каждый документ (Gemini 2M контекста)
2. Предлагает папку для каждого файла. Диалог:
   - «Этот файл — договор с поставщиком. Предлагаю в папку "Юридические".»
   - Пользователь может согласиться, предложить другую папку, или отметить как личный
3. Создаёт структуру папок автоматически
4. Генерирует manifest (каталог файлов с описаниями)

**Два типа папок:**

| Тип | Видимость для AI | Назначение |
|---|---|---|
| **Рабочие** | Да — входят в контекст задач | «Финансы», «Маркетинг», «Юридическое» |
| **Личные** | Нет — только для пользователя | «Мои идеи», «Шпаргалки», «На будущее» |

**WOW-эффект:** Пользователь свалил хаотичную кучу документов → прошло время → всё разложено по папкам с понятными названиями. «Одна кнопка = решённая проблема.»

**Результат фазы:** Структурированная база знаний проекта:
- Папки с файлами
- Manifest (каталог): имя файла → описание → папка → тип → размер
- Готовность к передаче Профессору

### Фаза 2 — Планирование (Профессор)

**Триггер:** Пользователь подтверждает что документация собрана + нажимает «Начать планирование» (или Менеджер предлагает).

**Вход для Профессора:**
- Паспорт проекта
- Manifest документов (описания, структура папок)
- Tools manifest (список доступных инструментов)
- Ответы на уточняющие вопросы (если были)

**Процесс (по фреймворку — раздел 6):**

1. **Аудит данных:** Что есть? Чего не хватает?
2. **Аудит ресурсов:** Какие инструменты подключены? Какие рекомендуется подключить?
3. **Запрос недостающего:** Если данных недостаточно → вопросы пользователю через Менеджера. «Для планирования нужна информация о [X]. Подключите GitHub / загрузите ZIP с данными / ответьте на вопросы.»
4. **Декомпозиция:** Разбивка на задачи с зависимостями
5. **Финальный план:** Пронумерованный список задач

**Пользователь видит в Пульсе:** «🧠 Глубокий анализ проекта...»

**Результат:** Структурированный план (JSON/объект) с задачами, зависимостями, описаниями.

### Фаза 3 — Утверждение плана

**Триггер:** Профессор вернул план.

**Эксперт** переводит план на человеческий язык. Объясняет:
- Что будем делать и в каком порядке
- Почему именно такой порядок
- Сколько примерно задач
- Где нужно участие пользователя, а где система справится сама

**Пользователь** может:
- Утвердить план
- Обсудить и скорректировать (добавить/убрать/переставить задачи)
- Отправить на пересмотр Профессору

**Результат:** Утверждённый план → Менеджер создаёт задачи в Пульсе.

### Фаза 4 — Выполнение задач

**Принцип: строгая последовательность с возможностью обхода.**

Система учит правильному ведению проекта. Задачи выполняются по порядку. Причина: результат задачи N часто является входом для задачи N+1.

**Состояния задачи в Пульсе:**

| Статус | Визуал | Действие при клике |
|---|---|---|
| ✅ **Выполнена** | Зелёная галочка | Просмотр результатов |
| 🔄 **В работе** | Активная (выделена) | Перейти в чат |
| 🧠 **На проверке** | Пульсация | Ожидание вердикта Профессора |
| ⚠️ **Замечания** | Жёлтый | Просмотр замечаний, решение |
| ⬜ **Следующая** | Серая, разблокирована | Можно начать |
| 🔒 **Заблокирована** | Серая, замок | Предупреждение при попытке открыть |

**Клик на заблокированную задачу:**
> «Мы рекомендуем сначала завершить задачу [N]. Результаты этой задачи используются в следующих. Начать всё равно? Это на ваш страх и риск.»

Не блокировка — предупреждение. Пользователь взрослый, может решить сам.

**Выполнение одной задачи (цикл):**

```
Пользователь кликает задачу в Пульсе
    ↓
Новый чат с Экспертом (чистый контекст)
    ↓
Эксперт получает:
  • Паспорт проекта
  • Manifest документов (рабочие папки)
  • Описание текущей задачи (из плана)
  • Резюме завершённых задач (краткие выводы, не полная история)
  • Файлы, прикреплённые к задаче
    ↓
Эксперт НЕ получает:
  • Полную историю чатов предыдущих задач
  • Внутренние рассуждения Профессора
  • Историю диалога с Менеджером
    ↓
Работа: диалог, анализ, использование инструментов
    ↓
Результат готов → Эксперт предлагает завершить задачу
    ↓
[Если Профессор включён]
    Результат → Профессор → вердикт
    ✅ → задача закрыта
    ⚠️ → замечания пользователю
    ❌ → на доработку
    ↓
Менеджер: итог задачи, предложение следующей
```

**Резюме задачи:** После закрытия Менеджер сжимает результат до ключевых выводов и решений. Это резюме передаётся в контекст следующих задач. Не полная история — только выводы.

### Левая панель — Пульс проекта (постоянная)

Всегда видна. Содержит:

**📋 План** — список задач со статусами. Клик → открывает задачу в рабочей области. Активная задача выделена. Заблокированные — серые с замком.

**📁 Файлы** — структура папок проекта. Рабочие папки + личные (📌). Кнопка «+ Загрузить» → триггер разбора. Клик на файл → просмотр (FileViewer уже есть).

**💡 Идеи** — блок для заметок. Пользователь в любой момент может сказать «запиши идею» или нажать +. Не мешает текущей работе, не теряется.

**⚙️ Паспорт** — сворачиваемый блок. Название, описание, контекст проекта. Настройки (вкл/выкл Профессор, модели).

### Рабочая область — контекстная (центр)

Содержимое зависит от текущей фазы/действия:

| Контекст | Что отображается |
|---|---|
| Первый вход | Диалог с Менеджером (встреча, разбор файлов) |
| Планирование | Прогресс Профессора → объяснение плана Экспертом |
| Задача выбрана | Чат с Экспертом (изолированный контекст задачи) |
| Задача завершена (просмотр) | История чата задачи (read-only) + результаты |
| Между задачами | Итог от Менеджера + предложение следующей задачи |

### 5.5 Пульс проекта — обновление в реальном времени

**Фоновая активность Эксперта** (tool use в процессе):

Когда Эксперт использует инструменты (поиск, генерация), прогресс отображается в Пульсе. Технически: streaming response от API уже содержит tool_use events. Клиент перехватывает их и показывает в панели Пульса.

```
Tool call: web_search("конкуренты кофейня Арбат")
→ Пульс: 🔍 Поиск конкурентов...

Tool call: create_document(type: "spreadsheet", ...)
→ Пульс: 📊 Создание таблицы...

Tool call finished
→ Строчка исчезает
```

Не WebSocket — используется существующий streaming (SSE от Vercel AI SDK). Пульс подписывается на события текущего чата.

### 5.6 Карта хранения данных

> Полная карта: что создаётся, кем, где хранится, кто потребляет.

| Что | Кто создаёт | Где хранится | Кто потребляет |
|---|---|---|---|
| Паспорт проекта | Секретарь | `Project.context` | Менеджер, Профессор, Эксперт |
| Manifest файлов | Менеджер | `Project.manifestJson` | Профессор, Эксперт |
| Полный отчёт планирования | Профессор | `Project.planReport` | Менеджер, пользователь (по запросу) |
| Структурированный план | Профессор → Менеджер | `Project.planJson` | Пульс, создание ProjectTask |
| Резюме задачи | Менеджер | `ProjectTask.outputSummary` | Эксперт (в следующих задачах), пользователь |
| Артефакты задачи | Эксперт | `ProjectFile` (taskId + source) | Пользователь, следующие задачи |
| Вердикт Профессора | Профессор | `ProjectTask.professorVerdict` | Пользователь, Эксперт (при доработке) |
| Итог длинного диалога | Автоматически | `ProjectFile` (snapshot) + `Chat.snapshots` | Продолжение того же чата |
| Идеи | Пользователь | `ProjectIdea` | Пользователь |

### 5.7 Привязка артефактов к задачам

Когда Эксперт создаёт документ (презентацию, таблицу, текст) — это артефакт задачи. Привязка через `ProjectFile`:

```
ProjectFile:
  taskId — к какой задаче относится
  source — кто создал:
    'upload'            — загружен пользователем
    'generated'         — создан Экспертом (артефакт)
    'snapshot'          — итог длинного диалога
    'professor_report'  — отчёт Профессора
  role — зачем:
    'input'     — входные данные для задачи
    'output'    — результат работы
    'reference' — справочный материал
```

При завершении задачи видно: какие файлы были входом, какие — результатом. Следующая задача может получить конкретные артефакты предыдущей.

### 5.8 Полная карта потоков данных между ролями

```
Секретарь
  ВЫХОД → Project.context (паспорт)

Менеджер (разбор файлов)
  ВХОД  ← Project.context + загруженные файлы
  ВЫХОД → ProjectFolder (папки)
         → ProjectFile (файлы с описаниями, source='upload')
         → Project.manifestJson (каталог)

Профессор (планирование)
  ВХОД  ← Project.context + manifestJson + tools_manifest + userAnswers
  ВЫХОД → Project.planReport (полный анализ — текст)
         → Project.planJson (структурированный план — JSON)
         → ProjectFile (отчёт, source='professor_report')

Менеджер (создание задач)
  ВХОД  ← Project.planJson
  ВЫХОД → ProjectTask[] (задачи в Пульсе)

Эксперт (выполнение задачи)
  ВХОД  ← Project.context
         + Project.manifestJson (только рабочие папки)
         + ProjectTask.description (текущая задача)
         + [предыдущие ProjectTask.outputSummary]
         + [ProjectFile где taskId = предыдущие и role = 'output']
         + [последний Chat.snapshot если был авто-итог]
  ВЫХОД → Chat messages (история)
         → ProjectFile (артефакты, source='generated', role='output')
         → ProjectFile (snapshot, source='snapshot') — при авто-итоге

Менеджер (завершение задачи)
  ВХОД  ← Chat messages последние + артефакты задачи
  ВЫХОД → ProjectTask.outputSummary (резюме для следующих)
         → ProjectTask.status = 'done' | 'review'

Профессор (проверка)
  ВХОД  ← ProjectTask.outputSummary + артефакты задачи (role='output')
  ВЫХОД → ProjectTask.professorVerdict
         (JSON: verdict, shortSummary, fullAnalysis)
```

## 6. Фреймворк планирования Профессора

Жёсткая структура. Профессор работает по ней, не импровизирует.

### 6.1 Аудит входных данных

Что известно из паспорта? Что известно из manifest? Что НЕ известно, но критично?

**Результат:** Список вопросов к пользователю (если нужны).

### 6.2 Аудит ресурсов и инструментов

**Какие данные есть?** Документы из manifest, их содержание.

**Какие инструменты подключены?** Tools manifest:
```
<available_tools>
  <tool name="web_search" status="connected" />
  <tool name="file_generation" status="connected" capabilities="docx, pptx, xlsx" />
  <tool name="file_analysis" status="connected" />
  <tool name="github" status="not_connected" />
  <tool name="google_drive" status="not_connected" />
</available_tools>
```

**Какие рекомендуется подключить?** С обоснованием: зачем, на какой задаче, что будет если не подключить.

### 6.3 Декомпозиция на задачи

Для каждой задачи:
- Цель (одно предложение)
- Входные данные (откуда: от пользователя / из предыдущей задачи / из инструмента)
- Ожидаемый результат
- Требуемые инструменты
- Нужна ли проверка Профессором

### 6.4 Карта зависимостей

- Какие задачи строго последовательны?
- Какие можно делать параллельно? (на будущее — сейчас строго последовательно)

### 6.5 Анализ рисков

- Где проект может «сломаться»?
- Где пользователь скорее всего застрянет?
- Где обязателен контроль качества?

Пронумерованный список. Каждая задача:

## 7. Изоляция контекста

### Проблема
Длинный чат → контекст переполняется → деградация качества.

### Решение: два уровня изоляции

**Уровень 1 — между задачами.** Каждая задача = отдельный чат с чистым контекстом.

**Уровень 2 — внутри задачи.** Длинный диалог внутри одной задачи → авто-итог → сброс контекста (раздел 8).

### Что получает Эксперт при открытии задачи

| Данные | Источник | Размер |
|---|---|---|
| Паспорт проекта | Секретарь | ~500 токенов |
| Manifest документов | Менеджер | ~1-3K токенов |
| Описание текущей задачи | Профессор (план) | ~500 токенов |
| Резюме предыдущих задач | Менеджер | ~500-1K на задачу |
| Последний snapshot (если был) | Авто-итог | ~1-2K токенов |
| Файлы задачи | Прикреплённые | Варьируется |

**Итого system prompt:** ~5-10K токенов. Чистый контекст, максимум места для работы.

### Что НЕ получает
- Полную историю чатов предыдущих задач
- Историю чата ДО последнего snapshot (если был авто-итог)
- Внутренние рассуждения Профессора
- Диалог с Менеджером
- Личные файлы пользователя

## 8. Управление контекстным окном (авто-итог)

### Проблема

Пользователь не знает что такое токены и контекстное окно. Он работает над задачей, диалог растёт, качество падает. Пользователь думает «AI стал хуже работать».

### Решение: автоматическая «передача смены» внутри задачи

Итог создаётся как Markdown-артефакт в чате. Это одновременно:
- **Документ для пользователя** — можно открыть, прочитать, убедиться что ничего не потеряно
- **Триггер для сброса** — всё что было ДО итога больше не передаётся модели
- **Файл проекта** — сохраняется в ProjectFile, доступен в любой момент

### Когда срабатывает

| Триггер | Действие |
|---|---|
| **70% контекстного окна** | Эксперт мягко предлагает зафиксировать |
| **Пользователь просит** «подведи итог» | Немедленно |
| **Задача завершается** | Финальный итог → outputSummary для следующих задач |

При 70% — мягкое предложение, не принудительное: «Мы много наработали, предлагаю зафиксировать ключевые моменты.» Пользователь может согласиться или попросить подождать.

### Как выглядит для пользователя

```
... диалог ... 50 сообщений ...

Эксперт: «Мы уже многое проработали. Зафиксирую 
ключевые моменты, чтобы продолжить эффективно.»

┌─────────────────────────────────────┐
│ 📋 Итог работы                      │
│                                     │
│ ## Решения                          │
│ - Выбрана стратегия X               │
│ - Ценообразование: модель Y         │
│                                     │
│ ## Создано                          │
│ - Таблица сравнения конкурентов     │
│ - Черновик ценовой политики         │
│                                     │
│ ## Продолжаем                       │
│ - Доработать финансовую модель      │
│ - Согласовать скидочную политику    │
│                                     │
│              [Открыть]              │
└─────────────────────────────────────┘

Эксперт: «Всё зафиксировано. Продолжаем — 
нам осталось доработать финансовую модель.»

... новый чистый контекст, но тот же чат ...
```

### Что происходит технически

```
1. Мониторинг: каждый API-вызов возвращает usage.total_tokens
   Клиент отслеживает заполнение (порог: 70% от лимита модели)

2. Триггер: модель вызывает tool createTaskSnapshot
   Генерирует структурированный итог:
   - decisions[]     — принятые решения
   - currentState    — где остановились
   - artifacts[]     — созданные файлы
   - openQuestions[] — нерешённые вопросы
   - nextSteps[]     — что делать дальше

3. Сохранение:
   → Markdown-артефакт в ProjectFile (source='snapshot')
   → Маркер в Chat.snapshots [{messageId, fileId, createdAt}]
   → Сообщение в чате с isSnapshot=true

4. Сброс контекста (при следующем API-вызове):
   System prompt: паспорт + manifest + задача + резюме предыдущих задач
   + содержимое ПОСЛЕДНЕГО snapshot (вместо полной истории)
   + сообщения ПОСЛЕ snapshot (новые)
   Старые сообщения НЕ отправляются модели

5. Для пользователя:
   Скроллит вверх → видит ВСЮ историю (включая до итога)
   Визуальный разделитель:
   
   ... старые сообщения (приглушённые) ...
   ──────── 📋 Итог зафиксирован ────────
   ... новые сообщения (обычные) ...
```

### Множественные итоги

Если задача длинная, итогов может быть несколько. Каждый новый включает предыдущий (обновляет, не накапливает). Модель всегда видит только последний snapshot.

```
История в БД: [msg1..msg50, snapshot1, msg51..msg100, snapshot2, msg101..]
Что видит модель: system_prompt + snapshot2 + [msg101..]
Что видит пользователь: всё (с разделителями)
```

### Структура snapshot

```typescript
interface TaskSnapshot {
  taskId: string;
  snapshotIndex: number;     // 1, 2, 3... (порядковый номер в задаче)
  createdAt: Date;
  decisions: string[];       // Принятые решения
  currentState: string;      // Где остановились
  artifacts: string[];       // Созданные файлы (ссылки)
  openQuestions: string[];   // Нерешённые вопросы
  nextSteps: string[];       // Что делать дальше
  fullMarkdown: string;      // Полный текст для артефакта
}
```

## 9. Прозрачность для пользователя

### Принцип: «Прозрачная кухня»

Ресторан с открытой кухней: видно что готовят, но не лезешь к плите. Пользователь не хочет видеть внутренности, но хочет чувствовать контроль.

### Три уровня глубины (Progressive Disclosure)

| Уровень | Что | Где | Для кого |
|---|---|---|---|
| **Поверхность** | Статусы задач, прогресс, уведомления | Пульс, основной UI | Все |
| **Детали** | Вердикт Профессора, резюме задач, план, итоги | Клик на элемент | Все, кто хочет |
| **Глубина** | Полный отчёт Профессора, развёрнутый анализ | Кнопка «Подробнее» | Продвинутые |

### Что показывать

**Всегда видно (поверхность):**
- Статусы задач в Пульсе
- Прогресс tool use (🔍 Поиск..., 📊 Создание...)
- Уведомления от Менеджера («задача завершена», «Профессор проверил»)

**По клику (детали):**
- **Вердикт Профессора** — пользователь заплатил за проверку, он должен видеть результат. Краткий формат: что хорошо, что исправить, общая оценка.
- **План проекта** — полный план с задачами, зависимостями, обоснованием порядка. Доступен в любой момент через «📋 План» в Пульсе.
- **Резюме завершённых задач** — клик на ✅ задачу → что сделано, какие решения, какие файлы.
- **Итоги (snapshots)** — Markdown-артефакты в чате. Пользователь может открыть и прочитать.
- **Manifest файлов** — структура папок + описание каждого файла.

**По запросу (глубина):**
- **Полный отчёт Профессора** (planReport) — аудит данных, анализ рисков, обоснования. Кнопка «Подробнее» рядом с планом.

**Не показывать:**
- Сырой JSON (план, manifest, verdict)
- System prompt injection (что именно получает модель)
- Chain of thought Профессора
- Детали tool use (конкретные промпты к поисковику, raw response)

### Технически: двойной формат

Профессор генерирует результаты в двух форматах:

```
professorVerdict: {
  verdict: 'approved' | 'issues' | 'critical',
  shortSummary: "Работа выполнена качественно. Одно замечание: ...",  // для UI
  fullAnalysis: "## Анализ\n### Логика\n...",  // для «Подробнее»
  issues: [{ severity, description, suggestion }]  // структурированно
}
```

## 10. Открытые вопросы

### 10.1 Проверка Профессором — синхронная или асинхронная?

**Варианты:**
- **Синхронная:** Пользователь ждёт вердикт (30-60 сек для Opus). Простая реализация, но ожидание.
- **Асинхронная:** Пользователь может начать следующую задачу, вердикт приходит уведомлением. Сложнее, но лучший UX.

**Рекомендация:** На первом этапе — синхронная. Показываем прогресс: «🧠 Профессор проверяет...» с галочками. Асинхронная — оптимизация на будущее.

### 10.2 Редактирование плана в процессе

Что если на задаче 3 пользователь понимает что нужна дополнительная задача?

**Предложение:** Менеджер может добавить задачу в план (вставить между существующими, обновить зависимости). Но это v2 — на первом этапе план фиксирован после утверждения.

### 10.3 Простые проекты

Не все проекты требуют полного цикла. «Адаптировать материалы для Казахстана» — не нужен Opus для планирования.

**Предложение:** Менеджер оценивает сложность. Для простых проектов план составляет Эксперт (Sonnet/Gemini) в диалоге — без фреймворка Профессора. Критерий: количество задач ≤ 3 → упрощённое планирование.

### 10.4 Параллельные задачи

Профессор может определить что некоторые задачи можно делать параллельно. На первом этапе — строго последовательно. На будущее: параллельные задачи разблокируются одновременно, пользователь выбирает с какой начать.

### 10.5 Manifest — формат и хранение

**Первый этап (без RAG):** JSON/Markdown файл в БД проекта. Описание каждого файла: имя, тип, папка, краткое содержание (2-3 предложения). Передаётся в system prompt.

**Второй этап (с RAG):** Описания → embeddings в pgvector. Поиск по содержимому документов. Manifest остаётся как индекс, но Эксперт может запрашивать конкретные фрагменты.

## 11. План реализации (порядок ТЗ)

> Каждый пункт — отдельное короткое ТЗ. Не один монолитный документ.

### Этап A: Фундамент (новая страница проекта)

**ТЗ-A1: Новая страница проекта — layout**
- Двухколоночный layout (Пульс слева + Рабочая область справа)
- Компоненты Пульса (пока пустые): План, Файлы, Идеи, Паспорт
- Рабочая область — пока placeholder
- БД: phase в Project, таблица ProjectTask (структура)

**ТЗ-A2: Файловая система проекта**
- Таблицы ProjectFolder + ProjectFile
- UI: дерево папок в Пульсе, загрузка файлов
- Два типа папок (рабочие / личные)
- Интеграция с FileViewer (уже есть)

**ТЗ-A3: Менеджер — первый контакт + разбор файлов**
- Промпт Менеджера (из PE после проработки)
- Диалог в рабочей области (ServiceChat)
- Tool: createFolder, moveFile, updateManifest
- Триггер при загрузке файлов
- Manifest (каталог файлов) — генерация и хранение

### Этап B: Планирование

**ТЗ-B1: Профессор — планирование**
- API endpoint для планирования
- Передача данных: паспорт + manifest + tools
- UI: прогресс в рабочей области
- Сохранение плана (planJson + planReport) в БД

**ТЗ-B2: Утверждение плана + создание задач**
- Эксперт объясняет план (чат)
- UI: кнопки утвердить/обсудить
- Создание ProjectTask из плана
- Пульс: отображение задач со статусами

### Этап C: Выполнение задач

**ТЗ-C1: Задачи — открытие + изоляция контекста**
- Клик на задачу → создание чата с чистым контекстом
- System prompt injection (паспорт + manifest + задача + резюме)
- Навигация между задачами в Пульсе
- Блокировка/предупреждение для задач не по порядку

**ТЗ-C2: Авто-итог (управление контекстным окном)**
- Мониторинг usage.total_tokens на клиенте
- Tool createTaskSnapshot для модели
- Markdown-артефакт в чате + сохранение в ProjectFile
- Сброс контекста: snapshot заменяет историю для модели
- Визуальный разделитель в чате (старые сообщения приглушены)

**ТЗ-C3: Завершение задачи + резюме**
- Кнопка «Завершить задачу»
- Менеджер формирует outputSummary
- Обновление статуса в Пульсе
- Разблокировка следующей задачи

**ТЗ-C4: Проверка Профессором (опционально)**
- Результат → Opus → вердикт (shortSummary + fullAnalysis)
- UI: три состояния (одобрено, замечания, критично)
- Доработка при замечаниях

### Этап D: Полировка

**ТЗ-D1: Прозрачность — доступ к внутренним документам**
- Просмотр вердикта Профессора (краткий + подробный)
- Просмотр полного отчёта планирования (planReport)
- Просмотр резюме завершённых задач
- Progressive Disclosure: поверхность → детали → глубина

**ТЗ-D2: Блок Идеи**
- Таблица ProjectIdea
- UI в Пульсе
- Быстрое добавление из чата задачи

**ТЗ-D3: Переключение провайдеров**
- Config проекта: роль → модель
- UI настройки в Паспорте
- Переключение dev → prod

- **Биллинг / стоимость** — отдельная задача
- **Smart Routing для tools** (Исполнитель) — оптимизация на будущее
