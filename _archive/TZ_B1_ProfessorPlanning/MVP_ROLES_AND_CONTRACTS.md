# Simply MVP — Карта ролей и контрактов

**Версия:** 1.1 (после ревью архитектора)  
**Дата:** 2026-02-08  
**Назначение:** Единый справочник для написания промптов. Фиксирует роли, границы, входы-выходы и порядок работы.  
**Источники:** CONCEPT_Project_Orchestration.md (PE), SIMPLY_ORCHESTRATION_BLUEPRINT.md (Архитектура), ответы архитектора на блокирующие вопросы, ревью архитектора v1.0.  
**Статус:** Согласован PE + Архитектура. Готов к использованию.

## 1. Общая архитектура MVP

### Принцип

Пользователь — заказчик. Говорит «что» хочет, утверждает план, принимает результаты. Система декомпозирует, выполняет, проверяет. Переключение между ролями — автоматическое.

### Роли в MVP

| Роль | Модель (prod) | Общается с пользователем | Где живёт | Суть |
|---|---|---|---|---|
| **Секретарь** | Gemini Pro | Да | Страница создания проекта | Интервью → паспорт. Реализован ✅ |
| **Менеджер** | Sonnet | Да | Drawer (боковая панель) на странице проекта | Координатор. Диалог, навигация, объяснения |
| **Профессор** | Opus | Нет | Backend | Планирование + проверка качества |
| **Эксперт** | Sonnet | Да | Отдельный чат на странице задачи | Основной собеседник при работе над задачей |
| **Клерк-анализатор** | Haiku/Flash | Нет | Backend endpoint | Анализ загруженных файлов |
| **Клерк-суммаризатор** | Haiku/Flash | Нет | Backend endpoint | Формирование резюме завершённых задач |

### Ключевое архитектурное решение

**Менеджер и Эксперт — разные чаты, разные контексты, разные экраны.**

Пользователь общается с Менеджером в боковой панели на странице проекта. С Экспертом — в отдельном чате на странице задачи. Визуально это разные «люди» с разными аватарками. Handoff между ними не нужен — пользователь сам переходит между страницами, как переходит из приёмной в переговорную.

### Что делает backend, а что — промпт

| Действие | Кто | Тип |
|---|---|---|
| Встреча пользователя, первый контакт | Менеджер | Промпт (диалог) |
| Анализ загруженных файлов | Клерк-анализатор | Backend endpoint + промпт клерка |
| Создание папок, manifest | Backend | Автоматически по результатам клерка |
| Планирование проекта | Профессор | Backend endpoint + промпт Профессора |
| Объяснение плана пользователю | Менеджер | Промпт (диалог, план в контексте) |
| Утверждение плана → создание задач | Backend | Кнопка → backend создаёт ProjectTask из planJson |
| Работа над задачей | Эксперт | Промпт (диалог с tools) |
| Формирование резюме задачи | Клерк-суммаризатор | Backend endpoint + промпт клерка |
| Проверка результата | Профессор | Backend endpoint + промпт Профессора |
| Навигация между задачами | Менеджер | Промпт (диалог) |

## 2. Контракты ролей

### 2.1 Менеджер проекта

**Суть:** Координатор-собеседник. Не создаёт сущности, не вызывает tools. Получает данные как контекст, общается с пользователем.

**Три режима диалога:**

| Режим | Триггер | Что получает в контексте | Что делает |
|---|---|---|---|
| **Первый контакт** | Пользователь впервые заходит в проект | Паспорт проекта | Приветствует, показывает что понял проект, объясняет режим Профессора, предлагает загрузить файлы или начать планирование |
| **Представление плана** | Профессор вернул план | Паспорт + manifest + planJson + planReport | Объясняет план на языке пользователя, отвечает на вопросы, помогает принять решение (утвердить / обсудить / пересмотреть) |
| **Навигация** | Задача завершена / пользователь возвращается | Паспорт + manifest + статусы задач + резюме завершённых | Подводит итог, предлагает следующую задачу, отвечает на вопросы о проекте |

**Контракт:**

```
ВХОД (system prompt injection, зависит от режима):
  passport: { name, description, context }
  manifest: { files: [...] }                    // если есть файлы
  phase: string                                  // текущая фаза проекта
  planJson: { tasks: [...] }                     // если план создан
  planReport: string                             // если план создан
  taskStatuses: [{ title, status, summary }]     // если задачи существуют
  professorEnabled: boolean                     // по умолчанию true, toggle в UI настроек проекта

ВЫХОД (только текст диалога):
  Менеджер НЕ возвращает structured data
  Менеджер НЕ вызывает tools
  Менеджер НЕ создаёт сущности в БД
  Все действия (создание задач, папок и т.д.) — через UI-кнопки → backend

Если professorEnabled = true: в первом контакте объясняет ценность проверки.
Если professorEnabled = false: не упоминает проверку, адаптирует навигацию между задачами.
```

**Тон:** Деловой, но тёплый. «Проектный менеджер в хорошем бюро» — собранный, конкретный, уважительный. Не заискивает, не перегружает информацией.

### 2.2 Профессор (планирование)

**Суть:** Автономный аналитик. Один вызов — structured JSON output. Не общается с пользователем.

**Контракт планирования:**

```
ВХОД:
  passport: { name, description, context }
  manifest: { files: [{ name, description, folder, type, size }] }
  toolsManifest: { tools: [{ name, status, capabilities }] }
  // MVP: захардкоженный список (web_search, file_generation, file_analysis)
  // Будущее: динамический реестр из подключённых интеграций
  userAnswers: [string]                          // ответы на уточняющие вопросы (если были)

ВЫХОД (structured JSON):
  {
    questions: [string]                          // вопросы к пользователю (если данных недостаточно)
    // ИЛИ полный план:
    tasks: [{
      order: number,
      title: string,
      description: string,                       // подробное описание для Эксперта
      goal: string,                              // одно предложение
      input: string,                             // что нужно для начала
      expectedOutput: string,                    // что должно получиться
      dependencies: [number],                    // от каких задач зависит (по order)
      tools: [string],                           // какие инструменты нужны
      needsReview: boolean,                      // нужна ли проверка Профессором
      reviewReason: string                       // почему нужна / не нужна проверка
    }],
    risks: [{ description, severity, mitigation }],
    recommendations: [{
      type: 'connect_tool' | 'upload_data' | 'clarify',
      description: string,
      impact: string                             // что будет если не сделать
    }],
    planReport: string                           // полный текст анализа (Markdown) для "Подробнее"
  }
```

**Фреймворк (6 шагов, жёсткая последовательность):**
1. Аудит входных данных → что есть, чего не хватает
2. Аудит ресурсов и инструментов → что подключено, что рекомендуется
3. Декомпозиция на задачи → цель, вход, выход, инструменты, нужна ли проверка
4. Карта зависимостей → последовательность, блокировки
5. Анализ рисков → где сломается, где застрянет пользователь
6. Финальный план → пронумерованный список с обоснованием порядка

### 2.3 Профессор (проверка)

**Суть:** Получает результат задачи, возвращает вердикт. Один вызов.

**Контракт проверки:**

```
ВХОД:
  passport: { name, description, context }
  taskDescription: { title, goal, expectedOutput }
  outputSummary: string                          // резюме выполненной работы
  artifacts: [{ name, type, content_preview }]   // созданные файлы (превью)

ВЫХОД (structured JSON):
  {
    verdict: 'approved' | 'issues' | 'critical',
    shortSummary: string,                        // 2-3 предложения для UI
    fullAnalysis: string,                        // Markdown для "Подробнее"
    issues: [{
      severity: 'minor' | 'major' | 'critical',
      description: string,
      suggestion: string
    }]
  }
```

**Критерии проверки:** Логика, полнота, противоречия, соответствие плану, соответствие expectedOutput.

### 2.4 Эксперт

**Суть:** Основной собеседник пользователя при работе над задачей. Диалог + tools. Каждая задача — отдельный чат с чистым контекстом.

**Контракт:**

```
ВХОД (system prompt injection при создании чата задачи):
  passport: { name, description, context }
  manifest: { files: [...] }                     // только рабочие папки
  currentTask: {
    title, description, goal,
    input, expectedOutput,
    tools: [string]
  }
  previousSummaries: [{                          // резюме завершённых задач
    taskTitle: string,
    summary: string
  }]
  attachedFiles: [...]                           // файлы, прикреплённые к задаче
  lastSnapshot: string | null                    // последний итог (если был авто-итог)

ВЫХОД:
  Диалог с пользователем (текст)
  + артефакты через tools (документы, таблицы, презентации)
  + при завершении: сигнал backend что задача готова
```

**Tools Эксперта (MVP):**
- web_search — поиск в интернете
- file_generation — создание документов (docx, pptx, xlsx)
- file_analysis — анализ загруженных файлов
- createTaskSnapshot — создание итога (при авто-итоге)

**Авто-итог:**

При получении системного сигнала `[SYSTEM: Контекстное окно заполнено на X%...]` Эксперт:
1. Мягко предлагает пользователю зафиксировать прогресс
2. Создаёт структурированный итог через tool createTaskSnapshot
3. Итог содержит: decisions[], currentState, artifacts[], openQuestions[], nextSteps[]
4. Итог сохраняется как Markdown-артефакт в чате
5. После итога — продолжает работу, опираясь на snapshot + новые сообщения

**Fallback (пояс и подтяжки):** Если Эксперт не вызвал createTaskSnapshot в течение 5 сообщений после системного сигнала, backend принудительно вызывает Клерка-суммаризатора для текущего чата и подставляет snapshot при следующем API-вызове.

**Тон:** Думающий специалист. Архитектор в проектном бюро — анализирует, предлагает варианты, объясняет последствия. Не исполнитель-робот, а партнёр по задаче.

---

### 2.5 Клерк-анализатор файлов

**Суть:** Получает файл, возвращает структурированное описание. Маленький, узкий промпт.

**Контракт:**

```
ВХОД:
  fileName: string
  fileType: string (mime)
  fileSize: number
  fileContent: string | binary                   // содержимое или превью
  existingFolders: [string]                      // уже созданные папки (для рекомендации)

ВЫХОД (structured JSON):
  {
    description: string,                         // 1-2 предложения: что это за документ
    documentType: string,                        // "договор", "презентация", "отчёт" и т.д.
    suggestedFolder: string,                     // рекомендация по папке
    relevance: 'core' | 'reference' | 'unclear', // core — ключевой для проекта, reference — справочный, unclear — не удалось определить
    keyTopics: [string],                         // 2-3 ключевые темы (для manifest)
    language: string                             // язык документа
  }
```

---

### 2.6 Клерк-суммаризатор

**Суть:** Получает историю чата задачи + артефакты, возвращает резюме для передачи в следующие задачи.

**Контракт:**

```
ВХОД:
  taskTitle: string
  taskGoal: string
  chatHistory: [{ role, content }]               // последние N сообщений (или последний snapshot)
  artifacts: [{ name, type, content_preview }]   // созданные файлы

ВЫХОД (structured JSON):
  {
    summary: string,                             // 3-5 предложений: что сделано, ключевые решения
    keyDecisions: [string],                      // принятые решения (для контекста следующих задач)
    createdArtifacts: [{ name, description }],   // что создано
    openQuestions: [string]                       // нерешённые вопросы (если есть)
  }
```

## 3. Поток данных MVP

```
ФАЗА 0: Секретарь
  → Project.context (паспорт)

ФАЗА 1: Подготовка
  Пользователь загружает файлы
  → Backend вызывает Клерка-анализатора для каждого файла
  → Backend создаёт ProjectFolder, ProjectFile, обновляет Project.manifestJson
  → Менеджер получает manifest как контекст, общается с пользователем

ФАЗА 2: Планирование
  Пользователь нажимает "Начать планирование"
  → Backend вызывает Профессора (passport + manifest + tools)
  → Профессор возвращает planJson + planReport
  → Backend сохраняет в Project
  → Менеджер получает plan как контекст, объясняет пользователю

ФАЗА 3: Утверждение
  Пользователь нажимает "Утвердить план"
  → Backend создаёт ProjectTask[] из planJson
  → Пульс показывает задачи

ФАЗА 4: Выполнение (цикл по задачам)
  Пользователь кликает задачу
  → Backend создаёт Chat с чистым контекстом для Эксперта
  → Эксперт получает: passport + manifest + task + previousSummaries
  → Работа: диалог + tools
  → [Если авто-итог нужен: системный сигнал → snapshot → продолжение]
  → Пользователь завершает задачу (кнопка)
  → Backend вызывает Клерка-суммаризатора → outputSummary
  → [Если needsReview: Backend вызывает Профессора → verdict]
  → Задача закрыта, Менеджер предлагает следующую
```

## 4. Расширяемость (следующие этажи)

### Фундамент, заложенный в MVP

**Стандартный контракт клерка.** Любой клерк: получает structured input → возвращает structured JSON. Добавить нового клерка = написать промпт + создать endpoint. Ничего не ломается.

**Роли с лицом отделены от ролей-клерков.** Менеджер и Эксперт — стабильные промпты с характером. Клерки — заменяемые, оптимизируемые, масштабируемые.

**Данные между ролями — через БД.** Нет прямой связи между промптами. Каждый читает свой контекст из базы. Замена модели или промпта одной роли не влияет на остальные.

### Следующие этажи

| Этаж | Что добавляется | Что меняется в промптах |
|---|---|---|
| **2-й** | Клерк-планировщик (лёгкий, для простых проектов) | Менеджер получает флаг complexity → решает вызывать Профессора или клерка |
| **2-й** | Клерк-переводчик плана | Вместо Менеджера объясняющего план → клерк готовит user-friendly версию |
| **3-й** | Smart Routing для tools Эксперта | Дешёвая модель выполняет tool calls, Эксперт получает результаты. Промпт Эксперта не меняется |
| **3-й** | RAG для manifest | Manifest → pgvector. Эксперт получает инструкцию "запроси файл через tool" вместо полного manifest |
| **4-й** | Параллельные задачи | Профессор размечает параллельные задачи, Пульс разблокирует несколько |
| **5-й** | Менеджер с tool calling для делегирования | Менеджер сам вызывает клерков через tools вместо backend-цепочки |

**Принцип расширения промптов:** MVP-промпт решает MVP-задачи. Не усложняем «на будущее». При переходе на следующий этаж промпт адаптируется под новый контекст — это быстрая итерация, не рефакторинг.

## 5. Порядок разработки промптов

| # | Промпт | Зависит от | Сложность | Приоритет |
|---|---|---|---|---|
| 1 | **Профессор (планирование)** | Ничего | Средняя | Ядро ценности Simply |
| 2 | **Клерк-анализатор файлов** | Ничего | Низкая | Нужен для фазы 1 |
| 3 | **Менеджер** | Формат output Профессора | Средняя | Первый контакт пользователя |
| 4 | **Эксперт** | Формат задач из плана | Высокая | Основная работа |
| 5 | **Клерк-суммаризатор** | Формат output Эксперта | Низкая | Нужен при завершении задачи |
| 6 | **Профессор (проверка)** | Формат output суммаризатора | Средняя | Опциональный, но важный |

## 6. Ограничения MVP

- Максимум ~50 файлов в проекте (manifest в system prompt, без RAG)
- Задачи строго последовательные (нет параллельного выполнения)
- План фиксирован после утверждения (нет редактирования на ходу)
- Проверка Профессором — синхронная (пользователь ждёт 30-60 сек)
- Tools описываются вручную (без MCP)
- Менеджер без tool calling (только диалог)
- Промпты только под Claude (совместимость с Gemini не требуется)
